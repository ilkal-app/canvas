# @canvas/collab

## Purpose

The client side of sync: the connection to the relay, presence over awareness, the IndexedDB offline cache and reconnection.

## Public API

- `RecoveryConnection`: Connection status and subscription required by `CacheRecovery.attach`.
- `createCollabClient(options)`: Fetches the first token, loads the cached board into the store, then connects it to the relay; resolves with the `CollabClient`.
- `CollabClientSession`: What `CollabClient` is constructed with: the first token, its claims, the `TokenSource` of later ones, and an optional terminal cache refusal before any socket opens.
- `BoardTokenProvider`, `BoardTokenRequest`, `BoardTokenOptions`, `TokenSource`, `resolveTokenProvider(options)`: `getToken(request?): Promise<string>`, asked on every (re)connection with `{ isAfterRefusal }`: true when the relay refused the last token (a permission-denied answer, or a 4401 or 4403 close such as `access-changed`, in any state, `connecting` included) and none was accepted since, so a provider that keeps tokens asks its backend afresh, and `{ isRefresh: true }` when the token will replace an open connection's before it expires, so such a provider hands out a new one rather than the one it holds; exactly one of `getToken` and a fixed `token`; a fixed token wrapped as a provider.
- `CollabClient`: The sync client of one board: `status`, `lastSyncedAt`, `subscribe`, `disconnect`, `connect`, `destroy`, `presence`, `awareness`, `claims`, `layoutCarryOver`, `cacheWrites` (its binding's `writes`), `syncTimings()` (the first sync's `SyncTimings`, `undefined` before it).
- `ServerClock`, `estimateServerOffset`, `ServerOffset`, `ServerTimeSample`, `SERVER_TIME_SAMPLES`, `MAX_SERVER_TIME_ROUND_TRIP_MS`: The client's estimate of the relay's clock, handed to the client as `CollabClientOptions.serverClock`: each connection asks the relay's clock when it joins and with each keepalive answer, and the sample with the shortest of the last eight round trips wins (the relay's clock read halfway through it, wrong by at most half the round trip); `now()` reads the client's clock until the relay first answers. Shared timers count down on it.
- `ReactionChannel`, `ReactionSender`: A client's reactions, handed to it as `CollabClientOptions.reactions`: `send(drop)` sends on the current authenticated connection (false offline or before the relay accepts the token; the relay refuses a viewer's and anything past 10 a second), `subscribe(listener)` hears everyone else's as the relay fans them out with the sender's principal. Never stored, never presence state.
- `SyncTimings` (type): The first sync's phases in ms from monotonic marks: `authMs` (socket request to `authenticated`: WebSocket and TLS open, the relay's auth), `receiveMs` (to the relay's sync step 2 arriving) and `applyMs` (to synced: the step 2 applied, local updates acknowledged).
- `CollabClientOptions`, `CollabPresenceOptions`: Store, board, URL, `getToken` (or a fixed `token`), the readable layouts it declares, cache, layout converters, presence (name, colour, rate, timeout), backoff, idle timeout, and injected clock, scheduler, idle scheduler, random, transport, network, `onError`.
- `CollabStatus`, `CollabStatusListener`: `state`, `lastSyncedAt` (ms), `pendingUpdateCount`, `isReadOnly`, `isAcknowledged` (the relay has everything this connection holds: connected, its step 2, which carries edits restored from the cache, and every update since acknowledged, or connected read-only; the condition that holds compactions; the site forgets a board's unsent edits only on it), `rejectionReason`; a new frozen object per change.
- `CONNECTION_STATES`, `ConnectionState`: `connecting`, `connected`, `reconnecting`, `offline`, `unauthorized`, `outdated`.
- `CONNECTION_EVENTS`, `ConnectionEvent`, `nextConnectionState(state, event)`: The connection state machine, pure.
- `DEFAULT_IDLE_TIMEOUT_MS`: 30 000: a connection silent this long is dropped and retried.
- `DemoBusyNotice`, `DEMO_BUSY_REASON`: Reported when the relay turns a demo board visitor away for now (1013 `demo-busy`); the client retries.
- `decodeBoardToken(token)`, `BoardTokenClaims`, `TokenPrincipalType`: Reads a board token's claims without verifying it (the relay verifies); for identity, and the holder's feature flags (`features`) when the token carries them.
- `BOARD_TOKEN_ROLES`, `BoardTokenRole`: `owner`, `editor`, `commenter`, `viewer`.
- `createWebSocketFactory(webSocketClass?)`: The default transport over the platform `WebSocket` (browser, worker, Node 22).
- `CollabSocket`, `CollabSocketFactory`, `CollabSocketHandlers`, `WebSocketLike`: The transport seam: tests pass a fake that counts bytes.
- `createBrowserNetworkStatus(host?)`, `NetworkStatus`, `NetworkStatusHost`: `navigator.onLine` and the `online`/`offline` events; always online in Node.
- `DocumentCache`, `CachedBoard`: The device's copy of boards: `earlierLayouts` (optional), `load`, `readUpdates` (optional: the log without marking it seen), `append`, `compact(boardId, snapshot)` (false when another tab's newer snapshot is in the way), `delete`, `close`.
- `SnapshotPreviewCache`, `CachedSnapshotPreview`: Optional `DocumentCache.snapshotPreview`: current-layout-only `read` without advancing seen records, and atomic snapshot/opaque-preview `compact` under the same CAS and unseen-tail rules. Ordinary compaction clears a sidecar; inputs and read results are owned copies. Recovery publication clears the previous preview. A connection bound to an archived generation refuses active-generation preview reads and writes; later compaction preserves retained recovery metadata.
- `openIndexedDbCache(options?)`, `IndexedDbCacheOptions`, `DEFAULT_CACHE_DATABASE_NAME`: The writer-layout-scoped IndexedDB cache: a snapshot per board and an update log keyed by an auto-incremented `seq`; `writerLayoutVersion` (default `DOCUMENT_LAYOUT_VERSION`) names it, `onError` receives a legacy board the one-time copy could not read, and its `earlierLayouts` reads the `…:layout:<n>` databases below it.
- `deleteIndexedDbBoards(options)`, `IndexedDbBoardPurgeOptions`: Deletes the boards `isDeleted` picks (by their stored key) from every cache database of a namespace on the device: each writer layout's up to this build's, a later layout's the browser lists, and the unsuffixed pre- one; their snapshots and every update record, one transaction per database, after any already requested; the databases stay and none is created. The site deletes a person's boards with it when they sign out.
- `SnapshotStamp`, `snapshotDigest`, `isTrustedStamp`: What a cache stores beside a compacted snapshot (a fast digest of its bytes and the writing build's layout and schema versions), and whether a reopen may trust it for exactly those bytes and skip the trial store's second apply.
- `MemoryDocumentCache`, `MemoryCacheStorage`, `MemoryStoredBoard`: The same contract in memory, for tests and headless clients; one storage models several tabs.
- `prefixDocumentCache(cache, prefix)`: A view of a cache keeping every board under `prefix + boardId`, with every capability of the cache passed through (`earlierLayouts`, `readUpdates`, `snapshotPreview`): the site keeps each person's boards apart with it. Runs the shared cache contract (`cache/prefixed-document-cache.test.ts`), with a guard that it offers every member the cache does.
- `findUnsentChanges(board, store)`, `UnsentChanges`, `SyncedStore`: What a cached board's records hold that a store lacks (a struct past its state vector, or a deletion it has not made), as a count of records and one update; pure. The layout carry-over uses it; the site uses it to clear a board's unsent mark only when the connection's store covers the cache log.
- `EarlierLayoutCaches`, `EarlierLayoutBoard`: The copies of boards that builds writing earlier stored layouts left on the device: `writerLayoutVersion`, `find(boardId)` (oldest first, the unsuffixed pre- database's left-behind boards included, each copy with its `source`, the record keys read and `isPreLayoutCache`), `delete(boardId, copy)` (only the records read).
- `LayoutCarryOver`, `LayoutCarryOverOptions`, `StrandedEdits`: Once per open, after the first sync: deletes earlier-layout copies holding nothing the store lacks, converts and carries unsent edits when a converter exists, else keeps them in `stranded` until `dismiss(source)`; carried edits are stored by `storeDurably` before a copy goes.
- `DEFAULT_LAYOUT_CONVERTERS`, `findLayoutConverter(from, to, converters?)`, `layoutStepKey(from, to)`, `LayoutConverter`, `LayoutConverters`: The converters by stored-layout bump (`1->2` is the identity, by ruling; `2->3` is the identity; `3->4` is the identity) and how a bump's converter is found: the whole bump, else its single steps chained.
- `BoardCacheWrites`, `CacheWriteTracker`: A board cache's pending appends: `isPending` from request until the IndexedDB transaction completes or aborts, `subscribe` (on each change of it), `settled()` (waits until idle), `holdNewWork()` (defers compactions while the page is being hidden or unloaded), `workSettled()` (waits until every write and compaction requested so far, its cached preview included, has settled); the tracker counts promises given to `track`.
- `DocumentCacheBinding`, `DocumentCacheBindingOptions`, `DEFAULT_COMPACT_EVERY`, `DEFAULT_COMPACTION_IDLE_TIMEOUT_MS`: Restores a cached board into a store, stores every later update, compacts every 500 at idle time (10 s timeout); `writes` tracks each append until its transaction commits or aborts; `holdCompactionWhile(isHeld)` / `resumeCompaction()` keep records the relay lacks uncompacted (the collab client holds until everything is acknowledged). Optional `prepareSnapshotPreview` prepares display bytes before compaction; a revision change discards them, holds/destruction are rechecked after awaiting, and failed or unsupported preparation preserves ordinary compaction. Optional `yieldToBrowser` (also a `CollabClientOptions` field) makes `open` restore in browser tasks, through the store's `applyUpdateInSteps`.
- `OUTBOUND_CHUNK_BYTES`, `splitUpdate(update, maxBytes?)`: The chunk size whole transactions are merged up to (1 MiB), and the split of an update into struct-range chunks ordered by Yjs dependencies, then delete-only chunks (cuts transactions: only for a transaction above 7 MiB and a reconnect no replay covers).
- `planStoredReplay(log, remoteStateVector, localStateVector, maxBytes?)`, `StoredReplay`: Plans a large sync step 2 from the cache's logged transactions: those the relay lacks, cut to what it lacks and merged up to the chunk size, cut only between transactions; `undefined` when the log cannot cover the store.
- `SINGLE_TRANSACTION_BYTES`, `transactionChunks(update, maxWholeBytes?, chunkBytes?)`, `TransactionChunks`: The largest transaction sent whole in one message (7 MiB, under the relay's 8 MiB cap), and how one transaction is sent: whole, or cut by struct ranges above that.
- `MAX_UNACKNOWLEDGED_BYTES`: The most bytes of step 2 chunks and live updates a connection leaves unacknowledged (4 MiB; a larger single message goes alone).
- `UnsentChangesSplitWarning`: Reported once per client to `onError` when something is cut by struct ranges: a transaction above 7 MiB, or a reconnect no replay covers (a legacy compacted cache, an unreadable log, a cache without `readUpdates`).
- `UPDATE_TOO_LARGE_REASON`, `FRAME_TOO_LARGE_CLOSE_CODE`: `rejectionReason` `update-too-large` of a client the relay closed with 1009 after authentication for a frame past its limit (a struct too large to split); the client stops in `outdated`.
- `yieldToBrowser`: Lets the browser run waiting input and frames: `scheduler.yield()`, else a later macrotask (a `MessageChannel`, else a zero-delay timeout); never resolves in the current microtask checkpoint.
- `createIdleScheduler(host?)`, `IdleScheduler`, `IdleSchedulerHost`, `IdleTask`: Runs work at idle time: `requestIdleCallback` with a timeout, else a zero-delay timeout; injected in tests.
- `computeReconnectDelay(attempt, backoff?, randomValue?)`: The wait, in ms, before a reconnection attempt: exponential, capped, shortened by jitter.
- `ReconnectBackoff`, `DEFAULT_RECONNECT_BACKOFF`: Base delay, cap and jitter ratio; the default 250 ms, 10 000 ms, 0.5.
- `RECONNECT_BASE_DELAY_MS`, `RECONNECT_MAX_DELAY_MS`, `RECONNECT_JITTER_RATIO`: The first and the longest wait, in ms, and the largest share jitter removes.
- `PresenceChannel`: Presence over a Yjs `Awareness`: `setLocal`, `getLocal`, `getRemote`, `subscribe`, `recheckEditing` (checks peers' editing claims against the board again), `setHidden(isHidden)` (clears the local awareness state, so peers see the client leave, and holds every send until it is shown again with the state as last merged, an idle pooled MCP client), `destroy`, `clientId`. A silent peer is removed when the timeout passes (the sweep runs early for it, `nextSweepDelayMs`).
- `PresenceChannelOptions`, `PresencePrincipalInput`: What a channel is built from: awareness, principal (colour optional), rate (Hz), timeout (ms), clock, scheduler, and `objectExists` (a peer's editing claim on an object the board does not hold is dropped, the rest of its presence kept).
- `PresenceListener`: Receives the remote snapshot after each inbound flush that changed it.
- `DEFAULT_PRESENCE_TIMEOUT_MS`, `MIN_PRESENCE_TIMEOUT_MS`, `MAX_PRESENCE_TIMEOUT_MS`: 30 000, 20 000 and 30 000 ms: how long a silent remote client stays; 30 s is y-protocols' own cap.
- `PresenceState`, `PresencePrincipal`, `PresenceCursor`: One client's presence (with the `page` it shows, and the text it edits): principal (id, kind, name, colour, and an agent's relay-stamped `operatorId`), cursor (world units), selection, viewport, `editing`, `updatedAt` (ms). A client publishes presence under its store's Yjs client id (`DocumentStore.clientId`).
- `PresenceEditing`: The text a client edits: `objectId`, and `anchor` and `focus`, UTF-16 offsets into its text (equal for a caret). Transient: never in the document.
- `WriterStampedPresence`, `writerClientIdsOf(state)`: What the relay adds to a remote state: `isNameSigned` (whether `principal.name` is the token's signed name; if not, only the principal id may name the writer, kept only as a boolean) and `writerClientIds`, the Yjs client ids it vouches the client wrote with, relay-owned, never in the local state, kept by presence as at most 16 unsigned 32-bit integers (anything else in the list dropped); and its reader, `[]` for a state no relay stamped.
- `writersOperatedBy(presence, operatorId)`, `OperatedWriterIds`: The Yjs client ids of a user's present agents, each agent with a relay-stamped `principal.operatorId` equal to the user: `vouched`, the writer ids the relay vouches they wrote with (with the agent's id; less any vouched for another present client), proof enough to undo; `unstamped`, the awareness ids of those whose stamp is still empty, a candidate only (their first write arrives before the stamp); and `agents`. What the user's undo history records and undoes (`createHistory`'s `operatedWriters`).
- `PresenceViewport`: A visible region: `x`, `y`, `w`, `h` in world units, `zoom` in screen pixels per world unit.
- `PresenceUpdate`: A change to the local presence: a present field replaces, `null` clears, an absent field keeps.
- `PresenceSnapshot`, `PresenceClientId`: Every remote client's presence, by awareness client id; a new map whenever anything changes.
- `PRINCIPAL_KINDS`, `PrincipalKind`: `user` or `agent`.
- `isPresenceState(value)`, `isPresencePrincipal(value)`: Runtime guards (a `page` must match the id pattern) for remote awareness states and principals. A peer controls its awareness state entirely, so presence bounds and cleans it: a state whose id is over 256 characters is left out like any other the guard refuses; a name has C0 and C1 controls, U+2028, U+2029 and bidi controls stripped and is shortened to 256 characters (at a grapheme boundary where `Intl.Segmenter` exists, else at a code point), so a collaborator stays visible (an empty name is left empty; the app shows their id); a selection keeps its first 1,000 ids and drops any over 64 characters. The local name gets the same treatment instead of throwing; a local id over 256 characters throws `RangeError`.
- `isValidCursor`, `isValidViewport`, `isValidSelection`, `isValidEditing`: Runtime checks: finite cursor, positive-size viewport and zoom, non-empty object ids; an editing claim's object id (the id pattern, at most 64 characters) and integer offsets from 0 to 2^30. A remote claim keeps only those three fields.
- `mergePresence(current, update, updatedAt)`: Merges a `PresenceUpdate` into a state; pure; throws `RangeError` on a malformed field.
- `colourwayForPrincipal(id)`, `PRESENCE_COLOURWAYS`, `PresenceColourway`: The deterministic Ilkal colourway for a principal id (FNV-1a into the six colourways), the same on every client.
- `colorForPrincipal(id)`, `PRESENCE_PALETTE`: The deterministic presence colour for a principal id: its colourway's dark.
- `presenceIntervalMs(rateHz)`, `decideOutbound(state, nowMs, intervalMs)`: The outbound throttle: rate (20–30 Hz) to spacing in ms; a leading-edge send or one trailing flush.
- `DEFAULT_PRESENCE_RATE_HZ`, `MIN_PRESENCE_RATE_HZ`, `MAX_PRESENCE_RATE_HZ`: 25, 20 and 30 Hz.
- `OutboundThrottleState`, `OutboundDecision`: What the throttle knows (last send in ms, pending flush) and what it decides.
- `applyChangedClients(previous, changed, readState, localClientId)`: Inbound coalescing: folds the clients changed since the last flush into a new snapshot; pure.
- `findStaleClients(lastSeenAtMs, nowMs, timeoutMs)`: The remote clients silent for the whole timeout.
- `nextSweepDelayMs(lastSeenAtMs, nowMs, timeoutMs, intervalMs)`: How long until the channel sweeps again: its interval, or sooner when a client turns stale first.
- `computeFollowViewport(target, screen)`, `followClient(snapshot, clientId, screen)`: "Follow": the local viewport that shows a collaborator's region, centred and fitted; pure math, no camera.
- `nextFollow`, `IDLE_FOLLOW`, `FollowState`, `FollowEvent`, `FollowContext`, `FollowOutcome`, `FollowNotice`, `FollowCause`, `FollowStopReason`: the follow and spotlight state machine: choosing, stopping (Esc, camera input, Stop), a spotlight taking over and its opt-out, and what the app moves the camera to and announces.

- `PresenceClock`, `PresenceScheduler`, `PresenceTimer`: Injected time: `now()` in ms; `schedule(callback, delayMs)` returning a cancellable timer.

From the repo root: `pnpm test` runs every package; `pnpm vitest --project @canvas/collab` watches this one; `pnpm bench` includes `src/presence/presence-channel.bench.ts` (fifty clients at 25 Hz: one tick applied and coalesced, and the coalescing alone).

The client's unit tests (`src/client/collab-client*.test.ts`) run against `src/client/__fixtures__/fake-relay.ts`, which speaks the relay's protocol in process, counts every byte clients send, and delivers nothing until the test pumps it, on the frozen clock and manual scheduler of `src/presence/__fixtures__/manual-time.ts`; it can refuse chosen tokens (`refusedTokens`), close every connection before answering its token as a relay whose board failed to load does (`loadFailure`), and records every token it receives. `collab-client-token.test.ts` covers the token provider: a fresh token per reconnection, a token that expires between connects, one retry after a refusal (by message or by close code), the backoff after it when a relay accepts each token and then closes with 4401 (`closeAfterAuth`), a refresh that returns the refused token staying `unauthorized`, a provider failure retried with backoff, a token for another board, a token that arrives after `destroy()`, and the `isAfterRefusal` the provider is told (true after a 4403 `access-changed` while still `connecting`, false once a token was accepted). A provider's answer is a promise, so those tests `await harness.settle()`. The cache implementations share one contract suite (`src/cache/__fixtures__/document-cache-contract.ts`); the IndexedDB one runs it on `fake-indexeddb`. `pnpm bench` includes:

- `src/cache/indexeddb-cache.bench.ts`: restoring a cached 10k-object board (snapshot plus 200 updates) into a new store. On an M-series Mac this took about 410 ms in the per-field layout of when the bench ran alone (about 600 ms when other benches compete); in the grouped layout of it takes 280–410 ms (mean 313 ms). That meets the mobile first-paint budget (< 500 ms at 10k objects) but not the desktop one at 50k, where the store's load is 2.6–3.3 s; nearly all of it is the store applying the snapshot.
- `src/cache/compaction.bench.ts`: a compaction at 10k and 50k objects. `encodeState` (the idle-time task) takes about 58 ms and 300 ms in the grouped layout of (79 ms and 420–1,500 ms, garbage collection included, in the per-field layout before it); storing the snapshot and deleting the log in fake-indexeddb takes about 4 ms and 10–25 ms.

The client against the real relay is tested in `tooling/e2e-sync` (collab may not import the relay). Randomised partitions, delays, reordering, dropped connections and relay restarts across many clients are the sync fuzz harness's ([`tooling/sync-fuzz`](../../tooling/sync-fuzz/README.md)).

`src/presence/presence-channel.test.ts` connects awareness instances in process through `__fixtures__/awareness-link.ts` (encoded awareness updates, no network), on the frozen clock and manual scheduler of `__fixtures__/manual-time.ts`. The presence round trip through the real relay is in `tooling/e2e-sync/src/sync/relay-restart.test.ts`.

## Design notes

Runs in the browser (DOM lib). No React.

### Sync client

- **The relay's protocol over the store, not over a `Y.Doc`.** `@hocuspocus/provider` (and y-websocket) need the `Y.Doc` itself, which `DocumentStore` keeps private (everything above the store works with opaque update bytes). A mirror `Y.Doc` would double the board's memory and apply every update twice, and would run Yjs's formatting clean-up twice with two client ids. The provider's reconnection also runs on its own timers (`@lifeomic/attempt`, `setInterval`), which cannot take the injected scheduler. So `client/relay-protocol.ts` speaks Hocuspocus 4's framing (document name, message type) around y-protocols' sync and awareness messages, the way the provider's `MessageReceiver` does, and `client/relay-connection.ts` runs the handshake with the store's `encodeStateVector`, `encodeSyncState(stateVector)` and `applyUpdate`. `tooling/e2e-sync` holds it to the real relay and to a stock provider on the same board.
- **The handshake is the resync.** On every connection the client sends only its token first. After the relay accepts it, the client sends its state vector and current awareness state; the smaller pre-authentication frame cap therefore never applies to board sync. The relay answers with its own state vector and what the client lacks; the client answers with what the relay lacks. Only missing updates travel in either direction; the unit and end-to-end tests count the bytes.
- **Offline edits.** The store accepts local transactions in every state. `OutboundQueue` counts local updates the relay has not acknowledged (`pendingUpdateCount`): an update made before the handshake's step 2 is held and travels inside it, in the causal order Yjs keeps; later updates travel live, one message each (a larger one in chunks, below), acknowledged in order by the relay's sync status. When a connection drops, unacknowledged updates count as held again; the next step 2 carries whatever the relay lacks, including integrated edits lost in flight. Unresolved cached structs stay in full persistence snapshots and are excluded from the handshake until their dependencies arrive; pending delete sets still travel. Acknowledgements do not certify unresolved cached bytes as saved remotely.
- **Outbound chunks.** The unit of sending is the transaction: a peer applies each message on its own, and its reference repair acts on whatever it sees, so a message never carries part of a transaction except in the cases listed last. A sync step 2 within `OUTBOUND_CHUNK_BYTES` (1 MiB) goes as one message. A larger one (a reconnect after offline work on a large board) goes as several step 2 messages that replay the unsent transactions whole and in order (`planStoredReplay`): each cut to what the relay lacks, merged with its neighbours up to 1 MiB, every cut between two transactions; a single transaction larger than 1 MiB goes whole, alone, up to `SINGLE_TRANSACTION_BYTES` (7 MiB, under the relay's 8 MiB cap), live or replayed. The replay's source is, first, the queue's own copy of this session's unacknowledged updates (`OutboundQueue` keeps their bytes until the relay acknowledges them, at the memory cost of the unsent edits; not on a read-only connection, whose updates the relay never applies); after a reload, the cache's log (`DocumentCache.readUpdates`, read without marking records seen), which covers the unsent work because the client holds compactions (`DocumentCacheBinding.holdCompactionWhile`) until it is connected with its step 2 sent and every message acknowledged, or the connection is read-only (a viewer's refused write must not stop compaction for good): a record the relay lacks is never folded into the snapshot, and the log grows meanwhile (a due compaction runs once released). The app's local board holds compactions too when it is the fallback of a configured relay (`createLocalBoardConnection({ shouldHoldCompaction })`). The store's delete set and anything written while the log was read follow last; local updates are held during the read. The command layer writes pastes, imports and deletes of more than 1,000 objects in transactions of at most 1,000, one undo step whose undo and redo also run one part per transaction, so typical large edits and their undo stay under 1 MiB a transaction. **What is still cut by struct ranges** (`splitUpdate`, ordered by Yjs dependencies, each writer's stamp before its objects, then the delete set; `UnsentChangesSplitWarning` goes to `onError` once per client): a single transaction above 7 MiB (live or replayed), and a step 2 larger than 1 MiB that no replay covers: a cache an older build compacted while it held unsent work, an unreadable log, or a cache without `readUpdates` (also a relay that lost data it had acknowledged); and unsent edits whose bytes were dropped on a read-only connection and whose log records were compacted meanwhile, which a later promotion to editor sends by struct ranges. Such a cut can show peers part of a transaction until the next chunk arrives (a whole backoff when the connection drops between chunks), and an editor peer's reference repair then rewrites references whose targets are still in flight, for good (a child re-rooted, a connector deleted, a comment unpinned); across transactions this cannot happen for the command layer's own parts: `createObjects` writes referents before referrers in every transaction, and a large delete's undo re-creates its parts referents first. Inside one transaction above 7 MiB it can: a cut follows Yjs's order within that transaction (a large delete's undo part re-creates its objects in the order they were first created, by author, not referents first), so any transaction above 7 MiB (1,000 heavy objects, such as hand-drawn paths with hundreds of points) can leave an editor peer a dangling reference until the next chunk. **Pacing:** at most `MAX_UNACKNOWLEDGED_BYTES` (4 MiB) of step 2 chunks and live updates are unacknowledged on a connection, or one larger message (a transaction of up to 7 MiB) alone (`ChunkWindow`); the next goes when the relay's sync status for an earlier one arrives (the acknowledgement Hocuspocus sends for every step 2 and update it handles, the one its provider counts unsynced changes by), with no timer. Each message is acknowledged separately; a step 2's held updates count as sent with its last message. **Too large to sync:** sync and awareness wait for token acceptance, so a large state vector does not hit the 64 KiB pre-authentication cap. A close 1009 before acceptance retries with backoff; after acceptance, a relay close 1009 (a frame past its 8 MiB limit) can come from one struct too large to split (more than 8 MiB of text in one piece); resending it would be refused forever, so the client stops in `outdated` with `rejectionReason` `update-too-large` (`UPDATE_TOO_LARGE_REASON`), the change stays on the device, and the app's connection chip says the change is too large to sync. The replay reads only this writer layout's cache (the one bound to the store); the layout carry-over reads the earlier layouts' and appends to this one, through the store, so the two never touch the same records. Tested in `client/collab-client-chunking.test.ts` (memory and log replays, 600 offline transactions across a reload, the legacy fixture), `client/collab-client-pacing.test.ts` (the byte window, a whole 1.4 MiB transaction, a cut 7.6 MiB one, a 9 MiB struct), `client/collab-client-read-only-hold.test.ts`, `client/collab-client-large-undo.test.ts` (a two-author delete of 2,200 objects in three parts and its undo, then an undo, redo, undo round trip, applied message by message by an editor peer), `chunking/*.test.ts`, and against the real relay in the sync fuzz (`tooling/sync-fuzz/src/run/large-offline-batch.test.ts`).
- **Tokens.** The client takes a token provider, `getToken(): Promise<string>`, and asks it for a token on every connection attempt, so a user who comes back after the token expired reconnects with a fresh one and the pending edits go out. A fixed `token` is still accepted (wrapped; it is handed out in the same task, so a connection with it opens as before) but cannot be refreshed. `createCollabClient` awaits the first token (its claims are the client's identity) and rejects if the provider does. A provider that rejects later counts as a failed attempt: reported to `onError`, retried with backoff; the idle timeout covers one that never answers. A refused token (`permission-denied`, or the close codes 4401 and 4403) is retried once, at once, with a fresh token (on the first connection within the same attempt, so the state goes from `connecting` straight to `connected` or `unauthorized`); if the provider returns the same token, or the fresh one is refused too, the client ends `unauthorized`. Every request for a token tells the provider `{ isAfterRefusal }`, true from a refusal until a token is accepted, whatever the state was when the relay refused: a provider that keeps tokens (the site's) asks its backend afresh then, instead of relying on seeing the state leave `connected`, which a 4403 during `connecting` never does. The allowance comes back once a token is accepted, but only the first such retry since the last sync is immediate: a relay that accepts every fresh token and then closes with 4401 or 4403 would otherwise be asked again at once, forever, so later refusals are retried with the normal backoff (`reconnecting`). Every token must open the client's board; one that does not ends it `unauthorized` (`wrong-board` or `malformed`). `ConnectionTokens` holds this, `RelayLink` runs the attempts.
- **Refresh on the open connection**. A relay that can refresh tokens tells each connection, once it joins, how long its token has left by the relay's clock (a stateless `token-expiry` message); an older relay says nothing, and the client then never refreshes. `TokenRefresher` (`client/token-refresher.ts`, one per connection) asks the provider with `{ isRefresh: true }` at about 75 to 80% of that lifetime (a lead of the larger of 60 s and 20%, up to 30 s of jitter from the injected random source, at least 5 s away), sends the new token as a stateless `token-refresh`, and on the relay's `token-refreshed` makes it the connection's token and schedules the next one, at least 30 s later (the relay accepts one refresh per 30 s per connection): the connection, its presence and its sync stay as they are, with no reconnect and no resync. Only a token for this board that differs from the current one and expires later is sent (`ConnectionTokens.refresh`); a stale token (a fixed `token`, a provider that ignores `isRefresh`) or a provider failure is retried once while more than 30 s remain, then the client waits. At most one refresh is unanswered. A token announced with under 15 s left is not refreshed, and nothing is sent within 5 s of expiry, so a timer that fires late (a sleeping or throttled tab) sends nothing. Whatever goes wrong, the relay's close is handled as before: a refused refresh closes 4401 `token-refresh-refused` or 4403 `access-changed` (one fresh token, the refusal held against the token sent), a flood 1008 (backoff), and a connection whose token was never refreshed is closed 4401 `token-expired` at expiry. Going offline, `disconnect()` and `destroy()` cancel a pending refresh with the connection. The client answers the relay's stateless keepalive (`{ "type": "keepalive" }`, every 15 s) at once with the same, so a quiet connection in a background tab, whose timers run once a minute, is not closed by the relay's 60 s timeout or the client's own 30 s idle check before its token is refreshed (`client/collab-client-token-refresh.test.ts`; the real site in `tooling/scenario/specs/site/token-refresh.spec.ts`). Tested in `client/token-refresher.test.ts`, `client/connection-tokens.test.ts`, `client/relay-protocol.test.ts` and `client/collab-client-token-refresh.test.ts` (the fake relay's `announcedExpiryMs` and `refreshPolicy`); against the real relay in `tooling/e2e-sync/src/sync/token-refresh-relay.test.ts`.
- **States.** `connecting` (first attempt), `connected` (the relay's step 2 has arrived), `reconnecting` (a failed attempt, a dropped connection, or a refused token being refreshed; retried), `offline` (the network is down or the app called `disconnect()`; nothing is attempted), `unauthorized` (terminal: sign the user in again and create a new client) and `outdated` (terminal: this build cannot read the board; reload the app; see "Layout version gate" below). A `permission-denied` answer and the WebSocket close codes 4401 (Unauthorized) and 4403 (Forbidden) end here once the refresh above did not help. A close with 1013 (Try Again Later; the relay's `storage-unavailable`, sent when a board's load failed, the database briefly down) is never a refusal: the client goes `reconnecting` and retries with the ordinary backoff, without spending the immediate token refresh, and a relay whose storage stays down is retried at growing delays up to the cap (tested in `client/collab-client-storage-unavailable.test.ts`; against the real relay in `tooling/e2e-sync/src/sync/storage-unavailable-relay.test.ts`). The offline cache is not cleared on `unauthorized`: whether a refused user's copy of a board stays on the device is the app's policy (`DocumentCache.delete`). `lastSyncedAt` moves when the first sync completes and whenever every local update has been acknowledged while connected. A read-only connection (viewer, commenter) reports `isReadOnly`; its edits stay pending, since the relay refuses them.
- **Reconnection.** Exponential backoff (250 ms doubling to 10 s) shortened by up to half by jitter, on the injected scheduler and random source; reset once a connection has proved itself: for a writer, when the relay's step 2 has arrived and the relay has acknowledged every chunk of the client's own first step 2 (in either order; a writer with nothing to send still sends an empty one), for a read-only client when the relay's step 2 has arrived. The one immediate retry with a fresh token is allowed again from the same point. A client whose update the relay refuses on every connection therefore keeps backing off instead of reconnecting at the base delay. Every close that is not a refusal or terminal is retried this way, among them 1012 (a relay restarting), 1013 `storage-unavailable` (a board that could not load) and 4425. A connection silent for 30 s (the relay echoes each client's awareness renewal, at most 18 s apart) is dropped and retried. `online` connects at once, skipping the backoff. Node's WebSocket reports a refused connection with an `error` and no `close`, so the transport ends a socket on whichever comes first.
- **Layout version gate.** Every connection declares the stored layouts the client's store reads, as the URL's `layouts` query parameter (`READABLE_LAYOUT_VERSIONS` of `@canvas/document` unless `readableLayoutVersions` says otherwise; `withReadableLayouts` in `client/relay-close.ts` replaces any `layouts` the URL already has). It is a query parameter, not a token claim, because it describes the build, not the user: the backend that signs tokens does not know which build will present them, and the token stays as it was. The relay refuses a client that cannot read the board before sending any of it, closing the socket with 4426 (`LAYOUT_GATE_CLOSE_CODE`) and `unreadable-layout`; it closes a client with `unstamped-write` when its update would give objects to a writer that never stamped, and with `invalid-stamp` for a malformed or lowering stamp. The relay also closes a connected client with 4426 `unreadable-layout` mid-session, when another client raises the board's layout above what this one declared; that close is handled exactly like the one at connect time, and whatever this client sent that the relay had not yet acknowledged was refused with it, so it stays pending. The client then ends `outdated`, with the reason in `rejectionReason`, and never reconnects: `disconnect()`, `connect()` and the network coming back leave it there. A permission-denied answer carrying one of the gate's reasons ends there too, rather than being refreshed as a bad token. A `DocumentVersionError` thrown while applying the relay's data (alone, or inside an `AggregateError` with a listener's error) is not reported to `onError` and does not drop the connection for a retry, which an early review found looping forever: it ends the client `outdated`, with the error's `problem` (`unversioned`, `unreadable-version`) as the reason. An update the relay cannot prove safe yet (4425 `incomplete-update`, `INCOMPLETE_UPDATE_CLOSE_CODE`: a writer's earlier message lost, typically) is not applied and closes the connection; the client treats that as any lost connection and reconnects with backoff, and its next sync carries what the update lacked. The backoff resets only after inbound sync and positive acknowledgements for every initial outbound step-2 chunk (read-only connections need only inbound sync); receiving the relay's step 2 alone cannot reset repeated 4425 refusals. Local edits made before or after an `outdated` end stay in the store and the cache, counted in `pendingUpdateCount`, and are never sent by that terminal client. Reloading creates a new client; the default IndexedDB cache isolates writer layouts as described below (tested in `client/collab-client-outdated.test.ts`; against the real relay in `tooling/e2e-sync/src/sync/layout-gate-relay.test.ts`).
- **Identity.** The token is decoded, not verified (the relay verifies); its `boardId` must match the client's, and presence takes its principal id and kind from `sub` and `principal`, so collaborators see the identity the relay attributes edits to. The relay does not yet check awareness states against the connection's token; that belongs to relay hardening.
- **Remote updates** are applied with `SYSTEM_ORIGIN` (the store's `isLocal: false`); per-update attribution lives in the relay's log. Updates the client applies from the relay are never sent back; anything else the store emits is, including Yjs's formatting clean-up after a remote change.

### Offline cache

- **Update bytes, not the document.** The cache stores the store's updates (from `subscribeUpdates`), local and remote, and restores with `applyUpdate`, so it needs no access to the `Y.Doc` (y-indexeddb would). What a restore applies is not stored again; what the store writes in response is (its reference repair of a board cached with a dangling reference, or Yjs's formatting clean-up), so the next load from the cache finds the repair there instead of repairing again from an empty memory. Two object stores: `snapshots` (one per board) and `updates` (the log, `seq` auto-incremented, indexed by board, so tabs never collide).
- **First paint.** `createCollabClient` awaits the cache before it opens a socket, so the app can paint the cached board while the network answers. The snapshot and the updates after it are applied as two transactions: merging the updates into a large snapshot first costs more than it saves: at 10k objects the restore averages about 675 ms merged and about 410 ms applied apart, which still misses the budget (see How to test).
- **Compaction** is due every 500 stored updates, local or relayed, and runs from an injected idle scheduler (`requestIdleCallback` with a 10 s timeout by default). In one task it encodes the store's state and asks the cache to store it. The cache's transaction only writes the snapshot and deletes the updates this connection appended or loaded, which are exactly the ones the snapshot covers: requests are transactions created when they are made, so IndexedDB runs them in order. Updates other tabs stored stay in the log. If another tab stored a newer snapshot first, nothing is written; the binding loads the board into the store and compacts again.
- **The long task remains.** Idle scheduling keeps compaction out of busy frames, but `encodeState` is one synchronous task of about 58 ms at 10k objects and 300 ms at 50k (the grouped layout of cut it from 79 ms and 420 ms or more). Input that arrives during it waits. Taking it off the main thread entirely means merging the cached bytes (the snapshot and the log, which already hold the whole board) in a worker; that needs a worker entry point this package does not have yet.
- **Failures** (quota, a blocked database, a closed connection) go to `onError` and never stop editing: the relay holds the board. A cache that cannot be read is skipped and the client connects without it.
- **One copy per board and writer layout on the device.** Everything that caches a board uses the namespace `DEFAULT_CACHE_DATABASE_NAME` (`canvas-board-cache`) with a physical database suffix `:layout:<DOCUMENT_LAYOUT_VERSION>:recovery:1` (currently `canvas-board-cache:layout:2:recovery:1`) and the board id as the key, whether a collab client binds it or an app binds its own store with `DocumentCacheBinding` (the app's local board when no relay answers does). So a board edited without the relay and opened later with it is restored from the cache before the first sync and its offline edits go to the relay in step 2. When the relay's board changed meanwhile too, the two merge like any two Yjs replicas: edits to different objects and fields all survive; concurrent writes to the same field of the same object resolve by Yjs's rule (the higher client id wins), not by wall-clock time.
- **Keyed by board only (shared devices).** The cache key is the board id, not the principal. On a shared browser profile, edits one guest made offline are restored into the next person's store for that board and sent to the relay over that person's connection: a deliberate decision while identities are per-tab guests, which must change when sign-in exists (a cache keyed by board and principal, or offline edits held until the same principal returns).
- **Durability.** The binding requests one append per update, synchronously, with no batching (compaction only rewrites what is already stored), so a reload never loses an edit; a tab killed while an append's transaction is still in flight can lose its last edit.

### Cache layout isolation

`openIndexedDbCache` appends the writer-layout suffix to default and custom database namespaces. The namespace depends on what the build writes, not the layouts it can read: a current build can read layout 1 from the relay without replaying an old build's whole-pair line edits into split layout-2 fields. The IndexedDB object-store schema remains version 1; this does not change the stored document layout.

On the layout-2 database's first successful creation, a readonly snapshot of its unsuffixed predecessor is copied atomically with schema creation. Snapshot versions, update keys and bytes are retained unchanged, including pending fragments and valid unstamped offline boards; nothing is compacted or re-encoded. A positive retained layout-1 stamp excludes that board, even if a later stamp superseded it. Already garbage-collected stamp content cannot be recovered. A board whose bytes cannot be read (malformed, or nested past the bound) is left out of the copy, stays only in the unsuffixed database, and is reported to the cache's `onError`; the other boards are copied (from the re-review: one such record used to refuse the cache open on every load, leaving the device without an offline cache for any board). Concurrent opens serialize through the destination's versionchange transaction, and an existing destination is never recopied or overwritten.

The legacy database is never written or upgraded, and a board is deleted from it only when the person dismisses it, or when `deleteIndexedDbBoards` picks its key (the site's sign-out, below). Skipped boards (a layout-1 stamp, or bytes the copy could not read) stay only there and are never converted or sent; the layout carry-over below reads them as layout 1 and tells the person, keeping each until dismissed. The copy is made by the layout-2 cache, or, when no layout-2 cache exists, by the first cache of a later layout (layout 2 bytes are valid layout 3 writes, so a person going from a pre- build straight to a layout-3 build loses no unsent edit); later bumps are handled by the carry-over. Writes to the old database after the copy are not imported. A same-layout reload restores the current cache normally. Embedders providing a custom `DocumentCache` must isolate persisted storage by writer layout too.

### Layout carry-over

A writer-layout-isolated cache never restores what an earlier layout's build cached, so without help every layout bump would silently orphan whatever the relay lacks: edits made offline on the old build, a board that only ever lived on the device. `LayoutCarryOver` closes that gap, once per open (no timer, no polling:'s caps are untouched).

- **Detection.** The IndexedDB cache's `earlierLayouts` reads, first, the unsuffixed pre- database (for a writer layout from 2 up), taking a board only when's copy left it behind (`classifyLegacyBoard`: a layout-1 stamp, or bytes it could not read; a copied board is not reported again), as layout 1; then `<namespace>:layout:<n>` for every `n` from 1 below the writer layout. It opens only databases that exist (an absent one is not created), reads the board's snapshot and log with their record keys and snapshot version, and closes the database again. A delete removes only the records that were read, and the snapshot only while its version is the one read, so an old build's tab still open across the update and writing between the read and the delete loses nothing: its records stay for the next open.
- **What the relay lacks** is computed client-side from the synced store, not with a new relay message (the relay is unchanged): the collab client starts the pass when its state first becomes `connected`, that is once the relay's sync step 2 is in the store, so the store holds everything the relay has plus what the current cache added (which the handshake sends anyway). `findUnsentChanges` encodes the store's state vector and, with `encodeState` against that same vector (only its delete set is read; it includes the store's pending deletions, which its current cache holds), its delete set; a cached record lacks something when its diff against the vector still has a struct, or carries a deletion the store has not made. Deletions matter: deleting writes no new struct, so a state-vector comparison alone would call an offline deletion sent. The count of unsent changes is the number of cached records (the snapshot, each logged update) that lack something: a logged update is one transaction, and a compacted snapshot counts once.
- **Nothing lacking**: the earlier copy of the board is deleted and nothing is said (a pre- copy is left where it is).
- **Something lacking, a converter for the bump** (`DEFAULT_LAYOUT_CONVERTERS`, keyed `from->to`; a missing whole-bump key is chained from single steps): the unsent edits are converted, applied to the store with `SYSTEM_ORIGIN` (the client sends them), appended to the current cache by `storeDurably` and awaited, and only then is the earlier copy deleted. The direct append matters: the store's update event leaves out content the store holds pending (structs whose dependencies are missing, deletions of items it lacks), so the cache binding alone would not store it, and a failed append (a full quota) is not hidden: the copy is kept and reported. A pre- copy never gets a converter, the identity `1->2` included: its layout-1 stamp would be refused by the relay as `invalid-stamp`, and its whole-pair line edits would replay into split fields. The `1->2` converter is the identity, by our decision: layout 2 only split a line's `points` pair, the store still reads layout 1, and's copy already treats layout-1 bytes as layout-2 bytes. No build ever wrote a `…:layout:1` database (the suffix arrived with layout 2), so in practice it carries nothing; it is there so the mechanism is exercised end to end. The `2->3` converter is the identity too: layout 3 only lets a fill be a gradient and a stroke or text colour be `'ink'`, so a layout-2 build's unsent edits are valid layout-3 writes and its read-only tab's edits are sent after the reload. The `3->4` converter is the identity as well: a layout-3 build's unsent edits write placements without `pageId`, which layout 4 reads on `page-1`, and if `page-1` is gone by then the repair moves them to the first page (R1). The `4->5` converter is also identity: ordinary layout-4 content keeps its meaning, and absent constraints remain absent with effective start/start defaults. The `5->6` converter is the identity as well: layout 6 only lets an override record hold `textStyle` and `runs`, so every record a layout-5 build wrote means the same. The `6->7` converter is the identity too: layout 7 only lets a shape's fill or a frame's background be an image paint, so every paint a layout-6 build wrote means the same. The `7->8` converter is the identity as well: layout 8 only adds optional auto-layout fields to existing groups and override records. The `8->9` converter is the identity as well: layout 9 adds the colour tokens map and lets a colour name a token, so a layout-8 build's unsent edits are valid layout-9 writes.
- **Something lacking, no converter** (or a pre- copy, a read-only connection, whose edits the relay refuses, a copy whose bytes cannot be read, or carried edits the store or the current cache refused): the earlier copy is kept and reported in `stranded` (`StrandedEdits`: board, source, layouts, count) until the person dismisses it; `dismiss(source)` deletes the records of that copy the pass read, and nothing else. The app shows it beside its connection chip.
- **Not covered here.** Unresolved fragments carried into the store stay pending there and are stored in the current cache by the direct append; in an earlier copy they count as unsent on every open until carried or dismissed. Two tabs opening the board at once may both carry the same edits: the identity converter's are the same Yjs items, so they merge; a future converter that writes new items would write them twice (the same values, last writer wins).

### Deleting boards from the device

`deleteIndexedDbBoards({ isDeleted })` removes boards by their stored key from every database the cache and its carry-over could read: the unsuffixed pre- database, `<namespace>:layout:<n>` for every `n` up to the writer layout, and any later layout's database `indexedDB.databases()` lists (a newer build that ran before a rollback; where the browser cannot list databases, only the layouts up to the writer's are read). It only deletes records, never databases, so other keys (another person's boards, the playground's) and other tabs' open connections are untouched, and a database that does not exist is not created. Each database changes in one readwrite transaction, which IndexedDB runs after every transaction already requested on it; what a connection writes after it is not deleted, so the caller first stops every writer of those boards (the site closes the person's boards in every tab under a lock, `packages/app` README, "Signing out"). Tested in `cache/indexeddb-board-purge.test.ts` (two people in every layout's database, the unsuffixed one and a later one; no database created; no listing; a write requested first; a refusal).

### Presence

- **Never persisted.** Presence lives only in the Yjs `Awareness` the provider syncs, never in the board's `Y.Doc`, so the relay's update log and snapshots never see it. A test checks that `Y.encodeStateAsUpdate` of the document is byte-identical before and after presence traffic.
- **Outbound at 20–30 Hz.** `setLocal` merges into the local state; a leading-edge throttle writes it to awareness when the last write is an interval old (40 ms at the default 25 Hz), otherwise one trailing flush at the interval's end writes whatever the state is by then. So a 60 Hz pointer stream costs at most `rateHz` messages a second, and a stopped pointer's last position always goes out. The channel is the local state's only writer; the provider sends each awareness update as it already does.
- **Inbound coalesced.** Awareness `change` events mark clients dirty; one flush (the scheduler's delay 0, or a frame scheduler the app injects) folds them into a new snapshot and notifies listeners once. `getRemote()` folds pending changes on read, so a render loop can pull instead of subscribing. Remote states that fail `isPresenceState` (a fresh awareness's `{}`, a foreign client) are left out. The renderer interpolates between snapshots; this package does not.
- **Timeout.** A remote client silent for `timeoutMs` is removed with `removeAwarenessStates(…, 'timeout')`. The timeout is 20–30 s (default 30 s) because y-protocols runs its own wall-clock clean-up beside the channel: it removes silent peers after 30 s whatever the channel says (hence the cap), and renews every client's state once it is 15 s old, checked every 3 s, so an idle peer is silent for at most 18 s (hence the 20 s floor, which never drops a connected peer, whatever timeout that peer runs). Use the same value on every client so they agree on when a peer left. The channel also re-sends the local state every half of its own timeout, which keeps tests on the injected clock honest. `destroy()` clears the local state, which tells peers at once; destroying the awareness destroys the channel.
- **Agents** are principals of kind `agent` and appear in presence like people.
- **Colours** are derived from the principal id, so every client agrees without coordination; a principal may bring its own.
- **Time is injected** (`PresenceClock`, `PresenceScheduler`), so tests run on a frozen clock. Awareness keeps its own 30 s wall-clock clean-up as well; the two agree by default.
- Selection ids are plain strings until `@canvas/schema` defines an object id type.
- **Following** (whom a client follows) is not broadcast yet: `TODO`. When it lands it is a principal id, not an awareness client id, which changes on every reconnection.

### Recovering incomplete cached history

Relay handshakes use `encodeSyncState`, leaving incomplete cached structs in the
store and full persistence encoding while sending integrated offline edits and
pending delete sets. This avoids repeated 4425 refusal caused solely by retained
incomplete fragments. It neither resets storage nor changes compaction/CAS rules.
When a relay update releases retained structs, an editor sends the newly integrated
clocks back through the ordinary acknowledged update queue. `client/released-clocks.ts`
compares the post-apply clocks with both the old state and incoming non-Skip ranges;
ordinary peer traffic that releases nothing triggers no recovery encoding or acknowledgement
debt. Unresolved bytes remain excluded. Viewers do not recovery-send.
Dependencies that never arrive remain retained locally; successful sync does not
claim those unresolved fragments reached the relay.

`pendingUpdateCount` counts sendable queued updates, not every cached fragment.
`lastSyncedAt` records handshake/queue progress for integrated history; it does not
certify that every cached byte is saved remotely. The app's chip says `Connected`,
not that unresolved cached fragments have reached the relay. Fragments whose
dependencies never arrive remain locally recoverable in full cache snapshots.

Releases structs held by stale Yjs retry hints after their dependencies were
already delivered. Keeps real gaps out of the handshake and forwards history
released by either normal application or's retry repair. Neither replaces the
other. Seeded cached-start fault cases live in `tooling/sync-fuzz/src/run/pending-cache.test.ts`;
real-gate pending deletion coverage lives in `tooling/e2e-sync/src/sync/pending-delete-relay.test.ts`.

Viewer and commenter token claims select the store's read-only automatic repair mode before
loading cached bytes. Every authoritative authentication response updates that mode, including
role changes on reconnect. Dangling references and parent cycles are projected without local
repair updates, so they do not create an unacknowledgeable pending queue. This does not change
the existing explicit-local-edit policy or treat token claims as server authorization.
`client/collab-client-repairs.test.ts` covers cached/offline startup and role transitions;
`tooling/e2e-sync/src/sync/viewer-repairs-relay.test.ts` verifies headless `whenSynced` against
the real relay with both kinds of persisted repair candidates.

The board-token reader exposes optional signed `name` as `displayName`. Initial presence uses it ahead of the local name option; unnamed legacy/development tokens retain the local-name fallback. Relay stamps and cleans the authoritative signed name on publication.

### Reopening a poisoned device cache

`createCollabClient` stages cached records in a disposable read-only store before touching the
supplied store. A cache-only unversioned refusal opens the supplied fresh store against the
relay instead. A live store that is already refused, genuinely newer layouts, and over-depth
updates keep their existing terminal refusal. Recovery starts automatically after authenticated
sync; an offline open waits. This is a reopen boundary, not an in-place reset of an outdated client.

The optional `DocumentCache.recovery` capability provides `capture`, `publish`, and `retained`.
Publication compares the active generation, snapshot version, and exact update keys in one
transaction. It retains the old snapshot and every tail record, then binds only the publishing
connection to the new generation. Other connections stay bound to their old generation; their
later writes remain retained and stale compactions refuse. IndexedDB uses a separate `:recovery:1` physical database at schema 1.
It copies the previous same-layout database on first creation, leaves old tabs writable there,
and reads their later records on every recovery read. Local-only reopen also carries provable
whole old-format records before seeding a new board. Old source databases are not upgraded or
retired. Memory storage follows the same generation contract. Prefix views forward every key.

`CacheRecovery` checks whole records with the existing strict writer-stamp and document guards,
including complete dependency and deletion integration. It never stamps old writers, splits
mixed records, or changes the stored document layout. The clean candidate is published durably
before safe original records enter the normal update queue. CAS conflicts, quota failures,
disconnection, and destruction preserve source bytes. Viewers retain and export without replay.
`client.recovery.state` reports waiting, recovering, retained, or failed; `exportSources()` returns
original snapshots and updates. A successful connection does not assert every retained record
was recoverable. Custom caches without this capability retain the existing terminal refusal.

Recovery generations are never automatically retired. A later writer-layout carry-over includes
their snapshots, proves each whole converted record in isolation, and refuses to delete that earlier cache, preserving dependency bases for late
old-tab writes. Unprovable whole records may therefore remain on the device indefinitely. The
app provides a recovery-copy download; it is a diagnostic byte export, not an ordinary board
import. The independent poisoned-cache acceptance cases cover fake IndexedDB, real relay and
fuzz separately; generation and lifecycle tests additionally cover atomic abort, competing
publication, stale tabs, old-writer fencing, viewer, quota and post-publication crash/reopen.

Manual recovery publication marks the old generation export-only and durably fences every
previous physical cache format for that board. The fence survives later publication,
compaction and ordinary deletion. Older tabs remain writable; their later records stay
available for manual export and cannot resurrect an explicitly discarded update. A later
layout conservatively treats any source mixing manual archives with active bytes as manual
before conversion or recovery validation. Its persistent stranded notice offers a fresh-byte
download instead of dismissal. No manual archive retirement is implemented.

### Comment notices

`CollabClient.onThreadsChanged(listener)` subscribes to authenticated `threads-changed` stateless
messages for this board and returns an unsubscribe function. Destroy clears the listeners.
Listeners fetch the threads from the boards service; reconnecting applications also fetch to
cover notices missed while offline. Listener failures use the client's existing error handler.
`CollabClient.onVotesChanged(listener)` does the same for the board's dot vote (`votes-changed`,
); the notice carries no votes, and listeners fetch what the reader may see. Both kinds
share `client/board-notices.ts`.

Component repair authority: authenticated human writers materialize deterministic
reference-cycle/depth repairs. Agents are identified by the token's `principalType`, retain
legacy repair behavior, and only project component repairs in their read view; they never
write a foreign main's component repair. Viewer/commenter clients remain read-only.
