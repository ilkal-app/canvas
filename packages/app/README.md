# @canvas/app

Asset record discovery batches up to 50 unique IDs per request, with at most 12 requests in flight and visible assets first. Records, polling, event-stream opens and tile URL reads share a board adapter’s `Retry-After` deadline, retained across token refresh. Capacity waits release active work and do not consume image failure retries. Mutating requests retain their separate budgets.

## Purpose

The React shell around the canvas: dock, top bars, panels, dialogs, shortcuts and theming. The only package besides `tools` and `sdk` that may use React.

Today: a dock floating over the canvas's bottom centre holding the board mode's switcher and that mode's tools (shapes and lines in flyouts, tools not built yet shown disabled, "not available yet"), each with its shortcut hint, a hand tool and Space-drag pan, a zoom control over the canvas's bottom-left corner, the board-name and presence/share bars over its top, a sidebar with the contextual style panel (sections registered per object type, mixed values shown explicitly, one undo step per change), a virtualised layers panel in the layers drawer over the canvas's left side, a notice when an action did nothing or a command was refused, the canvas with the engine drawing a demo document on it (in a dedicated worker where the browser can render there), the camera of `@canvas/tools` wired to wheel, pinch, touch, middle-drag and keys, the select tool on the primary button and one finger (select, move, resize, rotate, marquee; finger-sized handles and bands, a double-tap zooms to the tapped object) with select all, select same type (mod+alt+a), Escape, Delete, arrow nudges, align, distribute and tidy up, the four order shortcuts and lock/unlock on the selection (`src/engine/selection-arrange.ts` runs each as one command, the order commands on the selection's largest same-parent subset) and undo/redo, a context menu on a right-click or a long-press listing the selection and arrangement commands that apply, a shortcut registry holding every navigation, tool, selection, arrangement and history shortcut as a typed action, a cheat sheet on `?`, a developer overlay on mod+shift+d (frame timings, frame rate and GPU memory), light and dark themes, and real collaboration: the playground page opens a board on the relay (`?board=`, `?relay=`), the engine edits the synced store, and the presence/share bar over the canvas shows the connection state and who else is on the board; without a reachable relay it keeps working on a local demo board. The camera, the select tool and history act on the actions; other tools subscribe as they arrive. Images: files dropped on the canvas, pasted, or picked with the image tool (`i`) are placed at their natural aspect (long edge at most 800 world units), drawn at once from their own bytes and uploaded to the assets service (`?assets=`), with a badge on each until its record is ready and Retry and Remove on a failure; a double-click, Enter or the image section's Crop button crops an image; the Layer section sets its opacity, as every layer's; an image copied from another board is linked to this one before it is pasted.

## Public API

The engine document accepts an optional whole-board `definitions` store alongside its page
view. Its scene feed expands component instances before enqueueing both main-thread and worker
renderers; off-page main changes update shown instances. Retained mains and their descendants
are hidden from rendering and hit testing. Virtual content is never written to the document.

- `prepareCachedProjection`, `PendingCachedProjection` (internal): validates cached board/viewport data before font loading; `accept` exposes it only after the current font identity matches. Fresh renderer proof is still required before display.
- `restoreCachedFontSet` (internal): loads known catalogue families in the saved fallback order and checks their complete current byte identity; never fetches a URL from cache data.

- **A section** is `{ id, title, context, order, render }`. `context` is one `SelectionContext` or several; `render` is mounted as a component (hooks are fine) with `{ context, selection, board, defaults, dispatch, applyStyle }`: the selected objects as stored (primary first), the document for reads, the active creation tool's style when nothing is selected, the shell's dispatch, and `applyStyle(patch, isInkPick?)`, which sets only the given fields (`isInkPick`: the colour a tool creates with was just picked as Ink, `true`, or as a fixed colour, `false`), on the selected objects whose type takes them (`styleChangesFor`) as one `style` canvas action (one `setStyle` command, one undo step), or on the creation tool's style (`setToolStyle`) when nothing is selected. Build controls from `src/panels/controls/` so mixed values look the same everywhere.
- **Arrangement, order and lock** stay `ShellAction`s (`arrange`, `selection`/`toggleLock` on the selection, `toggleLockOf` on given ids): the panel's arrange row, the context menu and the shortcuts dispatch the same actions, and only the engine's document side runs their commands.
- **A creation tool reads its style** from the document side when it creates an object: `EngineDocument.panels.toolStyle(tool)` (a `StylePatch`: its registered defaults with the person's choices over them). The shell hands every tool's resolved style to the engine as it hands it the active tool (`MountedEngine.setToolStyle`, from `useShellEngine`), so a tool mode never reads shell state.
- **Fill and Stroke have one home:** the `fill-stroke` section (contexts `shape`, `vector` and `frame`). Vectors and shapes extend it, and lines add `line` to its context and its fields there; none adds a second fill or stroke control. Frames show their stroke there (colour or none, width) but no Fill, since a frame's fill is its background, the frame section's, so for frames the section is headed "Stroke" (`titleFor`, an optional per-context heading of `StylePanelSection`). **Align**: for selected shapes and frames with a stroke, a list of Inside, Center and Outside (`strokeAlign`, absent shown as Inside, "Mixed" when they differ) sets the alignment alone, on the selected objects with a stroke only, one `setStyle`; it is not offered for paths or a creation tool's style. In Chrome: `tooling/scenario/specs/app/stroke-align.spec.ts`. The frame section's `Corner radius` sets one radius for every corner (Mixed when the frames, or a frame's corners, differ), and its `Independent corners` toggle shows each corner's own field.
- **Layer**: the `layer` section (`panels/sections/layer-section.tsx`, every selection context including `mixed`, order 5.5: after a type's own section of order 5, before colour mode and auto-layout (6) and fill and stroke (7); selection only), shown for any selection holding an object with an opacity. "Opacity" is a 0–100% slider and a percent field, "Mixed" when they differ; each commit is one `setStyle` of `opacity` over every selected object with one, 100% removing a layer's (absent is opaque) and giving an image its required 1. An instance's override rows offer it too (`override-opacity-field.tsx`).
- **Effects**: the `effects` section (`panels/sections/effects-section.tsx`, contexts `shape` and `frame`, order 50: after the frame (5), auto-layout (6) and fill and stroke (7) sections, before layout and arrange; selection only). A "Drop shadow" toggle turns on Figma's default shadow (`DEFAULT_SHADOW`) on each selected shape or frame without one, or writes `null`; while any has one, its X, Y, blur and spread (world px), colour (each keeps its own opacity) and opacity. Each change is one `setStyle`; differing values show "Mixed".

Signing in: the app never handles a credential. Sign in sends the whole page to `/api/auth/sign-in?return=<the current path>` (a path on this origin, else `/`); the service sends the browser to the identity provider and back to that path with the session cookie, which scripts cannot read and the app never sends or reads itself.

Secrets: an invitation's or a link's secret travels in the address's fragment (`/invite#<secret>`, `/join#<secret>`), which the browser never sends to a server, so it reaches no web server or request log and no `Referer`; the old form with the secret in the path is not found. The site takes it out as soon as the page loads (`history.replaceState` to `/invite` or `/join`), before the page asks anything, keeps it in memory and in the tab's session storage (for the round trip through signing in), and sends it only when the person clicks Accept the invitation or Join the board, in the body of `POST /api/invitations/accept` or `/api/links/join`, once however often they click. It is never logged, shown or put in the tab's title. A signed-out person signs in with the clean address as the return path, so the secret does not ride in the sign-in's `state`, which the service passes through the identity provider in a URL; back in the same tab, the page finds it in session storage and still waits for the click. `index.html` sets `<meta name="referrer" content="same-origin">` (not `no-referrer`, which would send `Origin: null` and fail the service's origin check), so no address is sent to another origin.

Opening a board: `GET /api/boards/:id`, then the connection (`openSiteBoard`) with a token provider over `POST /api/boards/:id/token` (`createApiTokenProvider`: kept 8 of its 10 minutes, one request at a time; a refresh of the open connection, about 8 minutes in, asks for a new one, so the connection stays open while the person keeps their role), the person's name for presence, and the device's cache kept per person (deleted when they sign out on this device: [Signing out](#signing-out)). When the relay closes the connection (its 4403 `access-changed` when the owner removes the person or changes their role), the provider forgets its token (`followBoardAccess`), so the collab client's retry carries one signed anew: the new role, or a refusal (`404`), which closes the canvas, says "You no longer have access to this board" with the way home, and stops: the provider answers every later attempt with the same refusal without asking the service. Move to trash holds the board's token requests until the service answers (`useSiteBoard`'s `holdTokensWhile`): the service closes the board on the relay as soon as the deletion commits, so a token asked for meanwhile would be refused; once the deletion went through the page lets the board go without asking, and after a failed one the requests go on. A new board starts empty; the demo board is the playground's.

### Signing out

Signing out on a device deletes what that device keeps of the person (item 4), so the next person at the same browser cannot read their boards with the browser's tools. What is kept per person: the boards' cache (IndexedDB; every key is `user:<id>/board:<id>`, the user id percent-encoded so it holds no `/` and no person's prefix starts another's keys (a UUID is unchanged, so existing caches keep their keys), `scopeBoardCache`) in the current writer layout's database `canvas-board-cache:layout:<n>`, in earlier layouts' databases the carry-over reads, and possibly in the unsuffixed pre- one; the record of their boards with unsent edits (`canvas.unsent-boards.<user id>` in `localStorage`); and, not keyed by person, the copied images (`canvas.copied-assets`) and the view-only notices shown in a tab (`sessionStorage`). No board token or role is stored on the device (tokens live in the page's memory), and dismissing stranded edits deletes that copy rather than recording anything.

The order (`useSignOut`, `PersonDeviceData.forget`):

1. With boards holding unsent edits (`UnsentBoards`: marked by a connection at its first pending edit, in flight included (one write per burst; a tab that crashes leaves the mark), or when it is let go with edits pending, for stranded edits, and at each of the person's edits on a local board; cleared only by a connection whose device cache is open, which the relay has acknowledged everything of (`isAcknowledged`, which `connected` alone is not: edits restored from the device travel in its step 2 and are never pending), with nothing pending, after 2 s without an edit, whose store covers the board's cache log, the one place every tab's unsent edits are; a viewer has none), the site asks first (`SignOutDialog`): how many boards, and that signing out discards them. Cancel changes nothing. With nothing unsent, nothing is asked. The sign-out carries the count the person agreed to (0 with no question).
2. The session shows `signing-out` ("Signing out…"), so this tab's board pages go and close their connections; the other tabs are told (`signing-out` on the `BroadcastChannel`) and, if the same person is signed in there, show the signed-out page, closing their boards, and open none of the person's caches again.
3. The person's lock is taken exclusively (`CacheLocks`): every open copy of their cache holds it shared, so the deletion starts only when no tab can write the cache any more, and no copy opens until it is over. A tab that keeps it past 10 s fails the sign-out.
4. The unsent boards are counted again, now that every tab has closed the person's boards (a tab closing with an edit pending marks it): more than the person agreed to stops the sign-out, deleting nothing, and the question is asked again with the new count. Otherwise every key of the person's is deleted from every cache database (`deleteUserBoardCache`, `deleteIndexedDbBoards`); the unsent record, the copied images and the tab's view-only notices are forgotten. Another person's boards and records stay.
5. Only then is the session ended on the service (`POST /api/auth/sign-out`).

A deletion that fails (a lock not granted in time, a database that refuses) keeps the person signed in: the service is not asked, the other tabs are told (`sign-out-failed`) and ask the service again, and the site says "Signing out did not work: your boards could not be deleted from this device…". A service that fails after the deletion keeps the person signed in too, with the device's copy already gone (the boards load from the relay again): the device takes them back (`PersonDeviceData.resume`), so their boards are cached and recorded again, and the other tabs are told (`sign-out-failed`) and ask the service again. A session that simply expired (a request answered `401 signed-out`), or a sign-out on another device, deletes nothing here: the person did not ask on this device, and their cache stays for their next sign-in. The private environment's Sign out has no person to delete for. Without the Web Locks API (outside a secure context) the deletion relies on the other tabs closing their boards when told; without `BroadcastChannel` other tabs learn of the sign-out at their next request. Tests: `person-device-data.test.ts` (two people, the lock's wait, the timeout, a failure), `site-app-sign-out.test.tsx` (the order, the question, Cancel and focus back on Sign out, a reopened board dropped before its restored edits were acknowledged, a deletion failure, a service failure, an expired session, other tabs), `sign-out-dialog.test.tsx`, `cache-locks.test.ts`, the collab package's `indexeddb-board-purge.test.ts`, and the scenario `tooling/scenario/specs/site/sign-out.spec.ts` (an edit left unsent, the question, IndexedDB empty of the person after confirming, the board from the relay after signing in again).

### Fonts

For the current library and coverage files, `assets/fonts/library/catalogue.json` and

lists their licences. The table below also preserves provenance for the original bundled files.

The chrome (toolbar, panels, dialogs) is set in the host's fonts (`ChromeFontSet`, `theme/chrome-fonts.ts`). The shell's own, which the library and the SDK ship, are open: Geist at 400 and 500 and Geist Mono for numbers and shortcut keys (`NEUTRAL_CHROME_FONTS`), static WOFF2 faces from the `geist` npm package 1.7.2. Every face is kept in `packages/app/assets/fonts/`, emitted as a content-hashed file and never inlined (`?no-inline`, `test:bundle` rows), and added to the page once by `useTheme` (`loadChromeFonts`). Rand is Regular and Medium only, the brand's two weights: every heavier weight in the chrome is Medium, and the shell and site set headings, table heads and strong text to 500. Rand's two faces (and Geist's, in the shell's set) are fetched as soon as the theme mounts, with `font-display: fallback` (text waits for them at most about 100 ms, then shows in the stand-in), and given Geist's 1.3 em line box with the cap height centred, so the text styles' line heights hold; until they land the chrome is set in `Rand fallback`, the system's Arial or Helvetica scaled to Rand's average width (`RAND_FALLBACK_FACE`), so it barely reflows. Scripts Rand lacks fall through to the system's font. Geist Mono's files come from the `geist` npm package (which declares a peer dependency on Next.js, so the files are copied rather than depended on). The board uses its own static TrueType copies of Geist and Geist Mono. Text is set in the fonts the app serves, listed as `FONT_FAMILIES` in `src/text-input/font-catalogue.ts`, licensed static TrueType faces, with regular, bold, italic and bold italic wherever the family supplies them. The page loads the default family at startup and other families on demand for the text tool's layout and hands the same files to the engine where it renders, so the caret the page draws and the glyphs the engine draws agree: a main-thread engine host shares the page's library (`pageTextFonts`), and the engine worker is posted the page's bytes once they load (`postFontFiles` from `spawnEngineWorker`, transferred copies, in the page's order; `withFontFiles` in the worker's script puts them into its library), so each file is downloaded once per page and the worker never fetches, whatever the HTTP cache keeps. The build emits the files beside the bundle (`?no-inline`, as it emits the worker scripts) under content-hashed names (`assets/<name>-<hash>.ttf`), never as base64 inside it (`test:bundle` rows check the entry has no `data:font` and the names carry a hash); the page fetches them by URL. No size is written measured without the fonts: a new box typed into before they load is held as a local draft and created, measured, when they land (`PAGE_TEXT_LAYOUT.whenReady`, `TextEditingSession.writeHeld`); a session that ends first creates it with a placeholder size, and every text this client wrote without fonts is measured again then (`TextSizeFollower.fontsLanded`, as a system change). Whoever distributes the app keeps each licence with its files.

## How to test

From the repo root: `pnpm test` runs every package; `pnpm vitest --project @canvas/app` watches this one. Pure modules (`shortcuts/`, `keymap/`, `state/`, `theme/`, `canvas/backing-store-size.ts`) run in Node; component and hook tests opt into jsdom with a `// @vitest-environment jsdom` docblock. `theme/token-usage.test.ts` fails if a component stylesheet uses a literal colour or an undefined token.

`pnpm --filter @canvas/app dev` serves the shell on a standalone page (`index.html`, `src/playground/main.tsx` over `start-playground.tsx`); `pnpm --filter @canvas/app build` builds the library. `pnpm --filter @canvas/app test:bundle` (run by `pnpm check` after `build`, never by `pnpm test`, which stays free of Vite builds) builds the library in memory without and with `VITE_CANVAS_HARNESS=1` and checks it against `scripts/bundle-expectations.ts`, one row per assertion: the harness is left out of a normal build, and the text pass's `layout` and `msdf` fallback handlers are in the entry, the engine worker and the job worker, where text renders.

### Two tabs on one board

1. `pnpm dev:relay` (repo root): the relay on `ws://127.0.0.1:1234` with its boards in an embedded Postgres under `services/relay/.dev-relay/`, and the development token endpoint on `http://127.0.0.1:1235/token`.
2. `pnpm --filter @canvas/app dev`, then open `http://localhost:5173/?board=x` in two tabs (or two browsers). Both open board `x`; the first to connect to a board nobody has written seeds it with the demo board (a board you cleared stays empty). The presence/share bar at the top right says `Live` and shows the other tab's avatar; move a rectangle in one tab and it moves in the other; `mod+z` in a tab undoes only that tab's own edits (each tab is its own guest, `guest-<hex>`, kept in session storage, so a reload stays the same person).
3. Stop the relay and the tabs say `Reconnecting…`, keep editing, and send their edits when it is back. Without the relay running, a new tab says `Offline · local board` and works on the board kept on this device: the IndexedDB board cache (`canvas-board-cache:layout:<n>` for this build's `DOCUMENT_LAYOUT_VERSION`, keyed by the board id within this writer layout), seeded with the demo board only the first time, so a reload keeps its edits. Start the relay and reload: the same cache is what the relay path opens, so the offline edits go to the relay and reach every tab on the board. If the relay's board changed meanwhile too, the two merge like any two Yjs replicas: edits to different objects or fields all survive; concurrent writes to the same field resolve by Yjs's rule (the higher client id wins), not by time. The cache is keyed by board id only: on a shared browser profile, edits one guest made offline are restored into the next person's store for that board and sent to the relay over that person's connection: a deliberate decision while identities are per-tab guests, which must change when sign-in exists (a cache keyed by board and principal, or offline edits held until the same principal returns). A same-layout reload keeps edits (each is appended as it is made); a writer-layout upgrade opens a separate cache. On its first creation, this layout-2 build copies valid legacy cache records unchanged unless a retained layout-1 stamp is present. Skipped layout-1 edits remain only in the old database and are not restored or sent; this release supplies no recovery interface (see the collab README). A tab killed mid-transaction can lose its last one. Where IndexedDB is unavailable (some private windows, a blocked or full database) the board lives in the page's memory and the presence/share bar says `Offline · not saved`. The page logs nothing for a relay or token endpoint that does not answer (Chrome itself logs the refused requests).

Other relays: `?relay=wss://…` (and `?tokenUrl=https://…` when tokens come from elsewhere), or `VITE_RELAY_URL` and `VITE_TOKEN_URL` at dev-server start; `?relay=off` stays local; `?token=<board token>` uses that token as it is (for a token from `pnpm --filter @canvas/relay token`).

Images need the assets service: `docker compose -f services/assets/docker-compose.yml up -d`, then `PORT=1236 PUBLIC_URL=http://127.0.0.1:1236 pnpm --filter @canvas/assets dev` (1235 is the relay's token endpoint), and open the page with `?assets=http://127.0.0.1:1236` (or `VITE_ASSETS_URL`). There is no default: without one the page draws placeholders and says images need the board's server. A site build takes `VITE_ASSETS_URL` (`https:`) if it has one and drops `?assets=`, like the other overrides.

The deployed page is `pnpm --filter @canvas/app build:site` (`vite.site.config.ts`: `index.html` into `dist/site/`, with `VITE_SITE_BUILD=1`): the playground, or the site with `VITE_SITE_PAGES=1` (section [The site](#the-site)). ## Design notes

The default shortcuts cover canvas navigation, the objects and tools, and selection and arrangement, plus undo and redo.

- **Grid and snapping** are the person's preferences, not the board's: `isGridVisible` and `isSnappingOn` live in shell state, start from `localStorage` (`loadViewPreferences`; on a first visit object snapping with its guides is on and the dot grid, so grid snapping, is off) and are written back when they change. mod+' and mod+shift+' flip them in the reducer instead of being replayed to the engine as canvas actions; the shell hands them to the mounted engine (`setViewPreferences`), which shows the grid in its host (`EngineHost.setGridVisible`) and gives the select tool its `SnapSettings` with each pointer input, with the camera, so drags snap only to what is on screen and to the grid only while it shows. The pointer binding reports the snap modifier, Alt (Option on a Mac). The toolbar's toggles dispatch the same actions. The toolbar is memoised on the slices of shell state it shows (the active and available tools, each toggle's pressed state) and its own props, so a canvas action does not render it again.
- **Shortcuts are data.** A shortcut is a definition: chords, description, category, action. The registry is pure and immutable, so the cheat sheet, conflict detection and later remapping read the same list. Shortcuts only dispatch a `ShellAction`; the reducer records canvas actions with a rising `sequence`, which is where the engine and tools will subscribe.
- **Matching follows the person's layout first:** `KeyboardEvent.key` with exact modifiers; then `key` ignoring Shift for symbols typed with Shift (`?`, digits on AZERTY); then `KeyboardEvent.code` read as a US layout, for Option+letter on mac (which types `å`), Shift+digit and non-Latin layouts. The code fallback never applies when the typed key is an ASCII letter or digit, so Dvorak, AZERTY and QWERTZ letters mean what their layout says. One exception to character-first: a digit-row key is matched by position (with exact modifiers) before a Shift-insensitive symbol, so Shift+0 and Shift+1 keep going to 100% and fitting where the layout types `=` or `+` with them (German, Nordic, Spanish, Italian, Swiss); off the digit row the symbol still wins (AZERTY's Shift+M `?`).
- **Native shortcuts** (copy, cut, paste) are listed and reserved but never matched: the browser's clipboard events carry them, and only those events can read the clipboard.
- **The clipboard** (`src/clipboard/`). The shell binds a window-level router (`useClipboard`, `bindClipboardRouter`) to the document's `copy`, `cut` and `paste` events. It leaves an event alone when its target is editable (the text editor's input stops propagation of its own), when it was handled already, while the cheat sheet is open, and when it belongs to another shell on the page (an event inside a shell is that shell's; one on the page itself goes to the shell used last). Copy writes three flavours: `application/x-canvas-objects+json`, a portable board (`exportBoard`) of the selection with its descendants, whose roots move to the board root where they are on the board and stack in the order the board painted them (`copySelection`); `text/plain`, the copied texts and labels one per line; and `text/html`, the texts as styled paragraphs for other apps, whose root element carries the objects again in `data-canvas-objects`, for paths that keep only standard types. Connector ends on objects not copied become free points where they were (`detachConnectorsFrom`); comments are not copied, since a pin belongs to a thread outside the document; images and videos keep their `assetId` (assets are referenced, never duplicated) and texts their runs. A paste tries the handlers by priority: the objects flavour, parsed and imported with `importBoard` (never trusted: format, schema,'s run boundaries, ids, references) and planned by `planPaste` (parents first, siblings bottom first, the box around the roots centred on the pointer, or 16 world units from the originals while the pointer is off the canvas); HTML (the embedded objects, else its text with bold, italic and colour as a text object); plain text as a text object. Everything a paste creates is one `createObjects` command of the local user (one undo step) at the board root, or on top of the group entered with a double-click while one is (re-expressed in its frame, so it still lands at the pointer), with new ids, and the new top-level objects become the selection. Pasted text boxes are sized by an estimate (0.6 em per character, 1.25 em per line) until the text editor measures them. Cut writes the copy first and only then deletes the objects it copied (their ids taken when the cut starts, one delete command, one undo step); a selection holding a locked object is not cut (the delete key leaves locked objects alone, so a cut would copy an object it did not remove): the cut is refused with a `cut-locked` notice and the clipboard left untouched. Copies keep `locked`, and a pasted locked object is still selected by a click. Every copy is also kept in the page's memory (`ClipboardMemory`), so a cut whose system write is refused loses nothing: a paste in the page reads the memory. A flavour over its paste limit (plain text 2 MiB; HTML and the objects JSON 4 MiB, since the canvas's own HTML carries the objects as escaped JSON, 1.2–2 times larger, and the 5,000-object cap is what bounds a paste of objects) is skipped so a smaller flavour of the same paste can be used, and when every flavour is over the person is told; an objects payload of more than 5,000 objects is refused with a notice, and a valid payload the board refuses ends the paste rather than falling through to its text. A paste that arrives during a drag creates nothing and asks the person to finish the drag. A cut deletes, after its write, only what is still unlocked. Notices are messages through the engine's `onNotice` (`MountEngineOptions`, `UseMountedEngineOptions`), which the shell shows on its status line beside the grouping notices; their codes (`cut-locked`, `paste-too-large`, `paste-mid-drag`, `paste-refused`, `clipboard-unavailable`) stay inside the clipboard. Duplicate (mod+d) is a copy pasted at once 16 world units away without touching the clipboard, on top of the originals' parent when they share one (re-expressed in its frame, `inParentFrame`), else at the root. Copy, cut and paste dispatched as actions rather than keys (a button or menu) go through the same router (`ClipboardRouter.runAction`: its handlers and memory) and the async Clipboard API (`createBrowserClipboardAccess`), which carries only plain text and HTML, so the objects ride in the HTML. Images: image files are the built-in `image/*` handler's (`createImagePasteHandler`, priority 200). A copy names the board it was made on (`application/x-canvas-board`, and `data-canvas-board` on the HTML's root; never a token), and the router gives a paste the board its items came from (`sourceBoardOf`). Pasting image objects within a board (or on a page that knows no board) needs no call; from another board, every image's asset is linked to this board with the link call and a token for the source board (the page's token endpoint, `BoardImageAccess.tokenFor`) before anything is created, and a link that is refused, or a source board whose token the page cannot get (or does not know), creates nothing and says why (`createLinkedPaste`). Duplicate never links. **The clipboard's source board is only a claim**: any web page can write `application/x-canvas-board` or `data-canvas-board`, and without a check a hostile page could name a board it does not hold an asset of, so that the victim's browser fetches that board's token and links the asset to a board the attacker reads (a confused deputy that breaks proof of possession once boards have access lists). So a cross-board link is attempted only for an image whose (asset id, source board) pair is in the page's record of its own copies (`CopiedAssets`, `src/assets/copied-assets.ts`) and matches the clipboard's claim. **The gate is at the chokepoint**: `PageImages.linkFrom` itself rejects, before any token lookup or request, unless every asset is recorded under the source board, so no paste handler (`registerPasteHandler` is public API) and no later refactor can link from a board the clipboard merely claims; `createLinkedPaste` asks the same question first only to choose the notice (`PasteImages.wasCopiedFrom`; the count of distinct images in the pasted objects, never trusted for anything else, tells the too-many notice from the copy-again one). `EngineClipboard` writes the record at every copy and cut of images, through the page's images (`PageImages.copies`, the `CopyLedger` `linkFrom` reads): the stored record below, and beside it this tab's own copies in page memory, which a clipboard, a remote update or a URL cannot write, kept for the life of the tab with no age limit (each copy whole, up to 20,000 pairs, oldest copy out first), so a cut and paste on one board works with the storage blocked, after a day and above 2,000 images, and a copy of more than 2,000 images pasted onto another board works in the tab that made it (after a reload or in another tab it is refused with its own sentence, `CROSS_BOARD_TOO_MANY_MESSAGE`, that at most 2,000 images can be pasted onto another board at once). The stored record: for each asset the board and the time, in `localStorage` under `canvas.copied-assets`, which is same-origin storage, so a copy in one tab pastes in another tab of the same browser (it is read afresh at every use; no `BroadcastChannel`). The record keeps at most 2,000 pairs and trusts a pair for 24 hours (a new copy renews it). The pairs of the copy just made are always kept whole (a copy of more than 2,000 distinct images is not stored at all: only the tab that made it can paste it onto another board), and the older pairs are evicted oldest first to make room, so a board full of images cannot push out a copy's own images, and a copy of one board cannot be recorded in part. Stored content over 1 MiB or over 4,000 entries is ignored, and the record never writes more than it reads: a board id over 128 characters is not recorded and a write over 1 MiB drops the older pairs (or is skipped). For any image not in the record no token is fetched for the claimed board, no request names it, nothing is created (the whole paste, as for a refused link), and the person is told to copy the images again on their board (`CROSS_BOARD_NOT_COPIED_MESSAGE`; the expired, evicted, pre-record and no-storage cases all land here, and it names no board); a link the service refuses keeps its own sentence (`CROSS_BOARD_REFUSED_MESSAGE`). A clipboard that claims the board being pasted into as its source makes no link, so it cannot be told from a paste within the board by the link alone: such an image is created only when the record holds its (asset, this board) pair (an honest copy on this board, also after the original was deleted) or the board's document already shows an image of that asset (`PasteLocation.shownImagesAmong`, asked once for the whole paste, as is the record); otherwise it is refused like an unrecorded pair. The paste of non-image objects is unchanged. Content of the storage that cannot be read is ignored, and where there is no storage (or it throws) nothing is trusted, so a paste of images that this page cannot vouch for is refused while everything else still pastes. **What the record protects against, and what it does not.** It stops a page of another origin, which can write the clipboard but not this origin's storage, from choosing the source board of a paste or from making this page show an asset the board does not hold. It holds only asset ids, board ids and times: no token, no bytes, no signed URL. It proves nothing to the service, whose own checks (a source token that the source board's link accepts) are unchanged, and it is not access control: it does not stop a person from copying an image they can see and pasting it elsewhere, which is what proof of possession allows. A script running in this origin (an XSS, a malicious extension with page access) could write the record, and a hostile page that puts on the clipboard an image this browser did copy, naming the board it was copied from, gets a paste the person could have made themselves; both are outside this threat. **Not covered: video objects.** A video's `assetId` and `poster` are outside the record (only images are recorded and checked); that is a known gap tracked separately. The engine side is `DocumentClipboard` (`src/engine/document-clipboard.ts`: the copy, the prepared cut, the paste location's `createObjects`, duplicate, over the engine document's store and its select tool; `createEngineDocument` makes it beside the engine document) and, per mount, `EngineClipboard` (`src/engine/engine-clipboard.ts`), which follows the pointer over the canvas for the paste location and takes duplicate (mod+d) before the engine document does.
- **The editable guard** comes from the prototype (webgl-whiteboard `src/app/controller.ts`, `onWindowKeyDown`): no shortcuts while typing in an input, text area or select; contenteditable is added. Keys a component already handled (`defaultPrevented`) are left alone, and canvas shortcuts are off while the cheat sheet is open.
- **Theming** is a token set applied as CSS custom properties on the shell's root element, not the document, so an embedding page keeps its own styles. Components use CSS modules and only `var(--token)`s.
- **The test harness** (`src/harness/`, for the scenario tests) replaces the prototype's `window.__wb`. Only a build or dev server with `VITE_CANVAS_HARNESS=1` has it: `useShellHarness` is chosen when the module loads, and Vite replaces the variable at build time, so a normal build keeps only a pass-through and drops the harness code (`test:bundle`, `scripts/check-bundle.ts`, builds the library both ways and checks). The harness hangs off the shell's root element (`[data-canvas-harness]`, property `canvasHarness`) rather than `window`, so each shell on a page has its own and an embedding page gets no global. It reports plain data (`snapshot()`, including the engine's camera, mid-glide included). In a harness build, `snapshot()` and pixel reads flush one batch of pending main-host frames when the scenario init script sets the `isCanvasHarnessClockFrozen` global. They use the current frozen time without advancing timers or draining follow-on frames; real-clock pages and production keep their normal schedule. Its canvas metrics take the drawing buffer and ratio from the engine (`MountedEngine.drawingBuffer`: the buffer the engine's latest frame drew into, where it runs), since a canvas handed to the engine worker is sized there, and fall back to the element's `width` and `height` before the first frame; after a resize the size arrives with the engine's next frame, so specs poll for it. `readPixels` is a capture request fulfilled inside the engine frame: the engine host answers in the next frame of its own (a worker's animation frames are not the page's, so the scenario's frozen clock does not stop them), and the frame's read-back runs after `submit`, in the task that drew it, so the GPU canvas needs no `preserveDrawingBuffer`; the pixels are converted to straight alpha. The harness page also reads `?platform=` and `?theme=`.
- **The engine mount** (`src/engine/`) is one function behind the `MountEngine` type: the shell calls one once per canvas (`useMountedEngine`): by default `mountDefaultEngine`, which runs the engine host mount below with the engine in its worker where the platform's `canRenderInWorker` probe (`OffscreenCanvas`, `transferControlToOffscreen`, `Worker`, an `OffscreenCanvas` WebGL2 context; once per page) succeeds and on the main thread (`MainThreadEngineHost`) where it does not, so the fallback Safari takes is the path `?engine=main` and `?workerProbe=fail` exercise; another through the `mountEngine` prop. Every mount the shell runs is the engine host mount (removed the older standalone main-thread mount, which had its own frame loop, camera transition and pixel capture; the main-thread host is its replacement). The board is a `YjsDocumentStore` (the `store` option; by default `createDemoDocument` loads the demo board, `createDemoBoard`: four sections of 70 rectangles, whose siblings carry distinct z keys in creation order so the order commands work on it however it is loaded, through `createObject` commands with the system origin, until documents come from the relay,/), and the scene derives from its change sets (`DocumentSceneFeed`), which also keep a hit-test R-tree current between frames. The local user (`LOCAL_USER_ORIGIN`, until sign-in) edits it with the select tool (`EngineDocument` over `SelectController` of `@canvas/tools`; the nine align, distribute and tidy-up `ArrangeCommand`s run `planArrange`/`runArrange` of `@canvas/tools` on the selection, one step each), and `mod+z`/`mod+shift+z` run the user's `createHistory`, where each drag is one step. The engine host mount runs this `EngineDocument` on the page (below); the frame clears to transparent so the theme's canvas colour shows. A Strict Mode remount keeps the same host (`engine-host-lease.ts`). When no host can start, `ready` rejects and `onEngineError` receives the error; faults after the start (a frame that throws, a worker that crashes) reach it too, through `MountEngineOptions.onFault`, in the worker and on the main thread alike; without `onEngineError` the page gets them through `reportError`.
- **Camera input.** The canvas's wheel (Control/⌘ zooms about the cursor, a plain wheel pans; a trackpad pinch arrives as Control-wheel in Chrome and Firefox, and as `gesturestart`/`gesturechange`/`gestureend` in Safari, whose default is prevented so the page does not zoom), two touch points (pan and pinch about their midpoint) and a middle-button drag go straight to the camera; primary-button and single-finger input is left to the tools: the select tool takes the primary mouse and pen button (the pointer is captured, so a drag that leaves the canvas keeps going; Shift and mod, ⌘ or Control on any platform, go with each event) while it is the active tool, and mouse and pen hovering too, so the canvas shows the cursor the tool asks for (a rotate cursor, an inline SVG image, over the band just outside a selection's corner, turned about its hotspot to the tool's angle (the corner's quarter turn plus the selection's rotation) in 15° steps so it wraps the corner it sits outside of, as in Figma; the untouched icon is the top-left corner's; `select-cursor-style.ts` builds each step's data URI once, and the style is written only when the value changes), kept up to date for a still pointer when the camera or the document changes. Keys go through the shortcut registry, so the editable guard applies: `+`/`=`/`mod+=` and `-`/`mod+-` zoom about the viewport centre, `Shift+0` and `mod+0` return to 100%, `Shift+1` fits the board (animated over 240 ms, at once with reduced motion), `Shift+2` fits the selection, and the arrows, which also nudge the selection, move the selection (1 world unit, 10 with Shift) or, while nothing is selected, pan the view (100 px, 500 px with Shift). Zoom stays within 0.02×–64×.
- **The developer overlay** (frame rate measured, always; memory instrumented) shows the engine's `BenchmarkSample` (the same summary the benchmark harness records): p50 and p95 of CPU time per stage and per frame, GPU time per timed pass, draw calls, uploads and visible records, and GPU memory per category now and at its peak. It reads through `readFrameStats` every 250 ms (`usePolledValue`, which takes a value or a promise of one, and starts no read while one is pending), never per frame, so watching the frame rate cannot cost frames, and it takes no pointer input but its "Frame bars" toggle, which shows a bar per recent frame (its stages against a 60 Hz frame, from the sample's `recentFrames`) and the newest frame's draws, segments, visible records, passes, pipeline switches and time past budget. The statistics are the engine's own: while the overlay is open the shell starts them on its engine (`MountedEngine.startFrameStats`; `useMountedEngine` starts them again on an engine mounted later) and stops them when it closes, so frames pay nothing for them otherwise. The engine host mount calls the host's `startFrameStats`/`readFrameStats`/`stopFrameStats`, which the engine answers from its own stage timers where it renders (the worker's, one message each way per read; the main-thread host's, at once), every stage included, the selection overlay and the capture too.
- **Frames per second** is `frameRateOf` (`src/diagnostics/frame-rate.ts`, pure, unit-tested) over a rolling window of the engine's own frame timestamps (`EngineFrameReport.frameTimeMs`, the page's clock even when the engine runs in its worker), not a second `requestAnimationFrame` loop of the overlay's own: `HostedEngine.frameTimesMs()` keeps the last `FRAME_RATE_WINDOW_MS` (5 s) of them, appended on every `onFrame` report it already receives (`recordFrameTime`), whether or not frame statistics are recording, since it costs only an array push. The overlay polls it at `DEVELOPER_OVERLAY_FPS_POLL_INTERVAL_MS` (about 2 Hz, slower than the 4 Hz of the other figures) so the number stays readable, and shows the current figure (frames drawn in the last second) and the lowest one-second bucket of the last 5 s that had a frame at all: a bucket with none is a quiet board (the engine draws only when something changed), not a stutter, and is left out rather than dragging the low figure down. Idle (no frame in the relevant window) reads `idle`, never `0 fps`, so a still board does not look broken. The figures are two columns of one table row (`Frame rate`), so their digits line up with the rest of the overlay (`font-variant-numeric: tabular-nums`).
- **The engine host mount** (`src/engine/mount-engine-host.ts`, the engine in a worker): `createEngineHostMount({ prefer, onEngineReady })` returns a `MountEngine` that starts an engine host in the canvas through `createEngineHost` (in a worker where the browser allows, else on the main thread; `start-browser-host.ts` gives up on a start that takes over 10 s), keeps it sized, forwards the canvas's pointer events with their timestamps (each coalesced move event on its own), and captures pixels inside the host's frame (`EngineHost.readPixels`, unpremultiplied for the harness). Everything that reads input or the document stays on the page: the camera controller, fed by the canvas's input bindings and the shell's shortcuts, and the select tool with the document and the undo history (`EngineDocument`, with the select tool's cursor). The host only draws: each change set of the document (the drag preview laid over it) is serialised at once and sent (`serializeChangeSet`), the selection overlay's model goes with `EngineHost.setOverlay` (one per task), which the worker draws with the tools' own `SelectionOverlay` at each frame's zoom (`createSelectionOverlayLayer`, given to the main-thread host and in the engine worker's script), and each new camera follows. A fit glides with `animateCamera` on the engine's own frames, so it keeps moving while the page is busy; `camera()` reports the camera the engine's latest frame drew until the glide reaches its target, and new input continues from there. If no frame draws the target within 500 ms after its duration (a hidden tab, a stalled worker, a slow frame on a weak GPU), the glide settles on its target (`EngineGlide`), never on the camera a frame drew on the way, and page and engine agree on it again. Frame reports also bring the drawing buffer's size (`drawingBuffer()`), and faults go to the shell's `onEngineError`. In harness builds the engine harness also records the page's long tasks and each pointer input's time to the report of the frame that took it (`PageResponsiveness`), for the benchmark's leaf-selection drag. A canvas can hand its control to a worker only once, so a hold (`engine-host-lease.ts`) keeps the host through React's Strict Mode remount and destroys it only after the last release. The engine worker's script is `src/engine/engine-worker.ts`, which Vite bundles from the inline `new Worker(new URL(…, import.meta.url))` (the library build emits it as `dist/assets/engine-worker-*.js`, an ES module found relative to `dist/index.js`: `base: './'`). The engine's job pool builds path meshes and decodes images in job workers running `src/engine/job-worker.ts` (the engine's default handlers), which `engineJobWorkers(scope)` (`spawn-job-worker.ts`) starts, as many as `chooseWorkerCount` allows: from the engine worker for the worker host, from the page for the main-thread host (`start-browser-host.ts`). It is the shell's default where a worker can render (`mountDefaultEngine`); in harness builds that default puts the engine harness on the canvas too (`engineHarness`: frame reports, change sets and cameras for the engine alone, `loadDocument` into the page's document, frame statistics). The harness page's `?engine=worker|main` mounts it with the host kind forced (`src/playground/engine-shell.tsx`), `?engine=main` being the escape hatch to the main-thread host; `?content=empty` starts it without the demo board, so the benchmark harness (`tooling/bench`) draws only the boards it sends. `?content=selection-cap` supplies 600 rectangles for the selection outline-cap scenario. Once the canvas has handed its control over, the backing store stops setting its size and only reports it; the engine sizes the buffer.

The micro gate remains relative; this run had no matching prior reference. - **Images** (`src/assets/`, `src/engine/image-support.ts`). The engine draws images through its texture manager, whose `AssetSource` is code the page's options cannot carry, so it is built where the engine runs: the engine worker's script passes `createImages: createImageSupport`, and the host calls it with the opaque image channel `engine-init` transferred. **How the board and the reader's token reach the engine worker** (the controller's ruling): the page's images (`PageImages`, one per board connection) make a `MessageChannel` when the host starts (`imageHostOptions`), keep one port (`pagePortLink`) and hand the other to `createEngineHost` as `imageChannel`; the worker's `createImageSupport(port)` builds a `LinkedAssetSource` over it (`adapterPortLink`), which asks the page for `{ assetsUrl, boardId, token }` (`access-request`), and the page answers, again on a token refresh (the adapter asks after a `401`) and on a board switch (the adapter then ends the old board's streams and describes every subscribed asset again). A `BroadcastChannel` is never used (any same-origin page could hear it). A main-thread host gets the page's end directly (`directLinks`), both ports closed. A newer engine's link parks the one before rather than closing it (`EngineLinks`: the History preview borrows the board's images while the live engine stays mounted); once the newer engine's host is destroyed, `startBrowserHost` releases its link and the parked one is current again, caught up with the uploads under way (their bytes, and `uploaded` for the verified ones), the page's visibility and a fresh access, so an upload's badge never waits on an engine that is gone. The token is held by the page's `PageImages` and the adapter's `AssetsHttp` only, sent only in `Authorization` headers (events are read with `fetch`, not `EventSource`) and a link's JSON body, never put in a URL and never logged; `AssetsHttp` refuses to send it to any origin but the service's. The service refuses a token in a URL, and `assets/asset-urls.test.ts` scans every request the page's images and the engine's source make (upload, link, records, events, tiles, level, tile and original bytes) for one; the page needs none of the service's signed route URLs, which are for clients that cannot send headers. Signed URLs (in the adapter's records) are fetched without the token and read again past 900 s less a minute, and once more when refused. A tile's signed URL comes from its route as JSON (`SignedTiles`: kept until a minute before it expires, at most 1,024, signed again when the bucket refuses it) and the tile is fetched from it directly: a redirect from the service would reach the bucket with `Origin: null`, which its CORS rule refuses. Without an assets service the page answers `access: null` and the adapter serves the fallback: seeded synthetic images in harness builds (`harness-assets.ts`: `createFixtureAssetSource`, levels above 128 px after a 150 ms latency; a scenario holds and releases them over the `BroadcastChannel` `canvas-harness-assets`, the test harness's own), else none (placeholders). Images are decoded and resized by `decode` jobs in the engine's job workers, never on the thread that renders. **Uploads** (`PageImages.insert`): a dropped (`MountImages`, `bindImageDrop`), pasted (`createImagePasteHandler`) or picked (`ImagePicker`, the image tool's `pickImages`) file is refused with a notice when the board cannot take it (`refuseImageFile`: type, size), read in a worker (`prepare-image-worker.ts`, at most two files at once, the rest queued: the upright size from the file's header without decoding it (`image-header.ts`: PNG, GIF (the larger of its logical screen and its first frame, whose descriptor is found by walking at most 4,096 blocks), WebP, and JPEG; PNG/WebP/JPEG use EXIF orientation (PNG `eXIf` before image data, WebP `EXIF` only when extended `VP8X` advertises it, with RIFF padding; metadata reads capped at 1 MiB), AVIF with `irot`), over 64 megapixels refused before anything else is read, then SHA-256 with `crypto.subtle.digest`, the bytes released once hashed; a worker that fails to load or dies fails every waiting file with one notice, and the next drop starts a fresh one; the header's size only places the image, the service reads the image itself and its record keeps the size), handed to the adapter as a local image (`local-image`, a `Blob`; the page waits for `local-image-held`, at most a second, so the engine draws the new object from its bytes without asking the service, which cannot answer before the upload verifies), placed (`placeImages` of `@canvas/tools`) as one `createObjects`, and uploaded (`ImageUploads`: three at once, one per asset; `runUpload`: declare, put with progress through `XMLHttpRequest`, complete, with `Retry-After` waits, a fresh token after a `401` and one fresh start after a completion that a new put can fix). Once verified the page tells the adapter (`uploaded`), which follows the record and reports its status (`asset-status`) for the image's state (`UploadBadges`: over the image, following the camera every frame while one shows and asking for no frame otherwise: a determinate bar with the put's real bytes, "Uploading · 3.2 of 8.0 MB", and Cancel, which stops the upload and removes its images; a Spinner once sent); a `ready` record ends drawing from the page's bytes. A failed upload keeps its image, drawn from its bytes, outlined in dashed red with Retry and Remove (which deletes the image objects, never an asset), and the error toast (`UploadFailedToast`: "1 image couldn’t upload", counted, with Retry, until dismissed or retried) is posted to the shared toast region (`useToast`) like the shell's other notices. A collaborator's image still processing shows a Spinner and "Processing image…" (`PageImages.processing`). After a reload the file is gone, so an image whose upload never finished (the board is not linked to its asset) is a placeholder for good: the image section asks the service once when such an image is selected (`ImageAvailabilityCheck`, through `ImageAvailabilityProvider`) and, with Remove, says it is not available on this board (`UNAVAILABLE_IMAGE_MESSAGE`: the page cannot tell an abandoned upload from another board's asset, an unknown id or a collaborator's upload still going), or, only for an upload this page began (`ImageUploads.hasAdded`, availability `unfinished`), that it never finished uploading (within ten minutes of its placing: not yet). The Crop button stays focusable when it cannot crop (`aria-disabled`) and says why beside it, which a screen reader reads with it. `describeDevice(window)` (`device-description.ts`) gives the host the device's memory and whether it is a phone, for the GPU memory budget (`budgetForDevice`), which the texture manager and the path mesh cache share.
- **Behaviour to confirm with the owner** (fix round 2; controller rulings the owner may change). Images resize proportionally unless Shift is held, the reverse of other objects and what most whiteboards do for images: a plain drag of an image's handle keeps its drawn aspect (the crop region's), and Shift frees it (`resizeAspectOf` of `@canvas/tools`). A mixed selection follows its strictest member: a selection holding an image (or a group holding one) resizes proportionally unless Shift is held. A box off its image's aspect (after a Shift resize, or a merge of a crop with a concurrent resize or restyle) shows the image fitted inside it, centred with empty bands, never stretched; the next plain resize or a crop brings the box back to the image's aspect. Known limit: snapping, alignment, distribution and the selection frame of such an image use its stored box, bands included, while clicks hit only the drawn rectangle.
- **Grouping**. The arrange actions `group` (mod+g) and `ungroup` (mod+shift+g) run on the page's document side (`EngineDocument`, `runGrouping`): `group` runs `groupCommand` on the selection and selects the new group, `ungroup` runs `ungroupCommand` on every selected group and selects what they held; each is one command, so one undo step. Objects with different parents group nothing (`mixed-parents`), and the shell says why: the mount's `onNotice` option carries the sentence up (`useMountedEngine`) to the shell's one notice (see Notices below). Delete and the align, distribute and tidy commands leave a selected group that holds a locked object, as they leave a locked object, and say so the same way. Entering a group is the select tool's (a double-click; Escape, the `deselect` action, leaves one level); pointer input carries each event's `timeStamp` for its double presses. It lives in `run-grouping.ts`; the selection and arrange shortcuts (select all and same type, deselect, delete, lock, align, distribute, tidy, the four order commands, group and ungroup) are dispatched by `engine-document-commands.ts` (`runSelectionCommand`, `runArrangeCommand`), moved out of `EngineDocument` so it stays under 400 lines.
- **Undo and redo** (`runHistoryCommand` in `src/engine/engine-document-commands.ts`). The history actions run the person's `UndoHistory` from `@canvas/document`, never in the middle of a gesture. One click undoes or redoes at most one step; a step whose changes were all overwritten since (by someone else, by the same person in another tab, or by the product's own writes such as a reference repair), so that it can change nothing any more, is used up with nothing changed, and the shell shows "Nothing to undo here: this has changed since." (or "Nothing to redo here: …") through `onNotice`, so the click does not look ignored. The same notice shows when the undo would delete an object someone else (or the same person in another tab) has edited or referred to since it was created (a shape they recoloured, a frame they put something in, a shape they attached a connector to): the object stays with their work, and the step is used up (`engine/engine-document-undo-guard.test.ts`; in Chrome with two pages, `tooling/scenario/specs/app/undo-creation-guard.spec.ts`). When the history says another person changed it since (`lastProtection()`: the objects and their Yjs client ids), `runHistoryCommand` hands that to `onNotice`, and the shell outlines those objects while the notice shows (`noticeOf`, `NoticeOutlines`), keeping the words above. The design's "Can’t undo — Mira changed this since" is not shown: the writer's Yjs client id is chosen by the writing client and the relay ties none to a person, so a name could be forged (naming waits for a relay that stamps the client ids each connection writes with). A step that would have written back a value the relay's door refuses (a size past 2^32 or a non-finite coordinate a peer left) applies without it, and the shell shows "Part of this could not be undone: it holds a value out of range." (or "… redone: …") instead, read from the history's `lastOmission()`; when whole objects were not brought back it shows "Undo could not bring back N objects because their stored values are out of range." (`lastOmittedObjects()`) (`engine/engine-document-undo-guard.test.ts`; the rule is `@canvas/document`'s door guard). A click with nothing to undo or redo stays silent.
- **Collaboration in the shell** (`src/collab/`): the playground (`startPlayground`, `openPlaygroundBoard`) reads the board's address from the page URL (`parseBoardAddress`) and opens it before rendering the shell (`openBoardConnection`): a new `YjsDocumentStore`, then `createCollabClient` with a token provider (`createBoardTokenProvider`: the page's `?token=`, or a fresh token from the token endpoint for the tab's guest on every connection, so a user back after the token expired reconnects), the IndexedDB cache, the browser's network status and presence under the token's principal. The shell's engine (the host mount, as always) mounts on that store with the origin `user:<sub>` of the token (`userOriginFromClaims`), so the select tool's commands are the synced edits and each tab's undo history is its own (remote updates arrive with the system origin and are never in it). Once the first sync is done, a board nobody has ever written (no objects and no metadata stamp, `isStampedDocument` of `@canvas/document`; a board whose objects were deleted is stamped and stays empty) is seeded with the demo board through `writeBoard` (the command layer, system origin, the objects' own ids and times: two tabs seeding at once write the same objects, which merge). A token the relay refuses on the first connection (after the collab client's one refresh) shows `Not authorized`. A board this build cannot read (the relay's layout gate refuses the client, or its store refuses the relay's data; the collab client's `outdated`) shows `App out of date: reload the page`, with what to do in the tooltip, and never falls back to a local board; when the store found objects no writer stamped (its `unversioned` problem: data no build can trust, which reloading does not fix) it shows `This board cannot be opened safely right now` instead; while outdated the shell turns editing off the way the cheat sheet does (`useIsOutdated`: the toolbar, canvas and panels are inert, shortcuts and the clipboard off), and the chip, rendered by `AppShell` outside that subtree, stays live. Pan and zoom are off too: accepted for now, since no second stored layout exists yet, so an honest client cannot become outdated in the middle of a session (a read-only board mode is a follow-up). When no relay is configured, the client cannot start (no token), or the relay's first answer is a failure (unreachable, offline, nothing within 5 s) with nothing cached, the page closes the client and works on the local board (`createLocalBoardConnection`, `Offline · local board`) and does not retry until reloaded; with a cached board it stays synced and keeps retrying, and so does a viewer's or commenter's (read-only, filled in when the relay answers). The local board opens the same board cache (`openDefaultBoardCache`: the collab package's IndexedDB cache, `DEFAULT_CACHE_DATABASE_NAME`, keyed by board id; on a fallback it takes over the cache the relay path opened) and binds its store with `DocumentCacheBinding`, so its edits survive a reload and the relay path restores them before its first sync the next time a relay answers; both paths seed through `seedIfNeverWritten`. After a stored-layout bump, both carry the board's unsent edits over from the earlier layout's cache (the collab package's `LayoutCarryOver`: the synced path after the first sync, the local board against its restored store before seeding) or say plainly, above the chip, what could not be carried over (board, unsent changes, both layouts) until the person dismisses it. Without a cache it works in memory and its status says so (`isSavedOnDevice: false`, `Offline · not saved`). A token endpoint that does not answer (`TokenEndpointUnreachableError`) means no relay, as an unreachable relay does: it is not reported, neither on load nor on the client's retries. Harness builds connect only when `?relay=` says so, so scenarios never reach a relay a developer is running; the guest id is drawn only when a token is fetched, so a local page's seeded ids do not shift. The chip (`ConnectionChip`) reads the connection through `useSyncExternalStore`; the harness reports its status and reads objects from its store (`readObject`, `readObjects`). Remote cursors are not drawn yet (presence is exchanged; the chip counts the others).
- **Tool routing** (`src/engine/tool-router.ts`). The engine's document side (`EngineDocument`, used by both mounts) sends the pointer (the primary button, one finger, a secondary click, a held finger), the cursor and its refresh under a still pointer (`refreshCursor`), and the canvas keys through a `ToolRouter` to the active tool's `ToolMode`, with no check of the active tool of its own: every tool's mode comes from the registry below, the select tool's included (`modes/select-mode.ts`, `SelectToolMode`: a thin view of the one `SelectController`, so the selection outlives every switch of tool), and a tool with no registered mode yet leaves primary-button input alone with the default cursor. The select tool's overlay is always the base the active mode's fields are laid over. `registerToolMode(tool, factory)` makes a toolbar tool start a mode; `registerActivation(type, factory)` makes a double-click (or Enter, the `activate` selection shortcut) on an object of that type start its editing mode. The modes come from a registry (`src/engine/modes/`): each file named `<tool>-mode.ts` exports a `toolModeEntry` (`ToolModeEntry`: the tool, the object types its activation edits, `create` and `activate` over the `ToolModeServices` the document side gives), `TOOL_MODES` collects them (a file without one, or two for a tool or type, fails the unit tests), and each mount registers them all on its own router (`registerToolModes`), so tests stay isolated. A new creation tool adds its file (and, with the toolbar, its availability flag); `EngineDocument` does not change. The select tool is `modes/select-mode.ts`, the text tool `modes/text-mode.ts`, the sticky tool `modes/sticky-mode.ts`, the line tool `modes/line-mode.ts`, the pen `modes/pen-mode.ts`, the shape tool `modes/shape-mode.ts`. Each mode reads its creation tool's style through `ToolModeServices.toolStyleOf` (`DocumentPanels.toolStyle`). A mode that finishes hands back to the select tool, which takes the same input when the mode passes it on (a click outside the text being edited commits it and selects what it lands on), and the canvas tells the shell (`MountEngineOptions.onToolChange`) so the toolbar follows; the router merges the mode's overlay fields into the select tool's model, its `toolRects` appended, and the engine draws them after the selection (in the worker with the rest of the overlay). A double press activates on its second press (`isDoublePress`): ending the select tool's mode drops that press, and the new mode takes the rest of it; Enter activates the one selected object (`source: 'enter'`, so the text mode selects the whole text instead of placing the caret).

Row positions (`LayerRowIndex`) are remembered and, when a splice moves them, found again by an identity scan. Local change sets apply at once; remote ones are queued and applied together at the next animation frame (`LayerTree.queueChanges`), so a collaborator's burst costs one pass a frame. `layer-restructure.test.ts` checks random sequences of structural changes, collapses and expands against a full rebuild (`buildLayerRows`), and `layers-panel.bench.ts` times the tree at 50k objects (with every frame open, a create, reparent or restack is well under a millisecond). Click selects, Shift+click adds or removes, the keyboard follows the WAI-ARIA tree pattern (Left finds the parent by scanning up from the row), the primary selection's row is revealed (its ancestors expanded, O(depth) plus the splice) and scrolled into view unless the person is scrolling the list, and the group the select tool entered is marked (`aria-current`, an accent bar); each row's lock locks or unlocks that object alone (`toggleLockOf`, one `setLocked` command, the selection untouched); a locked row's accessible name ends in ", locked". **Drag and drop** (`useLayerDrag`): a press on a row that moves 4 px drags the selection (if the row is selected, objects inside another dragged object going with it) or the row alone; over the top or bottom quarter of a frame's or group's row (half of another row) the objects go above or below it as its siblings, below an open container on top of its children, over the middle into it (`layerDropAt`; a main is a container, an instance never is, ruling 14), shown by a line indented to the level they land at or an outline around the container; a locked container, or one among or inside the dragged objects, refuses the drop in the refusal colour and says why (`role="status"`); releasing dispatches one `placeLayers` action, so one `placeObjects` command and one undo step; Escape cancels; the list scrolls at its edges. Alt with an arrow moves the focused row's objects the same way (`layerKeyPlacement`: up or down past a sibling, Left out to above the parent, Right into the frame or group above) and keeps focus on the row. A person who cannot edit can neither drag nor move.

- **Touch and the context menu**. A finger's press starts a 500 ms timer (`LongPressTimer`) that sends `hold` with the time and the finger's place, unless the finger wanders 8 px first; the tool then opens the menu and is at rest, and the binding ignores the rest of that finger, so an entry chosen while it is still down runs. Fingers are forgotten when they lift, are cancelled or lose their capture, and a primary finger landing drops any left from a sequence whose lift was never seen. A second finger landing cancels the first finger's press or drag (`pointerCancel`: nothing is written and the press's selection is put back) while `bindCameraInput`'s two-finger gesture pans and pinches, and no finger is the tool's again until all have lifted. The canvas's `contextmenu` is always prevented; a mouse or pen one becomes `contextPress` (a right-click, or Control-click on a Mac), a touch one is ignored, since the long-press is the tool's own. When the tool asks for the menu the mount calls `MountEngineOptions.onContextMenu` with the press in viewport px (`contextMenuRequestAt`), and a finger's double-tap that activates nothing (on a leaf object, or on empty board, a frame's background included) runs zoom to selection, or zoom to fit when nothing is selected, on the mount's camera; a double-tap on a group enters it, as a double click does. A finger's double-tap is decided on its second lift: a second press that drags or is held is a drag or a long-press, and nothing is entered or zoomed. The menu (`src/context-menu/`) is the shell's own: `contextMenuSections` lists the registry's selection and arrangement shortcuts that apply to the engine's selection when it opens (select all and paste on empty canvas; delete, duplicate, copy, cut, lock and the order commands for one object; group, align and tidy up from two; distribute from three; ungroup with a group selected), in registry order with each shortcut's primary chord, so commands later tasks implement appear as their shortcuts land; choosing an entry dispatches the shortcut's own action. `ContextMenu` is a WAI-ARIA menu opened at the press and kept inside the viewport: focus moves to its first entry, the arrows, Home and End move, Enter or Space chooses; Escape (marked handled, so it does not also deselect), Tab and a press outside close it, and focus returns where it was. Rows are 44 px tall under a coarse pointer. The shell has no other menu ('s toolbar and panels are buttons), so this is a minimal one; its arrangement entries dispatch the same `arrange` actions as the style panel's arrange section, since both come from the one `ArrangeCommand` set.

Built by Vite in library mode (`vite.config.ts`, React left external); `tsc -b` emits only the declarations. The built entry imports its extracted stylesheet (`dist/index.css`) so a consumer gets a styled shell.

Record read cancellation releases the caller immediately without cancelling other readers.
A 30 s deadline aborts a hung record request and frees its slot, including stalled response bodies.

The header preflight accepts a TIFF orientation only as one SHORT in IFD0; absent tags,
malformed metadata, and nonstandard LONG orientation retain stored dimensions. This stricter
TIFF rule applies to JPEG as well as PNG and WebP. WebP requires the VP8X EXIF flag (`0x08`):
a trailing EXIF chunk in a simple VP8/VP8L file, or one with that flag clear, is ignored.
The assets service follows the orientation exposed by libvips: sharp's `ExifOrientation`
reads `VIPS_META_ORIENTATION`, which `autoOrient()` uses (sharp `src/common.cc` and
`src/pipeline.cc`). A local decode with sharp 0.35.4/libvips 8.18.6 confirmed a 32×12 WebP
with orientation 6 becomes 12×32 with the flag set, but stays 32×12 with the flag clear
or with simple VP8 and trailing EXIF. No pixel rotation is added to the page's header reader.

### Trace sheets

`src/trace-sheets/`: when an agent creates objects while the person has the board open, a sheet opens for that agent (option A of 2026-10-05: the sheet holds the agent's new objects). `TraceSheetTracker` holds, per agent, the objects whose `createdBy` is `agent:<id>` that arrived from the relay after the connection first reached `connected` (so nothing already on the board, and nothing the person's own undo brings back, lands on a sheet); a member someone deletes leaves it, and a sheet left empty closes. The sheets are the person's view state, never written to the document. The engine draws their tint (`createTraceTintLayer` of `@canvas/engine`, a layer of the shell's overlay, `engine/shell-overlay.ts`, through `MountedEngine.showTraceTint`): a fill at 8% in `--color-hand-agent` over the union of the members' world bounds, padded, and an outline; the page sends a model only when those bounds change. The tab (`TraceSheets`, over the canvas) sits at the sheet's corner, follows the camera each page frame without rendering React, names the agent from presence (else its id) and, for a person who can edit, offers Lift off and Keep sheet; a viewer sees the tint and the name. A polite live region announces each sheet that opens. When an agent with an open sheet leaves presence (its connection was lost), the tab reads "<name> · stopped" (the name presence last gave it) under an announced notice, "<name> stopped: connection lost. What it drafted stays on the sheet.", with Ask again shown disabled, "not available yet" (the app cannot ask an external MCP agent to retry); the objects stay and Keep and Lift off work as before; the tab keeps room for the notice inside the canvas, and returns to its working state when the agent comes back. The agents are judged only while the person's own connection is up, and taken for stopped only 2 s after it came up (presence repopulates after a reconnect), and an agent presence never showed (the MCP server's CLI joins without presence today) is never taken for stopped. Keep closes the sheet. Lift off runs `liftOff` of `@canvas/document` under the person's origin: one `deleteObjects`, one undo step in their history, keeping the objects someone other than the agent wrote to since (the rule, judged on the Yjs items by `writtenSinceCreation`) and those a kept or person's object depends on, and the shell's notice says how many it kept. Changes an agent makes to existing objects are not on a sheet: objects carry only `createdBy` and `updatedAt`. Tests: `trace-sheets/*.test.ts(x)`; in Chrome, `tooling/scenario/specs/app/trace-sheets.spec.ts`; with an MCP agent and a real relay, `tooling/e2e-sync/src/mcp/trace-sheet-relay.test.ts`.

### On-demand fonts

The font field keeps its native keyboard behavior and opens a searchable browser with category
filters and previews. The Library contains the 31 owner-named families plus legacy Liberation
Sans. Four Liberation Sans faces form the startup fallback; other families load only when
referenced by a board, an editing draft, or a visible preview. Text renders in fallback while
files arrive. Failed requests retain existing faces and do not loop; the catalogue offers an
explicit retry. Actual face availability is retained, with the engine's existing weight/slant
fallback where a family has no authored variant.

`DemandFonts` coalesces requests. `followBoardFonts` scans the initial board and only changed
objects thereafter, including labels. The worker receives each face generation once, and the
host requests a frame after loading. Layout and rendering share the same bytes. Coverage fonts
are selected by script; layout-only run substitutions preserve stored family names. Existing
script shaping behavior is unchanged. All fonts uses `/assets/fonts/` on the board’s configured assets service (`VITE_ASSETS_URL`,
or the development override). Opening a board calls the internal `configureFontCatalogue`;
`fontCatalogueBase` supplies the same route for metadata and face URLs. Owner import
and upload instructions are in `tooling/fonts/README.md`. Local font access is.

The checked-in files and `assets/fonts/LICENSES` carry licences and provenance. The new
`font-library` scenario proves search, choice and undo; the golden scene samples all five
categories on both GPU backends. The opt-in `font-library` benchmark distributes ten families
across the existing seeded board and checks the ordinary memory budgets. Frame timings are
reported; this scenario currently has no dedicated frame-time gate.

### Local fonts

The picker’s **On this computer** source requests browser permission only after **Allow local fonts**. Supported static TrueType and CFF bytes are read lazily for visible previews and sent only to this page’s rendering worker; a face of a collection (TTC or OTC), which the browser hands over as the whole file, is picked out by its PostScript name and extracted into a file of its own. Before the page parses a local file, a dedicated worker reads it as the page will (`LocalFontChecker`, `local-font-check-worker.ts`: parsing, its character map and HarfBuzz shaping); a file that fails there, crashes the worker or takes longer than `LOCAL_FONT_CHECK_TIMEOUT_MS` (10 s) is offered as unavailable and never parsed on the page. No upload API or document field receives bytes. Variable-only families are listed as unavailable; unsupported browsers explain the alternative.

After a reload, a board's families that no catalogue holds are offered once to `restoreLocalFonts` by the missing-fonts tracker. When the browser reports the `local-fonts` permission as already granted (`localFontPermission`, read without prompting), it lists the installed fonts and installs those families, so the owner's local text draws without opening the picker. Under `prompt` or `denied` it lists nothing and the missing-fonts notice shows. The Font field labels a family installed from this computer `… (on this computer)` (`isLocalFamily`, `DemandFonts.isLocal`); the stored value stays the plain family name.

A local family keeps every face: faces beyond weight and slant (Condensed, Display) are installed under their PostScript names. The text section's Face select (`panels/sections/text-face-row.tsx`) offers Regular and each installed named face of the shared family (`pageNamedFaces`, labelled by `faceLabel`), and shows only when the family has named faces or the text names one. Choosing a face writes the run's `postScriptName` as one command; Regular removes it.

A missing family keeps its stored name and renders with a category/name-based library fallback, retaining weight/slant where available. Arbitrary private family names have no shared classification metadata, so unknown names use the default sans. The inspector marks missing fonts. Opening their words asks for an available replacement; cancellation writes nothing, and replacement restyles the whole object in one undo step. Moving, resizing and other style changes remain available. A pending replacement is discarded if the document closes, permission changes, the object becomes locked, or the prompt is cancelled. A board that names missing fonts says so in the board's notices (`text-input/missing-fonts-notice.tsx`): which families, kept up to date incrementally from objects, overrides, variant presets and text styles (`missing-board-fonts.ts`), and what they are shown in. An editor's Replace… opens the board-wide replacement of the first missing family (`replaceMissingFont` canvas action, `engine/document-font-replacement.ts`): the chosen family replaces it on every text, override and unlocked text style naming it in one `replaceFontFamily` command, so one undo step; locked objects and the styles they name are left and the notice line says how many. Dismiss ignores those families on that board until the page reloads or another family goes missing.
