# @canvas/document

## Purpose

The board document: the `DocumentStore` interface over Yjs and its one implementation, `YjsDocumentStore`, with the codec that maps schema objects onto Yjs shared types, and the **command layer** on top of it: the only way the board changes, for people, tools and agents alike. Every command validates its whole input against the board and `@canvas/schema` first, then runs as one transaction carrying an `origin` (user, agent, undo, system). Z-order is a fractional-index key per object (`z`), generated here and compared by the schema's rule (`compareKeys`, `compareSiblings`), with the four order commands (bring to front, send to back, bring forward, send backward). On top of the commands, a per-user **undo history** scoped by origin: each user undoes and redoes only their own commands and those of agents they operate. Beneath them, a **reference repair** that runs after every remote update and every undo or redo, so references that concurrent deletes leave dangling are repaired the same way on every client. No React, no DOM, no network.

## Public API

- `searchableTextOf`, `SearchableText`, `SearchGroup`, `foldForSearch`, `searchWordsOf`, `matchesQuery`, `matchesFoldedQuery`, `SearchIndex`, `SearchHit`, `SearchOptions`, `DEFAULT_SEARCH_LIMIT`: Board search, pure: the text an object is found by (a sticky's or text object's text, a shape's or connector's label, a frame's name, grouped as stickies, text and sections); folding that ignores case and accents (Arabic and Hebrew marks too, not the kana voicing marks); a query matches when every word starts one of the text's words, or occurs anywhere for Chinese, Japanese and Korean; and an index built from a snapshot, kept current from change sets (reading only the ids they name), whose results come in group order with each one's page and section (nearest frame), optionally for one page, at most 200 unless asked.
- `createComponentCommand`, `createComponentInputSchema`, `CreateComponentPlan`, `CreateComponentResult`: Creates a board-local main at the selection bounds with children kept in place; optional `variantAxes` make it a variant set, with an empty preset for every value, and `variantPresets` (`{ "axis=value": { [childPath]: record } }`) fill them in the same command, each record checked as `setVariantPreset` checks one against the main as it will be.
- `createInstanceCommand`, `createInstanceInputSchema`, `CreateInstancePlan`, `CreateInstanceResult`: Places a main reference at a world point, with optional independent size and `overrides` (each path checked as `setInstanceOverride` checks it, same error codes), in one transaction and one undo step.
- `detachInstanceCommand`, `detachInstanceInputSchema`, `DetachInstancePlan`, `DetachInstanceResult`, `DetachClamp`: Materializes inherited content as a same-id frame, preserving attachments and nested instances; `idMap` maps each source path to its new child; a scaled instance's copies are baked, each value past its stored range clamped and listed in `clamped` (`DetachClamp`).
- `setInstanceOverrideCommand`, `setInstanceOverrideInputSchema`, `SetInstanceOverridePlan`, `SetInstanceOverrideResult`: Merges permitted content, text style, colour, image and visibility fields into one child-path LWW record; a `text` without `runs` clears stored runs, so the record stays valid; a `mainId` on a nested instance swaps its main, refused unless it is a live main in the slot's `swapOptions` (when set) that makes no cycle and stays within depth; paths follow each slot's effective main.
- `resolveOverridePath`, `overridePathInputSchema`, `overridePathError`, `MAX_OVERRIDE_PATH_INPUT`, `OverridePathResolution`, `ResolvedOverridePath`, `OverridePathRefusal`, `OverridePathRoot`: Override paths by child name as well as id: an id path as stored is kept; otherwise each step names a direct child of the current layer (the main, a frame, a group, or a nested instance's effective main; an unnamed instance by its main's name; a name may contain `/`, so every split is tried) and resolves to the id path stored, or `invalid-override-path` / `ambiguous-override-path`. `setInstanceOverride`, `resetInstanceOverrides`, `setVariantPreset`, `resetVariantPreset`, `createInstance` overrides and one-call presets take such paths and store ids; `setInstanceOverride` and `setVariantPreset` report the id path.
- `setSwapOptionsCommand`, `setSwapOptionsInputSchema`, `SetSwapOptionsPlan`, `SetSwapOptionsResult`: Sets the live mains a slot may be swapped to, or clears the list with `null`; an edit of the slot's main, never rewriting stored swaps.
- `resetInstanceOverridesCommand`, `resetInstanceOverridesInputSchema`, `ResetInstanceOverridesPlan`, `ResetInstanceOverridesResult`: Clears whole override maps, individual paths, or selected fields to resume inheritance; clearing `text` clears its `runs`.
- `setVariantAxesCommand`, `setVariantAxesInputSchema`, `SetVariantAxesPlan`: Sets a main's variant axes; `renames` carry its presets, its instances' selections and nested selections to new names, a removed value's preset goes and selections naming it are kept, `axes: null` removes variants; every axis value gets a preset map (`{}`) so first edits by two people merge. `variantPresets`, keyed by the new names, merge records into the presets in the same command; not with `axes: null`.
- `setVariantPresetCommand`, `setVariantPresetInputSchema`, `resetVariantPresetCommand`, `resetVariantPresetInputSchema`, `ResetVariantPresetPlan`, `ResetVariantPresetResult`, `SetVariantPresetPlan`, `SetVariantPresetResult`: Merge fields into, or reset, one axis value's preset at a path of the main, checked as an instance's override at that path would be; an emptied preset stays `{}`, and a reset reports the paths it changed. A record may move and size a child and patch an auto-layout container's layout; at the main's own id it holds only the variant's `width`, `height` and, for a main with auto-layout, an `autoLayout` patch. On an axis some preset sizes this way (`variantSizedAxes`), an instance that has not fixed the axis takes its variant's size, or the main's own, whenever its variant or the main's presets change, in the same undo step; resizing the instance fixes the axis (`isWidthFixed`, `isHeightFixed`). A child without a record follows its constraints into the variant's box.
- `setInstanceVariantCommand`, `setInstanceVariantInputSchema`, `SetInstanceVariantPlan`, `SetInstanceVariantResult`, `DroppedOverride`, `switchedOverrides`, `selectionErrors`: Switch an instance's variant (a value per axis, `null` for the default), dropping its own overrides of fields the old or new presets set at the same path (its text kept), and report the stored selection and the dropped fields; the rule and the selection check, shared with `createInstance`'s `variant`.
- `setConstraintsCommand`, `setConstraintsInputSchema`, `SetConstraintsResult`: Sets pin/stretch behavior on direct children of frames or mains, retaining omitted axes.
- `setAutoLayoutCommand`, `setAutoLayoutInputSchema`, `setLayoutChildCommand`, `setLayoutChildInputSchema`, `SetAutoLayoutResult`: Set or remove a frame's or main's live `autoLayout`, and how boxes sit in one (`layoutChild { fill }`); the containers are laid out in the same transaction; another type is refused `unsupported-type`.
- `patchAutoLayoutCommand`, `patchAutoLayoutInputSchema`: Change some fields of the auto-layout of frames and mains that have one, merged into each container's own, so one inspector edit across different layouts is one undo step; laid out in the same transaction; a container without one, or another type, is refused `unsupported-type`.
- `planRelayout(source, touched)`, `RelayoutSource`: The live auto-layout a change calls for: every auto-layout frame or main a touched object is, is in or was in, re-laid with `layOutStack` from its outermost auto-layout ancestor down, box children in stacking order, hugging containers sized to their content, and a hugging main's size given to its instances on unfixed axes. `runCommand` writes it with each command, judged and undone with it; the store's repair pass writes it with the system origin after merges, so clients converge. Pure.
- `BoardReferences.instancesOf(mainId)`: Incremental immutable reverse index of stored instances, including references to retained retired mains.

**Store**

- `DocumentStore`: The substrate boundary: `clientId` (the Yjs client id it writes under), `read`, `readPages` (the live pages), `readTokens` (the colour token table), `readTextStyles` and `readEffectStyles` (the named style tables, `NamedStyleReads`), `get`, `references`, `transact`, `subscribe`, `subscribeUpdates`, `encodeState` (full persistence), `encodeSyncState` (integrated history and pending deletes), `hasPendingStructs`, `encodeStateVector`, `applyUpdate` (`ApplyUpdateOptions.isSilent`: update listeners are not handed the update, a cache restore), optional `applyUpdateInSteps` (the same apply in three browser tasks, yielding between the scan, the Yjs apply and the repair), `setRepairMode`, `versionError` (the layout or schema refusal it hit, if any), `destroy`; `YjsDocumentStore` listens to Yjs's `update` event only while it has update listeners.
- `ApplyUpdateOptions`: How `applyUpdate` applies an update: `isSilent` leaves update listeners out of it (not its repairs), so the store encodes nothing for them.
- `ApplyUpdateInStepsOptions`: `ApplyUpdateOptions` plus the `yieldToBrowser` that `applyUpdateInSteps` awaits between its steps.
- `YjsDocumentStore`: The Yjs implementation; owns one `Y.Doc`. `new YjsDocumentStore({ clientId, repairMode })` accepts a deterministic test client id and an automatic repair mode (default `write`).
- `RunnableStore`, `StoreRun`, `StoreBusyError`, `StoreDestroyedError`, `RunStopRequest`, `RunStopReason`: One writer holding a `YjsDocumentStore` across browser tasks: `beginRun()` opens a run, and until `close()` every mutation of the store (`transact`, `applyUpdate`, `applyUpdateInSteps`, `setRepairMode`, any history's undo or redo) throws `StoreBusyError` before it changes anything, unless made inside the run's synchronous `enter`; reads stay allowed; `whenIdle()` resolves when no run holds the store, and rejects with `StoreDestroyedError` once it is destroyed. `isRunning` tells whether a run holds it; `requestStop(reason)` asks the open run to stop before its next part (`revoked`: write access lost; `inbound-backlog`: the collab client holds too many inbound updates), which then rejects with `RunStoppedError` whose `cause` is a `RunStopRequest`.
- `watchCommentPins`, `CommentPinChanges`: Tells which threads one of the client's own transactions took the last comment pin from, and which its undo or redo pinned again, so the app and the MCP server delete and restore the thread in the boards service.
- `syncCommentThreads`, `CommentThreadWrites`, `CommentThreadSync`: Runs a client's thread deletes and restores for its own pin changes (`watchCommentPins`), one thread's writes in order (a delete and the undo right after it reach the service in that order), with `settled()` to wait for them.
- `whenStoreIdle(store, work)`, `waitForStoreIdle(store)`, `isStoreRunning(store)`: Does a write once no stepped run holds the store: at once when none does, else when it is idle (again if another run began), nothing when it is destroyed first; a forwarding page store waits on the store it writes through. What the app's self-firing writers (size followers, font replacement, image insert, comment pins) write through; `waitForStoreIdle` is the same wait as a promise (`false` when the store is destroyed first: the cache restore), and `isStoreRunning` tells whether a run holds it now (a text session holds its edits).
- `subscribeStoreRuns(store, listener)`, `storeRunState(store)`, `StoreRunState`, `StoreRunProgress`: Who follows a store's stepped runs: told when one opens, on each `StoreRun.progress(done, total)` report (`startRun` and `history.startRestore` report each committed part), and when it closes; the state now, read right after subscribing. A page store follows its board; a store with no runs never tells. What the app's busy indicator follows.
- `RepairMode`, `YjsDocumentStoreOptions`: `'write'` (automatic repairs write document history) or `'read-only'` (a viewer's or commenter's store: the same repairs are applied to the readable view only, nothing is written or left pending); and the settings of a new store (`clientId`, `repairMode`). `setRepairMode(mode)` switches a live store when the relay's role answer arrives.
- `OBJECTS_MAP_NAME`: `'objects'`, the name of the document's top-level `Y.Map` of objects.
- `PAGES_MAP_NAME`, `PageCreation`: `'pages'`, the name of the document's top-level `Y.Map` of pages (layout 4), and who creates a page and when (`DocumentTransaction.setPage`).
- `DocumentTransaction`: The typed write surface of one transaction: objects, text and vector-network edits, the pages (`pages()`, `setPage`, `deletePage`) and the colour tokens (`tokens()`, `setToken`, `deleteToken`).
- `TOKENS_MAP_NAME`, `TOKEN_FIELDS`, `tokenKey(id, field)`, `parseTokenKey(key)`, `ParsedTokenKey`, `TokenField`, `TokenIdentity`, `readTokens(map)`: `'tokens'`, the document's top-level `Y.Map` of colour tokens (layout 9), its `<id>.identity|name|light|dark` keys, an identity (`{ builtin, createdBy, createdAt }`) and reading the table from the map.
- `TokenWrite`, `TokenCreation`: A token as a command writes it (`id`, `name`, `light`, `dark`) and who creates an entry and when (`DocumentTransaction.setToken`).
- `setColorTokenCommand`, `setColorTokenInputSchema`, `SetColorTokenPlan`, `SetColorTokenResult`: Creates a custom colour token with a fresh id (`{ name, light, dark }`) or sets a token's name and values (`id` given; a built-in keeps its name); refuses `missing-token`, `duplicate-token-name`, `too-many-tokens` (64) and an agent's `not-own-token`. Registered as `setColorToken`.
- `createObjectsWithTokensCommand`, `createObjectsWithTokensInputSchema`, `CreateObjectsWithTokensInput`, `CreateObjectsWithTokensResult`, `CreateObjectsWithTokensPlan`, `TokenItemResult`, `MAX_TOKEN_ITEMS`: `createObjects` with `tokens`, 1 to `MAX_TOKEN_ITEMS` (100) `setColorToken` inputs written first, in order, each checked against the board and the items before it, so objects may name the new tokens by the ids in `newTokenIds`; one transaction and one undo step, refused as a whole with a token item's errors under `['tokens', index]`.
- `renameColorTokenCommand`, `renameColorTokenInputSchema`, `RenameColorTokenPlan`, `RenameColorTokenResult`: Sets a custom token's name, its `.name` key alone; built-ins refuse (`builtin-token`). Registered as `renameColorToken`.
- `deleteColorTokenCommand`, `deleteColorTokenInputSchema`, `DeleteColorTokenResult`: Deletes a custom token; objects naming it draw as ink (`unknown-color-token`); built-ins refuse. Registered as `deleteColorToken`.
- `resetColorTokenCommand`, `resetColorTokenInputSchema`, `ResetColorTokenPlan`, `ResetColorTokenResult`: Restores a built-in token's defaults by erasing its entry. Registered as `resetColorToken`.
- `setBoardTimerCommand`, `setBoardTimerInputSchema`, `SetBoardTimerPlan`, `SetBoardTimerResult`: Applies a timer action (`start`, `pause`, `resume`, `reset`, `set-duration`, `end`) at a moment by the relay's clock (`serverNowMs`) and writes the board timer whole; under the system origin it records `actor` as who acted. An action that does not apply writes nothing; a `start` for a missing section is refused (`missing-object`). Never undone. Registered as `setBoardTimer`.
- `FACILITATION_MAP_NAME`, `BOARD_TIMER_KEY`, `readBoardTimer(map)`, `BoardTimerView`: `'facilitation'`, the document's top-level `Y.Map` of facilitation state, its `timer` key (the board timer as one plain value), reading it (an invalid value reads as none), and `DocumentStore.boardTimer`, the timer as of the last transaction with its change listeners.
- `STICKY_AUTHORS_KEY`, `readStickyAuthors(map)`, `StickyAuthorsView`, `setStickyAuthorsCommand`, `setStickyAuthorsInputSchema`, `SetStickyAuthorsPlan`, `SetStickyAuthorsResult`: The board's "Show authors on stickies" setting: the facilitation map's `stickyAuthors` key (one plain boolean; absent or anything else reads as false), `DocumentStore.stickyAuthors` with its change listeners, `DocumentTransaction.setStickyAuthors`, and the `setStickyAuthors` command (`{ isShown }`, strict), outside every undo history; the relay door takes the key only as a boolean.
- `replaceFontFamilyCommand`, `replaceFontFamilyInputSchema`, `ReplaceFontFamilyInput`, `ReplaceFontFamilyPlan`, `ReplaceFontFamilyResult`, `SkippedFontUse`: Replace a font family everywhere a board names it (runs of texts, stickies and labels, instance override records, variant presets, text styles), only the family changing, with the caller's `measured` boxes, in one undo step; locked objects and, for an agent, objects in mains and text styles it did not create are left and reported under `skipped`, and so is a text style a left object names (`bound-by-left-object`: rewritten, peers' binding repair would change that object), the runs it does change detached from such styles; refuses the same family as both. Registered as `replaceFontFamily`.
- `setTextStyleCommand`, `setTextStyleInputSchema`, `setEffectStyleCommand`, `setEffectStyleInputSchema`, `SetNamedStylePlan`, `SetNamedStyleResult`, `MeasuredBox`, `BoundRange`: Create a named text style (a run's typography, no colour) or effect style (1 to 8 shadow layers) with a fresh id, or set one's name and value and rewrite its values on every run or shape and frame naming it, on every page and in mains, with the caller's `measured` text boxes, in one undo step; refuse `missing-style`, `duplicate-style-name` (case-blind), `too-many-styles` (64 per kind) and an agent's `not-own-style`. Registered as `setTextStyle` and `setEffectStyle`.
- `createObjectsWithStylesCommand`, `createObjectsWithStylesInputSchema`, `CreateObjectsWithStylesInput`, `CreateObjectsWithStylesResult`, `CreateObjectsWithStylesPlan`, `StyleItemResult`: `createObjectsWithTokens` (tokens optional) with `textStyles` and `effectStyles`, 1 to 100 `setTextStyle` and `setEffectStyle` inputs each, written first, in order, each checked against the board and the items before it, so objects may name the new styles by the ids in `newTextStyleIds` and `newEffectStyleIds`; one transaction and one undo step, refused as a whole with a style item's errors under `['textStyles' | 'effectStyles', index]`.
- `deleteTextStyleCommand`, `deleteEffectStyleCommand`, `deleteNamedStyleInputSchema`, `DeleteNamedStylePlan`, `DeleteNamedStyleResult`: Delete a named style, detaching everything naming it (its values stay), in one undo step; refuse `missing-style` and an agent's `not-own-style`. Registered as `deleteTextStyle` and `deleteEffectStyle`.
- `TEXT_STYLES_MAP_NAME`, `EFFECT_STYLES_MAP_NAME`, `STYLE_MAP_NAMES`, `STYLE_FIELDS`, `styleKey(id, field)`, `parseStyleKey(key)`, `readStyles(map, kind)`, `ParsedStyleKey`, `StyleField`, `StyleIdentity`, `StyleKind`, `StyleEntry`, `StyleTable`, `StyleWrite`, `StyleCreation`: The stored layout of the named styles (layout 16): two top-level maps, three keys per style (`<id>.identity`, `<id>.name`, `<id>.value`), read tolerantly, sorted by id.
- `NamedStyleReads`, `NamedStyleWrites`, `NamedStyleChanges`, `TextStylePatch`: The named styles' part of `DocumentStore` (`readTextStyles`, `readEffectStyles`), `DocumentTransaction` (`namedStyles`, `setNamedStyle`, `deleteNamedStyle`) and `ChangeSet` (`textStyles`, `effectStyles`: the ids changed); a text patch whose `textStyleId: null` detaches a range from its style (`formatText`).
- `ObjectPatch`: The fields a `patchObject` may change (any field except `id` and `type`).
- `ObjectFieldName`: Every field name of any object type.
- `ObjectFieldValue<K>`: The value types field `K` has across the object types that have it.
- `BoardSnapshot`: An immutable board (`Board` from the schema) plus `pages` (the live pages in page order, the virtual Page 1 when none is stored), `tokens` (the colour token table, always set by a store) and `issues`: the entries that could not be read, the network members a read hid from a path it shows, and the members of a stored parent cycle it shows re-rooted.
- `ChangeSet`: What one transaction changed: created, updated and deleted ids, the pages whose keys changed (`pages`, when any), the colour tokens whose keys changed (`tokens`, when any), its origin, local or remote.
- `DocumentUpdate`: One transaction's Yjs update bytes with its origin, for the sync client and persistence.
- `BoardReferences`: Read-only reverse indexes: children by parent (and the top child, `topChildOf`), connectors by target, comments by anchor.
- `DocumentWriteError`: Thrown by a write that fails schema validation; carries the schema's `BoardIssue`s.
- `ValidationIssue`: The shape of a validation issue the error is built from.
- `DecodeIssue`: An object-map entry the snapshot could not read, or a network member it hid (then with `member`, the member's id, and `field` its list), and why.
- `DECODE_ISSUE_CODES`: `not-a-map`, `unknown-type`, `missing-field`, `malformed-field`, `id-mismatch` (an unreadable entry); `hidden-segment`, `stray-vertex` (a hidden member); `parent-cycle` (an object on a stored parent cycle, shown at the root until the repair writes it there).
- `isParentCycleIssue(issue)`: Whether an issue names a stored cycle shown broken, rather than an unreadable object or hidden member.
- `isHiddenMemberIssue(issue)`: Whether an issue names a hidden network member (`hidden-segment`, `stray-vertex`) rather than an unreadable entry.
- `DecodeIssueCode`: One of `DECODE_ISSUE_CODES`.

**Commands**

- `batchCommand(command, key)`, `MAX_BATCH_ITEMS`, `BatchPlan`: A command that runs a single-item command over `{ [key]: item[] }`, 1 to 100 items: each planned against the board with the earlier items' writes laid over it, all applied in one transaction and one undo step (each object and token written once), results in order under `key`; any item's refusal refuses the batch, its error paths starting `[key, index]`; items that create, delete or reparent objects are refused.
- `runCommand(store, origin, command, input, environment, options?)`: Parses, validates against the board, then applies in one transaction (a plan the command splits: one transaction per part, one undo step); returns the result and change set, or the errors.
- `startRun(store, origin, command, input, environment, options)`, `StartRunOptions`, `RunReport`, `CommandRefusal`, `RunStoppedError`: A stepped run (no caller yet): plans and validates as `runCommand` does, splits into parts of at most `maxWrites` planned writes, and applies the first part in the calling task and each later one after `yieldToBrowser`, holding the store (`StoreRun`) and one undo step throughout; page listeners hear each part in its own task; a refusal is returned synchronously, an applied run resolves with its report (`parts`, `committedParts`, `slowestPartMs`, `isOverBudget`), a stopped one rejects with `RunStoppedError` (`committedParts`, `plannedParts`, `changes`, `cause`).
- `RunRefusedError`, `StagedPlanning`: A staged plan (`StartRunOptions.isPlanStaged`): `startRun` opens the run first, then parses and validates the command a stage at a time (`Command.planInStages`, else in one stage), yielding between stages; a refusal rejects as `RunRefusedError` (`errors`), a stop or rejected yield while planning as `RunStoppedError` with no part and no `plannedParts`, a destroy as `StoreDestroyedError`; the new objects the plan validated whole are written without validating them again.
- `CommandEnvironment`: The injected `clock` (ms) and `createId`, so tests are deterministic.
- `RunCommandOptions`: `removableUnder`, the agents whose component mains an agent's command may remove objects under (its operator's agents); every other write under another principal's main stays `not-own-main`.
- `CommandOutcome<Result>`: `{ status: 'applied', result, changes }` or `{ status: 'rejected', errors }`.
- `previewCommand(board, origin, command, input, environment)`, `CommandPreview`: What a command would write, without writing: parses, validates and records `apply` with the live auto-layout it calls for, as `runCommand` writes it (`{ status: 'planned', written }`, each object whole by id, `null` for a deletion), the board's bound not judged; the sync fuzz's model of the bound judges it itself.
- `worldBoxOf(source, object)`, `WorldBox`: Where an object is on the board: its axis-aligned box in the board's frame through its chain of parents (rotation applied; a line's or path's points, a path's handle control points, a connector's free ends, and its own origin, so an object with no geometry of its own is where it is placed), or `unplaceable` (a parent cycle, a number that is not finite or overflows). The one function the command layer, the select tool's far test and the fuzz's model measure with; a relay check calls it on its board before and after an update.
- `judgeExtents(before, after)`, `ExtentVerdict` (`ExtentsWithin`, `ExtentsOutward`, `PlaceLost`): Rule 1 of the bound: each extent obeys `|after| <= max(B, |before|) × (1 + BOUND_SLACK)`; a new object, or one that had no place, is held to B; `outward` names the extents, `unplaceable` an object that could be placed and would not be.
- `BOUND_SLACK`: The rule's relative slack, 2^-40 (a thousandth of a unit at B): the rounding of a round trip through a turned frame can leave an extent an ulp further out, which must not refuse an inward move.
- `isPastBound(where)`: Whether a `WorldBox` has an extent past ±`BOARD_BOUND` or cannot be worked out.
- `isFarObject(source, id)`: Rule 5: an object is far when its box, or a descendant's, is past the bound or cannot be worked out; storing a number past B does not make it far. The select tool and the fuzz use it.
- `worldBoundViolations(before, after, changed)`, `WorldBoundViolation`: The bound decided from two states of a board alone: every changed object and every descendant it carries (top-down, O(1) each), and each value with a limit (`findValueLimitIssues`); what `runCommand` refuses on, and what a relay would call.
- `boxSourceOf(reader)`, `overlaySource(base, written)`, `BoxSource`: A board as the bound reads it (`get`, `childrenOf`): a store, or a board with a command's writes laid over it.
- `COMMANDS`, `CommandName`, `CommandInput`, `CommandResult`, `findCommand(name)`: The registry: every command by name, for the MCP server, the headless client and the SDK, with each command's input (before parsing) and result types by name.
- `Command`, `AnyCommand`: A command: `name`, `description`, `input` (Zod), `validate(context, input)` → plan or errors, `apply(transaction, input, plan)` → result; `isPlacePreserving` for one that only re-expresses or detaches (`group`, `ungroup`, `deleteObjects`), whose result the bound does not judge; optional `split(plan, options?)` → `CommandParts` (`parts`, `result`) for a plan too large for one transaction, bounded by `SplitOptions.maxWrites` when given.
- `CommandContext`, `BoardReader`, `CommandValidation`: What `validate` reads (board, origin, time, id generator; the board's pages through the optional `readPages`, its colour tokens through the optional `readTokens`, and where a new root object goes through the optional `defaultPageId`, a page view's page shown) and returns.
- `CommandError`, `CommandErrorCode`, `COMMAND_ERROR_CODES`: A structured rejection: code, object id, path, message.
- `createObjectCommand`, `createObjectInputSchema`: Creates one object of any type; fills in id, `z`, `createdBy`, timestamps.
- `createObjectsCommand`, `createObjectsInputSchema`: Creates several objects in one transaction (a paste): fresh ids, references between the listed objects remapped, stacked on top of the target parent in input order. Every transaction writes referents before referrers, whatever the input order; past `MAX_OBJECTS_PER_TRANSACTION` (1,000) objects, several transactions of at most that many, each referring only to objects already written, one undo step. A listed main's inline `variantPresets` are checked as `setVariantPreset` checks one, name paths resolved; a main named in `drawnDefaults` is a component set's, drawn as its default combination: each axis's first value's records written on it and its children, each other value given the field back unless its own record sets it (text, nested paths and fields a main cannot carry are refused).
- `importedObjectsInStackOrder(board)`, `ImportedObject`: An imported board's objects (`importBoard`) as `createObjectsCommand` takes them, bottom first, each with its document index: the fields the command sets, the stacking key and the page left out (shared by the MCP's `import_document` and the relay's template seed).
- `createFrameCommand`, `createFrameInputSchema`, `CreateFrameCommand`, `CreateFramePlan`, `CreateFrameResult`: Creates a frame and takes the listed objects into it in one transaction, one undo step (`{ frame, childIds }`, the frame tool): the frame as `createObject` creates one, each object converted into its frame as a reparenting move does (nothing moves on the board), stacked in the order the board painted them; refused for a missing, duplicate, locked or grouped object, one listed with its ancestor, or the frame's own ancestor. Registered as `createFrame`. Drawing a frame over 1,000 objects on a 10k board (`create-frame.bench.ts`; Node 22, Apple M1 Max): `validate` about 10 ms mean, the whole command about 57 ms mean (50 ms min), as moving the same 1,000 objects with `moveObjects` costs.
- `MAX_OBJECTS_PER_TRANSACTION`, `CommandParts`: The most objects one `createObjects` transaction writes: a count, not a byte bound, chosen so typical objects stay under the collab client's 1 MiB chunk (the large-board mix measures 676–686 bytes an object, so 1,000 come to about 0.65 MiB; 1,000 long notes can exceed it and then travel whole up to the client's 7 MiB single-transaction limit); the same count bounds `deleteObjects`; a split plan's parts and whole result.
- `SplitOptions`: How `Command.split` bounds its parts: `maxWrites`, the most planned writes per part (an object written costs two, its stamp included, a deletion or a side-table entry one); absent, `MAX_OBJECTS_PER_TRANSACTION` objects per part as before.
- `comparePaintOrder(board, first, second)`: Orders two objects by where the board paints them, whatever their parents (the clipboard's copy order).
- `hasListedAncestor(board, object, ids)`: Whether an ancestor of an object is among the given ids (a command's input, a selection); `board` needs only `get`.
- `newObjectSchema`, `NewObject`: The object `createObject` takes: any type, shared fields as the command defines them.
- `deleteObjectsCommand`, `deleteObjectsInputSchema`: Deletes objects with their descendants; detaches (or deletes) attached connectors, re-pins comments. Past 1,000 deletions, transactions of at most 1,000, referrers first, the detaching in the first, one undo step.

**Undo**

- `createHistory(store, principalId, options?)`: A user's undo history over a `YjsDocumentStore`: records the user's and their agents' commands, one step per command; a command written in parts (`Command.split`: large pastes, imports and deletes) is one step whose undo and redo run one part per transaction, the last part first (`undo-groups.ts`); the creation guard keeps, in a later-applied part, what an object an earlier part kept lies in, as one step would. `options.historyKey` makes a keyed history, which records only agent commands whose origin carries the same key; a history without one records only commands without a key. `options.operatedWriters` (`OperatedWriters`: `records(clientId)` and `owns(clientId)`) also records a remote update written under exactly one client id `records` accepts, as a step of its own: the changes of an agent the user operates that writes from another process (the hosted MCP server). - `generateObjectKeys(lower, upper, ids)`: One key per object between two keys, each ending in the object's tag, so concurrent placements in one gap stay distinct.
- `compareKeys(a, b)`: Orders keys by UTF-16 code units (the order of `z`); an `Array#sort` comparator. Re-exported from `@canvas/schema`.
- `isValidKey(key)`, `MAX_KEY_LENGTH`: The key rule: base-62, a head letter stating the integer length, no trailing `0` in the fraction, at most 512 characters. Re-exported from `@canvas/schema`.
- `sortedSiblings(store, parentId)`: A parent's children bottom to top: by `z`, ties by id. For the layers panel and scene segments.
- `keysAtFront(store, parentId, ids)`: Keys that stack new objects above every current child of a parent (through `topChildOf`: O(1) while the top only rises, one rescan after the top child moves down or away); `createObject` and `connect` use it.

**Commands**

- `bringToFrontCommand`, `sendToBackCommand`, `bringForwardCommand`, `sendBackwardCommand`: The four order commands, registered in `COMMANDS` as `bringToFront`, `sendToBack`, `bringForward`, `sendBackward`.
- `ReorderCommand`, `ReorderPlan`, `ReorderResult`: Their `Command` type; the plan (`parentId`, the new key of each moved object); the result (`movedIds`).
- `reorderInputSchema`: `{ ids }`: one or more object ids, each listed once, all children of one parent.

**Arrangement**

The pure planners behind align, distribute and tidy up, moved here from `@canvas/tools` so the app's arrange commands and the MCP server's `arrange` tool plan alike. They take axis-aligned boxes in one frame and return per-object moves; reading the selection into boxes is the caller's.

- `ArrangeBox`, `ArrangeMove`, `boundsOfBoxes(boxes)`: One object's axis-aligned box in the frame it is arranged in, and how far a planner moves it; the bounds of several boxes.
- `ALIGN_KINDS`, `AlignKind`, `planAlign(kind, boxes, anchor?)`: Left, centre, right, top, middle, bottom: each box's edge or centre to the anchor's (the boxes' bounds unless given).
- `DistributeAxis`, `planDistribute(axis, boxes)`: Equal gaps between neighbours ordered by centre, the outer two fixed; three boxes or more.
- `planTidy(boxes)`: A grid of the boxes' reading-order rows, columns as wide as their widest box, spaced by the median gap now (at least 0).
- `copySelection(board, ids)`: The board a copy makes of a selection: the objects with their descendants, roots moved to the root where they are on the board, connector ends on objects not copied freed, comments left out (moved from the app's clipboard).
- `countCopied(board, ids)`: How many objects `copySelection` would copy, counted from ids without materializing anything (the duplicate limit is checked before the copy).
- `planPaste(board, at, offset?)`, `PASTE_OFFSET`, `inParentFrame(objects, parentToBoard)`, `inStackingOrder(board, children?)`: A copied board as `createObjects` lists it, centred on a point or moved by an offset (16 world units by default); top-level objects re-expressed in a parent's frame; a board's objects parents first, siblings bottom first.
- `planDuplicate(board, ids, offset?)`, `DuplicatePlan`: A duplicate (mod+d, and the MCP `duplicate` tool): the objects to create and their parent, the originals' shared parent or the root.

## Design notes

### The Yjs mapping (`src/codec/`)

The rules live in one place: `object-layout.ts` derives each type's layout from its schema, and `object-codec.ts` (`toYjs`, `writeObject`) and `object-reader.ts` (`fromYjs`, re-exported by `object-codec.ts`) apply it. Since objects are stored in a **grouped-field layout**: Yjs spends one item, about 400 bytes of heap, per key of a `Y.Map`, so the fields that are always written together share one plain value, and only the fields that people edit concurrently for different reasons keep their own key.

| Key in the object's `Y.Map` | Holds                                                                                                                                                     | Written by                                                 | Concurrent edits                                                                        |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| The object                  | A `Y.Map` under its id in the top-level `objects` `Y.Map`                                                                                                 | `createObject`, `deleteObjects`                            | Different keys merge                                                                    |
| `identity`                  | `{ id, type, createdBy, createdAt }`                                                                                                                      | Creation only                                              | Never edited                                                                            |
| `placement`                 | `{ parentId, x, y, rotation }`: where the object sits, in its parent's frame                                                                              | Moves, reparents, rotations, (un)group, repair             | Last writer wins over the four: a concurrent reparent and move keep one placement whole |
| `size`                      | `{ width, height }` (boxed types)                                                                                                                         | Resizes                                                    | Last writer wins over the two                                                           |
| `style`                     | Every other plain field of the type: colours, strokes, fills, caps, routes, alignment, a frame's name, an image's asset and crop, a comment's thread, ... | `setStyle` and other restyles                              | Last writer wins over the group: two restyles of one object keep one                    |
| `z`, `locked`               | The value itself                                                                                                                                          | Reorder (and reparent, which puts the object on top), lock | Last writer wins per key; merge with every group                                        |
| `updatedAt`                 | The value itself                                                                                                                                          | Every command (`runCommand` stamps it)                     | Last writer wins                                                                        |
| `from`, `to`, `anchor`      | A connector's ends, a comment's anchor                                                                                                                    | Dragging an end, the reference repair                      | Last writer wins per key; merge with restyles                                           |
| `points.0`, `points.1`      | A line's start and end (the schema's `points`), one key each (`codec/pair-codec.ts`)                                                                      | `setLinePoints` (one end), resizes and rotations of groups | Last writer wins per end: drags of different ends both stay                             |
| `text` + `emptyTextStyle`   | Text and sticky bodies: a `Y.Text` whose characters carry the style fields that differ from `ATTRIBUTE_BASE_STYLE`, and the style of empty text           | `setTextRuns`, the text calls                              | Characters merge; different style fields on one range both apply                        |
| `label`                     | `null`, or a nested `Y.Map` with the same `text` + `emptyTextStyle`                                                                                       | `setTextRuns`, `connect`                                   | As text                                                                                 |
| `vertices`, `segments`      | A path's vector network: a `Y.Map` from member id to `[order, member]`                                                                                    | The vertex and segment calls                               | Different members merge; one member keeps one writer whole                              |

- **Merge semantics.** A group is one last-writer-wins value: two people moving and rotating one object at once keep one of the two, and two restyles of different fields of one object keep one restyle whole (the per-field layout kept both). A shape's appearance is one such group: one person changing its kind while another changes its fill converge on one of the two whole styles, not a mix (`set-style.sync.test.ts` asserts convergence only); giving a shape's style fields keys of their own would be a stored layout change (version 3) with a memory cost, left to the owner. A move and a recolour, a restyle and a text edit, a reorder and a resize, a lock and anything else merge, because they are different keys (`store/grouped-layout.sync.test.ts`).
- **Placement is one group.** `parentId`, `x`, `y` and `rotation` are written whole by every command that changes any of them (a move, a reparent, a rotation, `group`, `ungroup`, the reference repair): `writeObject` writes a group whenever one of its fields changed. The position is in the parent's frame, so a reparent's position and a concurrent move's belong to different frames, and mixing one's `parentId` with the other's position moved the object by the offset between the frames. Now a concurrent reparent and move, two reparents into different frames, or the repair and a user's move keep exactly one client's placement, and the object stays where that client put it (`commands/placement.sync.test.ts`, both client-id orders). When a user's placement wins over the repair's and names a parent that is gone, the repair runs again on the update that brought it, from the user's position. `z` keeps its own key, because a reorder writes it alone and must merge with a move; after two concurrent reparents the key can come from the other client, which changes only where the object stacks among its new siblings.
- **A line's ends are two keys (fix round 1).** A line's `points` is stored as `points.0` and `points.1` (a `pair` codec, `codec/pair-codec.ts`), as a connector keeps `from` and `to` apart: people drag one end at a time, often at once, and `setLinePoints` writes only the end it moves. Stored as one key, two people dragging different ends kept one person's pair, and when Ada dragged one end, Bob then dragged the other and Ada undid, her step counted as overwritten and was skipped, so the step before it, the line's creation, was undone and the line vanished. Now both ends stay, and undo returns Ada's end and leaves Bob's (`commands/set-line-points.sync.test.ts`, both client-id orders). **Boards stored before the split** (lines drawn before this change; stored before layout 2) hold the whole pair under `points`, in stored layout 1. This build reads layout 1 and writes layout 2 (fix round 2: the version was raised, see "Changing the stored layout" below), so its first write to such a board stamps it 2, and from then on the relay's layout gate refuses builds that read only 1, which would misread the board. A reader sees such a line exactly as it was: an end without its own key is read from the old pair. - **Runs from attributes, relative to a base style.** A `Y.Text` can only put attributes on characters, and Yjs spends two items per attribute change along a text (a start and an end marker), so five attributes on every run cost about 26 items per three-run text. A character therefore carries only the fields that differ from `ATTRIBUTE_BASE_STYLE` (Inter, 16, opaque black, 400, upright; `codec/style-attributes.ts`), and a restyle to a base value removes the attribute (`null`). The base is part of the stored format and never changes. `fromYjs` rebuilds `runs` from `Y.Text#toDelta()`, a missing attribute reading as the base, merging neighbouring ops with equal styles (Yjs can split a stretch at redundant format markers after concurrent formatting), so the schema's run invariant holds by construction. The style of empty text (the schema's single zero-length run) is stored beside the text as `emptyTextStyle`. It is rewritten when text is written, and when a delete empties the text (it becomes the style of the first deleted character, as in the prototype's `spliceRuns`).

The order of vertices and segments carries no meaning, but a decoded path keeps the order it was written in: members are read by their stored order, then id; kept members keep their order and new members are appended.

Networks are synced by member id. So `setObject` or `patchObject` with mostly unchanged values does not clobber concurrent edits to the keys it leaves alone.

Each store stamps the document's metadata (`meta/document-meta.ts`: the schema version and `DOCUMENT_LAYOUT_VERSION`, in the top-level map `meta` under `document`) right before its first write to the objects, in the writing transaction, so its stamp has a lower Yjs clock than every object it creates and any peer that holds one of its objects holds its stamp too (Yjs integrates each client's items in clock order). The stamp follows the store's Yjs client id: when Yjs gives the document a new id (it does on finding another client using it), the next write stamps again. A writer that creates objects through raw Yjs (a relay migration, an import tool) calls `stampDocument(doc)` before its first object, in the same transaction. Deleted stamps count, because every writer stamps the same key: Yjs keeps one of concurrent stamps by client id and deletes the others where they merge, and a relay can forward a peer's sync reply whose delete set removes that peer's losing stamp before the winning stamp arrives, so a reader can hold a writer's stamp only as a deleted item, or no current stamp at all, for a while (tested, as is the held-back case). The check reads only entries the update named and caches writers already seen, so a remote update costs nothing extra. - **Changing the stored layout (a rule for future changes).** A layout change is any change to what the codec _writes_ (`codec/`, `object-layout.ts`: a key added, removed, renamed, split or merged, a value's shape, a new shared type) that a reader of the previous layout would misread or drop; a new optional schema field that lands in an existing group (`style`, `size`) adds no key and is read by older builds, but it is still one: an older reader decodes only the group fields it knows and rewrites the whole group when it writes any of them (a resize, a restyle), erasing the new field, and only the layout gate stops a tab already open on an older build. To make one: (1) raise `DOCUMENT_LAYOUT_VERSION` and describe the new layout in its TSDoc, and when the portable shape changes too raise `@canvas/schema`'s `SCHEMA_VERSION` with its migration step, and add the offline cache's converter for the bump in `@canvas/collab`'s `DEFAULT_LAYOUT_CONVERTERS` (the identity when every older edit means the same; without one, unsent edits are reported to the person instead); (2) keep the previous layout in `READABLE_LAYOUT_VERSIONS` with a read fallback in the codec, so boards already stored stay readable (the first write stamps them with the new version), or drop it only with a migration the relay runs. A current client that only _reads_ a board never stamps it (a store stamps right before its first write to the objects), so builds that read only the older layout can still open that board until someone with the new build first edits it; (3) write only the new layout, and write an old board's values only where they change, so a concurrent writer of the other values keeps theirs; (4) update the tests that pin versions (the relay's health and gate tests, the collab, headless and e2e-sync tests, the deploy smoke test's `layoutVersions` cases) and this README, the relay's README and decision record 0001; (5) add a sync test of an old board edited by two clients, and an e2e-sync test that an old board opened and edited by this build is stamped with the new version and still readable (`layout-gate-relay.test.ts`). Deploy the relay before the app: the smoke test checks that the relay reads the app's layout.

- **Updates** are Yjs update format v1 (`encodeStateAsUpdate`, `applyUpdate`), the bytes the relay persists in `board_updates`. When an incoming update leaves held structs, the store gives their combined bytes one integration pass in the same remote transaction. Yjs 13.6.33 can retain stale missing-clock hints after merged deliveries even when all dependencies are already held. Genuine missing structs and delete sets remain pending until their dependencies arrive; nothing is discarded. `store/remote-update.test.ts` pins reduced in-memory seed 2354 and both kinds of genuine gap. **Atomic remote updates.** Yjs applies an update's delete set at once but holds back structs it cannot integrate yet, so a peer's change of a field (delete the old value, insert the new) used to leave the field empty while the new value waited: the object read as `missing-field` and dropped out, and honest commands on objects referring to it were refused (`missing-parent`, `missing-connector-target`) or measured in the wrong frame. The store now applies an update's structs first (the depth walk, `readUpdateShape`, also finds where its delete set starts) and then its deletions; while structs are pending, a deletion of the current value of a key inside an object (an object's field, a label's) is held (`store/held-deletes.ts`) until the replacement arrives, which removes the old value itself, or until nothing is pending, when the rest applies. Whole objects, text, network members and anything not yet delivered are deleted at once, as before; with nothing pending an update applies exactly as before. `encodeState` and `encodeSyncState` carry the held deletions like Yjs's pending ones, and a store loading such a state holds them again. A newly held deletion changes nothing in the document, so Yjs reports no update for it; `applyUpdate` reports it to the update listeners itself (`isLocal: false`, the update's origin), so the device cache logs it like any applied update and a store replaying the log holds it again (fix round 1: without it, a reopen before compaction brought the deleted value back once the missing update arrived; `packages/collab/src/cache/held-deletes-cache.test.ts`). The report goes to every listener even when one threw on the rest of the update, and the first error is rethrown afterwards as before (`applyAndReport`, fix round 2): the held deletions are recorded inside the transaction, before Yjs calls any observer or listener, so a throwing listener can neither skip them nor split the update's content from its deletions. Cost on a 50k-object, 30 MiB state with 50k deleted values (one run on an M-series Mac): splitting copies the bytes in about 4 ms, the walk that finds the delete set is the existing depth check (about 220 ms, unchanged), and applying structs then deletions takes the same time as one `Y.applyUpdate` (1.1–1.4 s against 1.2–1.3 s); only when structs are pending does sorting the 50k deleted ranges add about 200–300 ms. `src/commands/partly-delivered.sync.test.ts` gives Bob a peer's second update before its first: the frame, connector target and turned group read as they were, `setConnectorEnd` applies, and a move inside the turned group lands where it does on the whole board.

### Validation and trust

Every transaction write validates before it touches the document: a new object whole against `boardObjectSchema`; a write to an existing object (`setObject` over it, `patchObject`) field by field, judging only what it changes ("Field-scoped validation" under the command layer below); text styles and style patches against `textStyleSchema`, network members against `vertexSchema`/`segmentSchema` with `findNetworkIssues` on the resulting network. Text runs must also split text between characters. Yjs stores each run's characters as a separate string and encodes a lone surrogate as U+FFFD, so a run boundary inside a surrogate pair would leave the writer with the emoji and every peer with two replacement characters, and they would never converge. The schema's run invariant carries this rule (`findRunIssues`), so `boardObjectSchema` and every command input that holds runs (`setTextRuns`, `connect`'s label) already refuse such runs, the latter as `invalid-input`. `setObject` and `patchObject` check the boundaries again after the schema (`findSplitCharacterIssues` in `store/object-validation.ts`, over the schema's `findRunsSplittingCharacters`), in text and sticky bodies and in labels, as defence in depth; the text calls guard their ranges with the schema's `isCharacterBoundary`.

Invalid values throw `DocumentWriteError` (schema `BoardIssue`s, code `invalid-object`); a missing object or a bad range throws `RangeError`. The failing call writes nothing. Yjs has no rollback, though, so writes made earlier in the same transaction stay, and are committed and broadcast to listeners and peers when the transaction ends. Validating a whole command before its first write is the command layer's job (below); it validates each object it will write with the same function the writes use (`store/object-validation.ts`).

`applyUpdate` does **not** re-validate objects. CRDT updates are trusted at this layer; the relay authenticates peers, and validating 50k objects on load would cost seconds. What `fromYjs` cannot read at all (an unknown `type` from a newer peer, a missing field, a wrong shared type, an id that is not its key) is left out of the snapshot and reported in `BoardSnapshot#issues`, never thrown. Before freezing a decoded object, the codec rejects a shared Yjs type, subdocument, binary view, array buffer, `bigint` or container JavaScript cannot convert reachable through a plain field, including unknown nested properties (a member of a network too), as `malformed-field`. What it refuses is what code would throw on: a `bigint` (JSON cannot write it, arithmetic with a number throws) and a container with an own `toString`, `valueOf`, `toJSON`, `constructor`, `__proto__` or `then`, or a prototype other than `Object.prototype` (`Array.prototype` for an array), which lib0 carries (`{"toString": 1}`, `{"__proto__": null}`) and on which `<`, `+`, `String()` and template literals throw (`compareSiblings` on a peer's `z` threw out of every client's next read). The own keys are checked without reading them. The codec then checks each known field's top-level kind against its schema (`codec/field-kinds.ts`: string, number, boolean, null, array, object, from the Zod definition; a schema it does not understand accepts anything): a number field holding an object or a string, `z` holding an array, a nullable string holding a number are `malformed-field` (`x: expected a number`), so no code compares, adds, formats or calls a method on a value of the wrong kind. It stops at the top level: ranges and the elements of an array or fields of a nested object are the schema's, which the reader does not run. It leaves the stored value untouched, so the rest of the board remains usable. Intended shared text, labels and network maps are decoded before this check. A value a peer chose is worded in a message only through `describeValue` (`codec/describe-value.ts`, package-internal): lib0 carries more than JSON does (a `bigint`, binary data, an object with no prototype), so `JSON.stringify` or `String` on it can throw, and a message built from it can be as long as the peer likes (a `bigint` in an object's `id` or `type` threw out of `fromYjs`, and `ObjectCache.flush` then rethrew on every later read and transaction of every client). `describeValue` never throws and is bounded: a string is quoted and cut to 48 characters (never inside a surrogate pair; C1 controls, U+2028, U+2029 and bidi controls are shown as `\uXXXX`, since a description reaches logs), a shared type, binary data or an object is named by its kind and never read. `describeId` gives a string id as it is and describes anything else. `describeJson` is the same for a value that is normally small JSON (the stored layout stamp in `DocumentVersionError`'s message: the JSON text, cut to 200 characters, when it can be written, else what `describeValue` says), so a `bigint` stamp is a `DocumentVersionError` and not a `TypeError` out of `applyUpdate`. Decoded objects are frozen by an iterative walk (`codec/deep-freeze.ts`) with no depth cap, so a peer's deeply nested value cannot overflow the stack on a read. A missing or malformed text attribute reads as the base style's value. Concurrent merges can produce states that no single write could: for example, a segment that ends at a vertex another client deleted. A path's network is read with those members left out, each reported in `BoardSnapshot#issues` as `hidden-segment` or `stray-vertex` with the path's id and the member's ("Vector networks" under "Reference repair" below); other such states pass through. The sync fuzz harness found converged boards that break `validateBoard` identically on every client: an object whose parent was deleted concurrently (`missing-parent`), or a connector or comment whose target was (`missing-connector-target`, `missing-comment-anchor`); 51 violations in 17 of 20 boards of the default run. The store now repairs those after every applied update ("Reference repair" below), and the harness fails any converged board that still breaks a rule.

### Refusals and throws

A command never throws for a state a peer can cause. Remote updates are not validated object by object, so the board can hold what no single write could: a segment whose vertex has not been delivered yet (the read hides it and reports it as `hidden-segment`), a duplicate, a stray vertex, an object with a value the schema rejects. `validate` reads the board as `store.get` shows it and checks each object it will write with the store's own rule, so the result is one of two things, never a throw:

- **A refusal**, `{ status: 'rejected', errors }` with nothing written (`encodeState()` byte-identical), for everything the input or the board can cause: a malformed input, a missing or duplicate id, a locked object, a type the command does not take, and `invalid-object` for a field the command would write that the schema rejects, or a new value the relay's door would refuse. A field a peer left invalid refuses only a command that writes it; a command that leaves it alone applies and keeps it as stored, except a size the door refuses, which refuses every write of the size group ("Field-scoped validation" below). `bringToFront` and the other reorders and `setLocked` used to skip the check and threw `DocumentWriteError` from `apply`; until every command but a delete refused an object with any invalid field.
- **A success that leaves the hidden member alone**, for a command with nothing to do with the network (reorder, move, rotate, restyle, lock, group, ungroup, duplicate): it works on the path as the read shows it, and a write keeps every member the read hid, so the segment whose vertex arrives a moment later is whole again on every client. A duplicate copies what the read showed, so it holds no hidden member. `editNetwork` works on the shown path too: it cannot name a hidden segment or join a vertex that is not there (a refusal), and deletes a hidden segment only when its own edit makes it unable to come back (`codec/network-collection.ts`). `deleteObjects` deletes the path with its members.

What still throws is a bug of the caller, never a state a peer causes: `DocumentWriteError` from a direct write on a transaction (`setObject`, `patchObject`, `setVertex`, `setSegment`, the text calls) that the caller did not validate first (from inside a command's `apply` it would mean `validate` missed a check), `RangeError` (a missing or unreadable object, a range outside the text, a patch that changes `id` or `type`, an invalid origin, a clock that is not whole milliseconds), `Error` (a transaction that has ended, transactions nested, one started from a listener) and `DocumentVersionError` from `applyUpdate` (a board this build cannot read, which the sync client handles). The reference repair skips a write the store refuses (`DocumentWriteError`) by design. The read never throws for what a peer stored: it reports it in `BoardSnapshot#issues`.

### The board bound

`BOARD_BOUND` is B = 2^30 (1,073,741,824) world units. **It bounds where objects are on the board, not the numbers they store.** Seven rules:

1. **World geometry.** For every object a command changes or carries (the objects it writes, and their descendants when a parent moves, turns or scales), take its axis-aligned box in the board's frame before and after the command: rotation applied through its chain of parents; for a line or a path the box of its points and vertices (a path's handle control points too, a connector's free ends; a group has none of its own, its members are judged); and the object's own origin, counted as one of its points, so placement is bounded regardless of extent (an empty group moved by 1e308 is refused; before, it stored x = 1e308). For each of the four extents (min x, max x, min y, max y): `|after| <= max(B, |before|)`, up to rounding: the limit is widened by `BOUND_SLACK` = 2^-40 of itself, about a thousandth of a unit at B, because a move or turn inside a turned frame goes through the frame's transform and back and can leave an unmoved or inward extent an ulp further out (the exact comparison refused about one in eight inward moves of a far object in a turned frame, and of moves to (B, y) into one). That is the whole test (`worldBoxOf`, `judgeExtents`); a real step outward, even a thousandth of a unit, is refused. An extent inside the bound may go anywhere inside it; an extent past the bound may stay or come inward, never go further out. Sizes need no rule of their own: a size that grows moves an extent. A new object is held to B itself. Example: an object whose right edge is at B + 400 may be moved left, or up and down, and may not be moved one unit right; a box at B - 100 wide 100 cannot be made 1e6 wide; a turn that carries a corner past B is refused.
2. **Stored numbers are not bounded**, only finite. A member of a group of two frames at -B and +B honestly stores about 2B: `group` re-expresses the frame at +B as 2B from a group at -B, and its box on the board is inside the bound, so it moves, pastes, duplicates and imports like any other.
3. **Values that are not positions** have limits of their own, the same on every way in (`findValueLimitIssues` in `@canvas/schema`): a rotation within ±B radians (a command normalises every rotation it computes into (−π, π]), a shape's corner radius, an image's natural size and the whole source image behind its crop at most B, a comment pin's offset from its object within ±B; stroke width and text size are held by the schema. `createObject`, `createObjects` (so paste and duplicate), any command that changes one, and `importBoard` refuse exactly the same: a value may stay where it is or come down, never be raised past its limit.
4. **Derived inputs never refuse.** A move's `by` and `to`, a turn's pivot, a resize's `origin`, a line end, a connector's free end are plain finite points (`pointSchema`): the select tool computes pivots and origins from stored geometry, and what is judged is the result.
5. **Far** means the object's box, or the box of anything it carries, has an extent past B, or a number it needs is not finite, or its box cannot be worked out (a parent cycle, an ancestor that is not finite). `isFarObject` decides it, for the select tool and the sync fuzz alike. Storing a number past B does not make an object far.
6. **The select tool** skips far objects in a transform and says so once (`FarSkip` names them); pivot, origin and handles come from the near ones. See `@canvas/tools`.
7. **An honest person is never stuck.** A far object can always be deleted (`deleteObjects` keeps every place, so it is not judged), and moved `to` a board position inside the bound, which rule 1 allows since its box comes inward. When its parent's frame cannot hold that point (an ancestor so far away that its numbers swallow the point, or not finite: `canHoldPoint`), the move takes it out onto the root (or into the frame it names) and says so in `rerootedIds`; no `parentId: null` is needed.

**Concurrency.** The rule is on each command, judged on the board its client sees. Two clients' commands, each within the bound, can merge past it (a move and a resize of one box write different stored groups and both survive: `world-bound.sync.test.ts`); the object is then far, and may stay or come in. A relay judging each update the same way would not stop that either.

**Where it is judged.** `runCommand` judges the result, not the input: after `validate` it records what `apply` would write (`RecordingTransaction`, which writes nothing), lays it over the board (`overlaySource`) and compares every written object and every descendant it carries, before and after (`worldBoundViolations`): one walk up the chain of parents per written object, then its descendants top-down in O(1) each (two transforms, two boxes) when its place changed, so a move of a group carrying 10,000 descendants judges 10,000 boxes (`resize-objects.bench.ts`). An object whose geometry and place did not change is skipped. A violation refuses the whole command as `invalid-input`, naming the object (an extent's error has an empty path; a value's names its field). `group`, `ungroup` and `deleteObjects` keep every object where it is and only re-express or detach (`isPlacePreserving`), so they are not judged: their re-expression can differ from the stored place by rounding, which the exact rule would otherwise refuse. The rule is decidable from stored states alone, without knowing which fields a command drove: a relay checking a peer's update would apply it to a scratch copy and call `worldBoundViolations(before, after, changedIds)` on `boxSourceOf` of both. The slack is the same everywhere the rule is applied (the command layer, the sync fuzz's model, `isPastBound` for far-ness, a relay), so they agree to the ulp; it also covers a relay judging the rounding of a `group`'s or `ungroup`'s re-expression.

**The store does not enforce the bound**, only finiteness of what commands write (`validateObject` refuses NaN and the infinities) and the drawable ranges of the relay's door (a new size past 2^32 or rotation past float32). Values a command derives from stored data are stored as computed when finite; only what is not finite is clamped (`finiteCoordinate`, `finiteGeometry`; `normalizeAngle` turns a non-finite angle into 0). The reference repair re-roots orphans the same way, and a composed rotation past float32 is wrapped into (−π, π] (written as summed, the door refused it). A move `by`, or a turn about its own origin, of an object whose place is far (its own position or an ancestor's past the bound, `isFarPlaced`) adds the displacement in the parent's frame instead of going through the board frame, which would cancel a far position away; with no far value on the board both are bit-identical to main.

**Reading stays tolerant.** `fromYjs` does not check values and `applyUpdate` does not validate, so a board that already holds an object past the bound (an older build, a peer that skips validation, a hostile client) loads as stored, is drawn, and is never rewritten; honest clients converge and go on deleting, moving and ungrouping around it (`hostile-raw-writes.test.ts` in `tooling/sync-fuzz`, where every command is held to the fuzz's own model of the bound). Nothing in the relay checks values yet.

**Paste and import** are judged like `createObjects`: `importBoard` refuses a portable document with an object whose box on the board, resolved through the parents that come with it, is past the bound, a value past its limit, or a number that is not finite (a `1e400` literal parses to Infinity), each an `out-of-bound` issue; the paste shows "The board could not take what was pasted." and never falls back to the plain text of the copy. A group of two frames at -B and +B pastes and duplicates where it fits; a duplicate offset 16 units outward from the edge is refused with the same notice.

### Transactions, change sets and reads

- `transact(origin, mutate)` validates the origin, runs `mutate` in one `Y.Doc#transact` with that origin, and returns its result. The `DocumentTransaction` stops working when `transact` returns. Transactions do not nest, and listeners must not start one synchronously (both throw).
- `subscribe` gets one frozen `ChangeSet` per transaction (local or `applyUpdate`), computed from `observeDeep` events: key changes on `objects` are creations, replacements and deletions; any nested event (text, label, vertex) is an update of the object it sits in. Ids are sorted. A transaction that leaves no entry changed (an object created and deleted within it) delivers no change set. An update Yjs starts on its own is reported with `SYSTEM_ORIGIN` and `isLocal: true`. In particular, after a remote change to formatted text Yjs runs a formatting-cleanup transaction, so one `applyUpdate` can deliver two change sets and two updates: the remote one, then the cleanup. When the update left references dangling, `applyUpdate` then runs the reference repair as one more transaction, also with `SYSTEM_ORIGIN` and `isLocal: true`, whose update the sync client sends like any local one.
- `subscribeUpdates` gets each transaction's update bytes, for the sync client and the local cache.
- Reads are lazy. A transaction only marks changed keys. The next `read()`, `get()` or `references` query decodes those keys, updates the reverse indexes and, for `read()`, builds a new snapshot. The new snapshot copies the id map (O(n)) but keeps every unchanged object value, so identity comparison finds what changed. Decoded objects are deep-frozen, because their plain values are shared with the document. The snapshot's id map is a `Map` subclass that throws on `set`, `delete` and `clear`, because every reader of the snapshot shares it. It is still `instanceof Map`, but `toEqual` against a plain `Map` needs a copy. `get()` during a transaction shows the last completed transaction; `DocumentTransaction#get` shows the transaction's own writes.
- `updatedAt` is not stamped here: the store has no clock, and the command layer stamps it.
- **Reverse indexes** (`references`, a frozen object holding only the three queries): the schema's `cascadeDelete` and related rules rebuild these on every call, O(n). The store keeps them up to date from each transaction's changes, so the cost is proportional to what changed. A returned set is never modified afterwards; a change replaces it, so keeping one is safe.
- **Undo** reaches the `Y.Doc` through `store/internal.ts` (`internalsOf(store)`), which is package-internal: `src/index.ts` does not export it, and `internal.test.ts` guards that. See "Undo and redo" below.

### The command layer (`src/commands/`)

Every mutation of the board goes through a command that validates against the schema, runs as one transaction and carries an origin, and agents use the same commands.

- **Validate first, then one transaction.** `runCommand` parses the input with the command's Zod schema (strict: unknown keys are refused), then calls `validate(context, input)`, which reads the board and returns either every problem found or a **plan**: each object the command will write, whole, stamped and checked with the store's own write validation (`validateObject`), and each reference checked with the schema's `validateBoard`. Only then does it open one `transact(origin, …)` in which `apply(transaction, input, plan)` writes the plan. A rejected command therefore writes nothing (the tests assert `encodeState()` is byte-identical), and `apply` has nothing left to fail on. Computing the writes once, in `validate`, also carries into `apply` whatever the command read that a transaction cannot (a parent's children, sibling z keys), since `DocumentTransaction` reads single objects but has no reverse indexes.
- **Errors are data.** A rejection is `{ status: 'rejected', errors }` with `CommandError`s: a code (`invalid-input` (also a coordinate or size past the board bound, see "The board bound" above), `missing-object`, `duplicate-id`, `locked`, `unsupported-type`, `mixed-parents`, `overlapping-selection`, `invalid-object`, and the schema's reference codes such as `missing-parent` or `invalid-connector-target`), the object id, a path and a message, so an agent can correct its call. An invalid origin or a clock that does not return whole milliseconds throws: those are the caller's bugs.
- **Deterministic, stamped in one place.** The clock and the id generator are injected through `CommandEnvironment` and read once per run; `createdBy` comes from the origin's principal. `apply` writes through a `StampingTransaction` that records every object written, and once `apply` returns `runCommand` sets `updatedAt` to the command's time on each of them, in the same transaction, so no command stamps it itself (a created object carries `createdAt` = `updatedAt` from its plan). An object whose reference fields the command wrote (`parentId`, `x`, `y`, `rotation`, `z`, `from`, `to`, `anchor`: the fields the reference repair also writes) always gets a new stamp, `max(now, stored + 1)` (at most the largest safe integer, which a peer that skips validation may have stored; fix round 3), even when the stored stamp already equals the command's time (fix round 2): the undo history tells a person's write of those fields from the repair's by that stamp, and the store writes a field only when its value changes. Two clients stamping one object at once keep one stamp, as for any field.
- **Proportional cost: sub-boards.** The schema's rules (`cascadeDelete`, `detachConnectorsFrom`, `validateBoard`, `localBounds`, the frame transforms) take a whole `Board` and scan it. `SubBoard` gathers only what a rule reads, through `get` and the store's reverse indexes (subtrees by `childrenOf`, connectors by target, comments by anchor, chains of ancestors), and the rule runs on that. The results are identical to running the rule on the whole board (`delete-objects.test.ts` checks this against `cascadeDelete` on the full snapshot).
- **Frames of reference.** Positions in `moveObjects`, a resize `origin`, a rotation's `about` and a free connector end are given in board coordinates and converted into the object's parent frame, so a move inside a rotated group goes where it looks. Moving a group or frame changes only its own `x`, `y`: children are relative to it. A move with a `parentId` converts the object's position after the move into the new parent's frame, and its rotation by the parents' rotations up to the ancestor the old and new chains share (so leaving a turned frame for the frame around it is exact); the object stays where the move puts it on the board, turned and nested frames included (tested to 1e-9). `group` puts the group's origin at the top-left of the members' bounds (in their parent frame, rotation 0) and rewrites each member relative to it; `ungroup` composes the group's placement into each child's. Both keep every object where it is on the board (tested to 1e-9). **Group resize**: a group stores no size, so `resizeObjects` takes the size of its derived box (`localBounds`) and scales what it holds along the group's own axes, about the box's top-left corner (`planGroupResize`, `affine-map.ts`); `origin` then names where that corner goes. Each descendant is written in its own parent's frame and keeps its rotation (objects are rigid): a boxed object's centre follows the scale exactly and its sides stretch by the length the scale gives its own axes (the select tool's multi-selection rule, exact for objects turned with the group or a quarter turn from it), while line points, path vertices and handles, free connector ends and the children of nested groups and frames are mapped exactly; font sizes and stroke widths do not change. A side of zero length cannot scale and stays. The command names only the listed objects in its result, refuses a descendant listed with its group (`overlapping-selection`) and a size that would collapse the box along a side, or grow a side of zero length, which cannot scale (`invalid-input`). Tested to 1e-9 in board space on a turned group (`group-resize.test.ts`); concurrent group resizes against child moves, restyles and an ungroup, and concurrent group and ungroup of overlapping selections, converge (`resize-objects.sync.test.ts`, `group.sync.test.ts`).
- **Concurrent-edit friendliness.** Commands patch only the fields they change (`patchObject`), and `setObject` on an existing object writes only changed fields, so a concurrent edit of another field survives. `setTextRuns` goes through the store's diffing text write (common prefix/suffix, reformat only changed ranges), never delete-all, insert-all; `setStyle`'s `textStyle` uses `formatText` with only the given style fields.
- **Typing carries its size**. The text editor writes every keystroke as one `setTextRuns` with the box's new measured `size` (`width`, `height`, positive), so the stored bounds that culling, hit testing and agents read follow the text, collaborators see the box grow as it is typed, and the text and its size are one undo step. Concurrent edits to one run merge through the `Y.Text` (`set-text-runs.sync.test.ts`: two people typing in one run keep both insertions; typing inside a range another person restyles converges, the typed characters taking the restyle, since `Y.Text` formats a range between two markers); concurrent sizes are last-writer-wins per field, and the next keystroke on either side writes the size of the merged text.
- **Field-scoped validation.** A command is judged by what it writes, not by the whole object: `validateObject` (`store/object-validation.ts`), the one rule of the store's `setObject` and `patchObject` and of every command's `validate` (`checkObject`), validates a new object whole, and a write to an existing one field by field (`store/written-fields.ts`): each field whose value differs from the stored one by the door's equality (`isSameValue` of `@canvas/schema`, NaN equal to NaN), and each cross-field rule such a field takes part in (a text's or sticky's runs with its characters; a path's changed vertices and segments with their ends, member by member, `store/network-write-check.ts`, so an edit of 100 of 1,000 vertices parses 100). A field it leaves as stored is not judged, valid or not, so a negative width, a NaN rotation or a nested style value of the wrong kind a peer left blocks no move, lock, reorder, restyle, group or label edit, and stays as it is; the reader still reports it (`BoardSnapshot#issues` unchanged) and the engine still treats the object as undrawable. Last, nothing a write stores may be refused by the relay's door (`store/door-values.ts`, part 1): every value under a key the door judges (placement, size, an image's crop and natural size, line ends, network members) passes `drawableValuesReason` or is what the board already holds, else the command is refused as `invalid-object` naming the field, never left to close the connection with 4426. **A size is judged whole:** a size the door refuses is never let through as stored, so a write of the size group that keeps one (a resize of the other dimension, a group's resize that leaves it unscaled) is refused naming the refused width or height until a write replaces it (a resize `to` a size in range, or a group's resize that scales it into range). A group's resize over a member's size that is not finite, and an image's crop over one, are refused naming that size (`findUnscalableSizeIssues`): nothing can be scaled or derived from it. The hub's size may no longer be the one this client holds (another client resized the object back into range, or this client was offline when it did), and the door judges the kept width as a change against the hub's and closes the client for good, while the hub's repair must stay; the nightly fuzz closed honest clients that way. A field outside the size (a NaN rotation kept by a move) is still kept as stored. A duplicate is a new object, judged whole: copying an object with an invalid field is refused (by `createObjects`' input schema), as a new invalid object would make the board worse.'s stored-`z` exception is one case of the rule. An undo restores Yjs items and is not validated by this rule.
- **Rules chosen here.** Locked objects cannot be moved, resized or rotated; other commands may change them, and `setLocked` locks or unlocks them (it writes `locked` alone, its own key, so a lock merges with a concurrent move of the same object). A group carries its descendants, so a group holding a locked object anywhere below it cannot be moved, resized or rotated either (`lockedDescendantOf`); a frame is not a group and still carries locked children. An object listed together with one of its ancestors is refused where it would move twice (`moveObjects`, `rotateObjects`, a resize with an `origin`, `ungroup`). `group` needs members that share one parent; the group is stacked where the topmost member was, with a fresh key (below). A reparenting move (`reparent.ts`) takes an object only into a frame or onto the root, never into itself or its descendants (`parent-cycle`), nor into a frame the same command moves (`overlapping-selection`: that frame has no settled position to convert into); an object whose parent is a group is refused (`invalid-parent`), since groups move as a unit, and a `parentId` equal to the object's own is a plain move. The select tool picks the new parent (the top-most frame under the object's centre on release); the command only checks and converts. `connect` needs at least one end on an object (two free points are a line). `setStyle` refuses a field the object's type does not take instead of ignoring it. `setLinePoints` moves one end of a line and is refused for a locked line, as a move is, and for an end put on the other end, since a line needs a length; a line's ends stay free points, so snapping one onto another object's anchor attaches nothing (a line attached to objects is a connector).
- **Z keys.** `z-placement.ts` gives new objects and ungrouped children their keys from `src/z-order/` (see Z-order below). `nextZAbove` puts an object above every sibling through the store's `topChildOf`, and `zKeysOnTop` several, in order (a reparenting move: the objects taken into one parent go on top of its children in the order the board painted them in, `comparePaintOrder`, since keys of objects from different parents are not comparable on their own): O(1) while the top only rises, and one rescan of that parent after the top child moves down or away. `zKeysAbove` puts a group's children directly above the group's key and below the next sibling's, with one lookup per sibling; `group` uses it too, for the new group's key directly above its topmost member's. Every key ends in its object's tag, so two groups ungrouped together, even groups with equal keys, give their children distinct keys. `createObject` rejects an input `z` that is not a fractional-index key (`invalid-input`). Such a key would sit on top of its parent and block every later placement above it. The schema's `z` rule now refuses such a key on every local write and on import (`invalid-z-key`), but remote updates are not validated, so a peer that skips validation can still put one on a board (the tests write it that way, `store/__fixtures__/remote-keys.ts`). Then `nextZAbove` refuses the placement with `unorderable-neighbours`, and so does `zKeysAbove` when neither the gap nor the top of the stack can be used; neither throws. `zKeysAbove` also moves to the top of the stack when the gap's keys would exceed `MAX_KEY_LENGTH`.
- **`createObjects`.** `createObject` makes one object per command, and a paste of N objects must be one undo step, so `createObjects` takes `{ objects, parentId }` and writes every object in one transaction. The listed ids are local to the input: every object gets a new id from the command's generator, and a listed `parentId`, connector end or comment anchor that names another listed object is rewritten to its new id; a listed object's `parentId` is another listed object or `null` (the command's `parentId`), and an end or anchor that names no listed object must name an object on the board (the reference rules then apply as for `createObject`). Keys are generated, never copied: the objects going into the target parent take `zKeysOnTop` in input order, each new parent's children stack from the first key, and `z` in the input is refused (`invalid-input`). Errors about an entry carry its input path (`['objects', index, …]`) as well as its new id, since the caller knows only its listed ids. A created instance's overrides are checked as `createInstance` checks its own (`createdOverrideErrors`): fields the target child takes, an auto-layout patch only on a child with a layout, and a swap only to a main the slot may show, with the objects created in the same call read in place of the board's; a record that fails refuses the call at `['objects', index, 'overrides', path]`. Pasting 1,000 objects (groups of eight shapes, a two-run text and a connector) onto a 10k-object board (`create-objects.bench.ts`; Node 22, Apple M1 Max): `validate` takes about 6.6 ms mean (4.2 ms min), and the whole command about 58 ms mean (34 ms min), most of it the Yjs transaction writing the 1,000 objects.
- **An image's crop moves its box**. `setStyle` of `crop` on an image writes the box with it (`croppedImageBox`): the crop is in fractions of the natural size and the box is the displayed size, so a crop that left the box as it was would stretch what stays shown. The box keeps the image's scale (world units per image fraction) and the shown part's place, the origin moving along the image's turned axes, so the crop tool sends one `setStyle` and an agent's crop looks the same. No field of the stored layout changes: the crop is in the image's `style` value, its box in `placement` and `size` (the grouped layout above), so a crop racing a concurrent restyle of the same image (an opacity) keeps one of the two restyles whole, and one racing a move or resize or another crop of it can pair one client's crop with the other's box (`set-style.sync.test.ts`, both client-id orders, and after either client's undo). The result converges and is valid, and it is never drawn stretched (fix round 1): the renderer, the hit tests and crop mode draw the crop at its own aspect fitted inside the box, centred (`fittedImageRect` of `@canvas/schema`), and `croppedImageBox` and `fullImageBox` measure from there, so the next crop stores a box of the crop's aspect again. A read-time correction of the box was not an option: images resize freely (non-uniformly) with the select tool, so a box off the crop's aspect is also a legitimate state. Whether style fields should merge field by field is the owner's open decision.
- **Adding a command**: write `commands/<name>.ts` exporting a `Command`, add one entry to `COMMANDS` in `registry.ts`, and a test with a diff assertion, a rejection test and a sync test. The reorder commands `bringToFront`, `sendToBack`, `bringForward` and `sendBackward` are one entry each. Their new keys are computed in `validate` (`planReorder`) and handed to `apply` in the plan.

**Deleting a 1k-child group on a 50k-object board** (`delete-objects.bench.ts`; Node 22, Apple M1 Max): planning the cascade through the reverse indexes (`validate`) takes about 1–1.4 ms (mean), against about 14–17 ms for the schema's `cascadeDelete` on the whole board, 12–14× less. The whole command takes 25–325 ms (mean 125–150 ms, high variance), almost all of it the store's transaction deleting the 1,050 objects; the same deletes on a bare `Y.Doc` take about 13 ms, so the store's per-transaction work on large deletions is worth profiling (a follow-up for the store, not the command layer).

### Z-order (`src/z-order/`, `src/commands/reorder.ts`)

Z-order is a fractional index, never array position, so concurrent reorders merge. There are four moves: bring to front, send to back, bring forward and send backward.

**Keys.** The key rule and the sibling order live in `@canvas/schema` (`src/z-order/`: `isValidKey`, `MAX_KEY_LENGTH`, `compareKeys`, `compareSiblings`), so the schema validates `z` by it and the engine, which may import only the schema, draws by the same order; this package generates keys. A key is an integer part followed by a fraction, over the base-62 alphabet `0-9A-Za-z` (ascending in ASCII, so comparing keys as strings compares them as numbers). The integer part's head letter states its length: `a` to `z` head 1 to 26 digits (the non-negative integers; `a0` is zero), `Z` to `A` head 1 to 26 digits (the negative ones). The fraction is any run of digits not ending in `0` (there is no key between `x` and `x0`). This is David Greenspan's scheme ([Implementing Fractional Indexing](https://observablehq.com/@dgreensp/implementing-fractional-indexing)), the one behind Figma's z-order and the `fractional-indexing` package. It is implemented here rather than added as a dependency because of the change below. The change: a generated key is **never a prefix of its upper bound**. The reference returns `a1` between `a0` and `a1V`, for example, where this returns `a0V`. That occasionally costs one character, and it makes appending to a key safe.

**Tags.** Generation is deterministic, so two clients that concurrently move different objects into the same gap would compute the same key. `generateObjectKeys`, which every key this package writes comes from, therefore appends a five-character tag: a `0` separator and four digits hashed from the object's id (the last never `0`). Concurrent placements of different objects then get distinct keys and the merged order is total with no coordination. Two ids share a tag with probability about 1 in 1.5 × 10⁷. `sortedSiblings` breaks any remaining tie (and duplicates in imported boards) by id. The separator matters for growth. A midpoint computed next to a key reads that key's digits until it finds room, and a `0` always leaves room, so the midpoint stops before the tag. Without it, the growth of keys placed next to an object depended on that object's tag: two layers with high tag digits swapped back and forth reached 512 characters after about 1,000 swaps instead of 2,525.

**Growth bound; no rebalancing.** Between any two distinct keys there is always another, so a move rewrites only the moved objects' keys and keys never need rebalancing for correctness. Every key the commands write is a generated key plus its five tag characters, and the lengths below include the tag. Repeated inserts next to the previous one make the midpoint digit walk a fixed cycle before a key needs another character. Toward a fixed upper neighbour the cycle is `V l t x z` (31, 47, 55, 59, 61), five inserts, because `Math.round` takes .5 up as in the reference. Toward a fixed lower neighbour it is 31, 16, 8, 4, 2, 1, six inserts. The tag's separator keeps tags out of the cycle. Tests check each bound on the tagged path, and a probe over 200 seeds of ids matched them exactly.

| Pattern                                                                                                           | Length of the written key                                                   |
| ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| At the ends (bring to front, send to back, new objects): the integer part counts up or down                       | 5 + log₆₂ n: 62 keys in 2 + 5 characters, 3,844 in 3 + 5, 238,328 in 4 + 5  |
| `n` objects placed in one gap at once                                                                             | about log₆₂ n more than the gap's bounds, + 5                               |
| 10k inserts at random positions (untagged)                                                                        | at most 7, + 5                                                              |
| Worst case, each object placed just below one fixed neighbour (for example two layers swapped with bring forward) | at most 2 + ⌈n / 5⌉ + 5: 2,007 after 10k; over 512 only after 2,525 inserts |
| Worst case, each object placed just above one fixed neighbour                                                     | at most 2 + ⌈n / 6⌉ + 5: 1,674 after 10k; over 512 only after 3,030 inserts |

The `2 +` in these bounds is the two-character integer part the neighbours share (such as `a1`). A longer shared integer part adds its extra characters once. When the two neighbours also share a generated fraction (a gap that starts inside an earlier key's digits), the first key in the gap carries that shared part, a one-off few characters, before the cycle starts.

`MAX_KEY_LENGTH` is 512. Only a run of more than 2,525 worst-case moves in one gap reaches it. `reorder.test.ts` swaps two layers under a fixed third with `bringForward` 2,525 times before the command refuses with `key-too-long`, rather than writing an oversized key. If that ever matters in practice, the remedy is re-keying the siblings of that one gap; nothing else needs it.

**The schema's `z` rule** is `isValidKey`: 1 to 512 characters of `[0-9A-Za-z]`; the first character a letter; at least as many characters as the head states (`a`–`z`: head code − `a` + 2; `A`–`Z`: `Z` − head code + 2); a fraction that does not end in `0`; not `A` followed by 26 zeros alone. The store's write validation and the command input schemas apply it through the object schema.

**Moves.** `planReorder` computes the new keys from the board and writes nothing. Each reorder command's `validate` returns that plan, and `apply` writes the keys (`patchObject` of `z` only); `runCommand` stamps `updatedAt`.

- `bringToFront` / `sendToBack`: the objects move as one block above (below) every other sibling, keeping their relative order, with keys counted up (down) from the top (bottom) unselected sibling. Nothing is written when they are already there.
- `bringForward` / `sendBackward`: each maximal run of selected siblings hops over the unselected sibling directly above (below) it, keeping its order; the topmost (bottom) run moves first, so a lower run can land next to it. A run already at the end stays.
- Validate first: `runCommand` opens no transaction unless every id exists and is listed once (`missing-object`, `duplicate-id`), all share one parent (`mixed-parents`) and the new keys fit. `unorderable-neighbours` is reported when a neighbour's key is not a valid key or two neighbours share a key; `key-too-long` when a new key would exceed the limit. Each error names the object and its input path.

**Concurrency.** Only the moved objects' `z` fields are written, so moves of different objects merge and concurrent moves of the same object keep one (last writer wins per field). The fuzz found one more thing worth knowing. When updates arrive out of order, Yjs applies an update's deletions at once but holds its insertions until the missing update arrives. An object whose `z` was just replaced is then unreadable for a while (`missing-field` in `BoardSnapshot#issues`), and it is missing from `sortedSiblings`. Delivering each client's updates in order is not enough to prevent this: client B's update can overwrite a value client A wrote, and must not reach a third client before A's. Causal order prevents it, and the relay provides causal order when it forwards updates in the order it received them. The fuzz deliberately breaks causal order: it skips a move when a client sees no siblings, and the store converges once everything arrives. `YjsDocumentStore` takes an optional `clientId`, so the fuzz fixes every client's Yjs client id and a seed replays exactly, merge winners included.

**No copied keys.** Every key a command writes is generated, never copied from another object. `group` used to give the new group its topmost member's key. The fuzz showed why that is wrong: two clients that group selections with the same topmost member at once (or overlapping selections, one member in both) create two sibling groups with one key. Both clients converge on that board, but a key between two equal keys does not exist, so every later move into that spot was refused with `unorderable-neighbours` (1 to 3 refusals per 5-client × 100-iteration run, and now and then one in the default run). The group now gets a fresh key between the topmost member's key and the next sibling's, from `zKeysAbove`, ending in the group's tag, so the two groups' keys differ and are ordered, and the stack looks the same as before. When that gap cannot be used (the member's key is not a fractional-index key), the group goes on top of its parent's stack, and `group` is refused with `unorderable-neighbours` only when the top cannot take a key either. We fixed the command rather than having a repair pass re-key equal siblings after the merge: the fix removes the collision outright, where a repair would leave a window in which commands are refused and would write on every client that sees the tie. Boards that already hold equal keys (from before this fix, or imported) still stack by id (`compareSiblings`), and a reorder that needs a gap between two of them is still refused; re-keying them is the repair pass's job. `group.test.ts` has the two-client tests: the same topmost member, and overlapping selections, each followed by a reorder into the spot between the two groups.

**Cost** (Apple M1 Max, Node 22, each bench run alone). `sortedSiblings` over 50k siblings takes 27 ms (sorting the bare keys takes 15 ms), so the scene graph should keep its segments ordered incrementally from change sets rather than re-sort per frame. `planReorder` over 50k root siblings: front and back take one pass over the siblings with no full sort, 13 ms; forward and backward sort, 33–44 ms. In both cases reading the siblings from the store is most of the cost. `keysAtFront` reads the top child from `topChildOf`: 0.5 µs with 50k children at the root (it was 4 ms as a scan). Generating 10k keys takes 1.6 ms at once, 6.3 ms tagged in one gap.

**Integration with the command layer.** The reorder commands are ordinary `Command`s. `validate(context, input)` looks the objects up and returns the plan. `apply(transaction, input, plan)` writes it. `runCommand` stamps `updatedAt` on every moved object. The store's `topChildOf` keeps each parent's top child up to date from the transactions' changes, which makes `keysAtFront` O(1) while objects are created at the front. After the top child moves down or away, the next query rescans that parent once.

**Shared with the engine.** The engine may import only `@canvas/schema`, and the sibling order it draws by must match `sortedSiblings`: `z` by UTF-16 code units, then id. Both use the schema's `compareSiblings`; the engine's `sibling-order-agreement.test.ts` checks its paint and pick order against it on one fixture.

### Undo and redo (`src/history/`)

Undo is per user and scoped by origin: it undoes only that user's changes, survives reconnection, and lets an operator undo the agents they operate.

- **One `Y.UndoManager` per user**, scoped to the `objects` map and reached through the package-internal `store/internal.ts`. Its `captureTransaction` predicate (`origin-ownership.ts`, `isOwnedBy`) records a local transaction when its origin is `{ kind: 'user', principalId: P }` or `{ kind: 'agent', operatorId: P }`, and its `historyKey` equals the history's (both absent for an unkeyed history). Origins are compared by value: the store hands Yjs a fresh frozen copy of each, so `trackedOrigins` is `new Set([Object])` (a plain object is tracked by its constructor) and the predicate decides. Yjs's own transactions carry `null` and are never tracked. Several histories can share a store; each records only its user's changes, subject to the shared-client-id limitation below.
- **Local only, but for the user's agents.** Remote updates (`applyUpdate`, change sets with `isLocal: false`) are not recorded by origin, whatever origin they are applied with, so a user's history on one device does not undo their edits on another. An agent that runs in its own headless client is undone by a history for its operator in that client: `createHistory(agentStore, operatorId)` records the agent's commands there. A history given `operatedWriters` also records, as a step of its own tagged with its writer, a remote update written under exactly one Yjs client id `records` accepts (the app: an id the relay vouched for one of the user's agents, or an agent's awareness id before its first stamp, only while connected; `operated-writes.ts`), and the clock range it wrote, which the guards count as own while `owns` accepts the id (`written-by-others.ts`). An undo first drops, unapplied, the newest steps whose writer `owns` rejects (a candidate id the relay vouched for someone else), and waits, doing nothing, while the newest step's writer is not known yet; `canUndo` leaves rejected steps out without dropping them. An update written under several client ids, or holding only deletes, is not recorded.
- **One step per command.** `runCommand` runs one transaction per command, including the `updatedAt` stamp, and the default `captureTimeout` of 0 never merges transactions, so a command that writes many objects (`group`, a delete with its cascade) is one step (tested). `captureTimeout` and `stopCapturing()` are there for tools that will merge a gesture into one step.
- **Undo is attributed.** `undo()` and `redo()` run inside `store.transact({ kind: 'undo', principalId: P })`, so their change sets and updates carry an undo origin the app can label, the store's view stays current, and the store's guard applies (no undo from a listener). `isOwnedBy` never owns an undo origin, so an undo is not recorded as a new step; `Y.UndoManager` puts its inverse on the other stack. It decides which stack by its `undoing`/`redoing` flag, which it clears when its own (here nested) transaction returns, before the store's transaction ends; the history holds the flag up until then. The undo origin's principal is the user who undid, also when the step was their agent's.
- **What a step restores.** The fields a command wrote return to their previous values, `updatedAt` included (undo restores the earlier stamp; it is not a new edit). Created objects are deleted, unless someone else has touched them since (below); deleted objects come back whole, with text runs, labels and vector networks (tested on the whole fixture board).
- **Concurrent edits (Yjs semantics).** Others' changes to other fields of the same object survive an undo. A later change by someone else to the same field wins: undo does not overwrite it. A step whose every change has been overwritten can change nothing: it is used up, and `undo()` returns `false` without touching the step before it (one click, one step; below).
- **Shared-store histories share a client id.** Histories on one `YjsDocumentStore` share its Yjs client id, even when their origins name different principals or operators. Origins decide which changes each history records; they do not make those histories separate CRDT clients. The [causal field guard](src/history/field-guard.ts) and [creation guard](src/history/creation-guard.ts) described below therefore cannot protect different principals' writes or objects from each other's undo when those principals share one store. A person and their own agent are a different case: the agent's commands belong to that person's one operator history, as intended; they are not separate principals requiring protection from each other's undo. Keyed histories of callers sharing one agent connection are told apart ([`write-lanes.ts`](src/history/write-lanes.ts)): each history records, per document, the clock ranges of the transactions it captures (its commands and its own undo and redo) on the document's client id under its key, its write lane, and the guards count an item of the store's own client ids in another lane than the step's as another writer's, exactly as another client's. A keyed caller's undo therefore keeps what another key, or the unkeyed history, wrote since, and the other way round. Ranges no history captured (the reference repair, system writes) stay the step's own. Unkeyed histories record nothing until a keyed history is made on the document, so a store without keys behaves as before; different principals' unkeyed histories on one store still share one lane.
- **No undo leaves a field empty (`field-guard.ts`).** Every field (or group of fields) of an object is always present in its `Y.Map`, and an object missing one cannot be read. The rule (`isGuardedFieldValue`): **an undo or redo of a step may delete a field's current value unless another client wrote that key concurrently with the step or since (a value whose Yjs clock the step's recorded state vector does not cover; a write the step had in view, and any delete, protect nothing), or the step itself replaced the key's value and restoring the earlier value failed. A kept value keeps its contents (case 3 below), and an object restored after a delete that raced an edit gets its emptied fields back (case 2).** Each step records in its Yjs `meta` the state vector before its first transaction (`causal-past.ts`; a step merged within the capture window keeps its first transaction's; the step an undo or redo pushes onto the other stack gets the vector as of that undo or redo, since it is that undo or redo's inverse), and the guard makes one pass over the key's values to find another client's write the vector does not cover. Where Yjs placed a losing write does not matter. Cases, all tested in both merge orders: a key added, removed, undone and redone any number of times (a network member) can always be removed again, so undo and redo never get stuck on their own re-creations (before the guard kept every current value with an earlier value of its key, and the value an undo or redo re-created always has one, so the step changed nothing and Yjs popped through to the next one: undoing a redone vertex undid the path's creation); a collaborator's move or add that raced the user's value, or an earlier copy of it an undo or redo made, keeps the value (fix round 1, Q2e and Q2b); a race older than the step does not (fix round 2: Ada and Bob move v3 at once, then Ada deletes the path's end, undoes and redoes; round 1 kept v3 on every redo); a value re-added by a command under an id deleted before, raced by another client's add of that id, is kept (Q2c, a known limit in round 1); a concurrent delete of the member protects nothing; a collaborator's later overwrite is not current, so undo leaves it. In the grouped layout only a network map gains and loses keys after an object is created. `Y.UndoManager` treats any later value of a key as "a change from another client" that it must not overwrite, even one the merge has already discarded, and can then leave the key without a value. Two cases, both tested with each merge order: (1) the user's write won a concurrent write to the same field: Yjs deletes the user's value and refuses to restore the one before it. The `deleteFilter` (`isGuardedFieldValue`) keeps the user's value instead: the other client's write is outside the step's past, and the step replaced the key's value. (2) The user deleted an object while another client edited it: undoing the delete re-creates the object's map without the edited field. `restoreEmptiedFields` writes the field's value from before the delete, in the same transaction, whatever plain content held it: `ContentAny`, or JSON or an embed a peer's encoder wrote (those came back `null`, an unreadable placement the relay's door refuses, which closed the undoing client; `field-guard.plain-content.test.ts`). A label another client replaced (added or removed) concurrently with the delete cannot be rebuilt from the deleted one, so it comes back as `null`, which is what a concurrent removal asked for (tested in both merge orders). (3) Case 1 for a field whose value is a shared type: two clients set a label at once and the user's won. The filter kept the label map, but Yjs deleted the text and runs the same step had put inside it, so the label, and with it the object, could not be read; the sync fuzz found a comment pinned to such a connector, off every board (`missing-comment-anchor`), because the reference repair leaves an entry that is present but unreadable alone. `isInsideKeptValue` also keeps whatever lies inside a value the filter keeps, when the step being undone or redone replaced that value's key: the step deleted an earlier value of the key, which Yjs keeps to the value's left in the key's item chain. It decides by the kept value and the step, not by which step inserted the item, because Yjs follows `item.redone`: after an earlier undo or redo re-created the label's text (undoing a removal of the label, or an edit of its text), Yjs asks about the re-created items, which the other stack's step inserted (fix round 1; asking which step inserted them left the label without its text, or with text nobody wrote). The step being applied is the one the history handed Yjs (`single-step.ts`, below); before Yjs could pop through a step that changed nothing to the next one in the same undo, which is how the fuzz reached the label. The cost per item undo would delete is a walk up its owners inside the object (two for a character of a label), and for an owner that is the current value of a replaced key, a walk over that key's earlier values with one delete-set lookup each (logarithmic in the step's size); it no longer grows with the stack.
- **History-walk memo (`key-replacements.ts`).** Repeated label-child checks share whether the exact step deleted an earlier value of the same owner item, only within one `SingleStep.apply`. Current-value and causal checks remain live. Every apply creates a fresh memo for its actual handed step and clears it in `finally`, including errors; nothing survives into another undo, redo, capture, remote update or GC. Yjs 13.6.33 restores all items before its delete-filter loop; item deletion does not change left links, and GC/merging happens after that loop. Re-read that ordering on a Yjs upgrade. `field-guard.memo.test.ts` counts the actual history walk during a rich-label undo; `single-step.memo.test.ts` covers operation, error and substituted-step lifetimes.
- **One click, one step.** `undo()` and `redo()` apply at most the newest step of their stack. `Y.UndoManager` pops a step and, when it changed nothing (another client overwrote all of it, the field guard kept every value it would remove, or Yjs refused every restore), pops the next one in the same call, so one click could undo several of the user's steps. `SingleStep` (`single-step.ts`) hands Yjs an array holding only the newest step, whose `pop()` puts the rest of the stack back as the manager's live stack before returning the step: Yjs then sees the stacks as when it pops the step itself (its conflict rule reads them while it restores) and its loop ends after the one step. Yjs is not patched; `single-step.test.ts` pins, on a bare `Y.UndoManager`, both the pop-through and how it pops, and is the gate for a Yjs upgrade. A step that can change nothing is used up: it leaves the stack, nothing goes onto the other one, and the call returns `false` while `canUndo()` (or `canRedo()`) may still be `true`; the app tells the person (`@canvas/app`, "Nothing to undo here: this has changed since."). Every pop closes the capture window (`stopCapturing()`): Yjs does so only when it pushes an inverse, so after a used-up step the next edit inside a `captureTimeout` window would have merged into the older step now on top (review; tested with a capture window and no app policy). Yjs restores a key's earlier value only when every later value of the key was deleted by the step, re-created, or deleted by a step on one of its live stacks (`isDeletedByUndoStack`); a redo step holds what its undo deleted, so once a new edit dropped the redo stack, a later value of the user's own that an undo had removed blocked the restore as if another client had written it (with ids reused after a delete, undo then undid nothing, or popped through). `ClearedRedoSteps` (`cleared-redo-steps.ts`) keeps the deletions of the redo steps Yjs drops for a recorded change, merged, as ids only (no content kept alive), and `SingleStep` shows them to Yjs as one delete-only step beside the live stacks while it applies a step, gone again before Yjs pushes the step's inverse. The set only grows, by id ranges, for the history's lifetime, as the stacks have no cap either. They are this history's own undo deletions, which Yjs read on the live redo stack until the drop, so a value another client wrote still blocks a restore (tested in both merge orders). With both, one client's undo and redo match an exact model of the two stacks with reused ids as with fresh ones (`field-guard.property.sync.test.ts`; 7 of 100 seeds failed before). Two clients: a step overwritten by the other client, a step the guard refuses in full (a label race Ada won, and the same race Bob won), and a redo step overwritten since are each used up without touching the step before or after them (`single-step.sync.test.ts`, both merge orders).
- **No undo throws part-way (`collected-copies.ts`).** Yjs 13.6.33's `redoItem` follows a value's re-creation link (`item.redone`) and reads what it finds as an item, but the copy can have been garbage-collected: an undone delete re-creates an object's map as the user's copy, Yjs stops keeping that copy when a cleared step had deleted inside it (`keepItem(item, false)` walks up to the map), and another client's delete of the object then collects the copy and its values. A later undo of an older edit of the object threw a `TypeError` out of Yjs after popping the step, with some of its values already restored. Before Yjs applies a step (after the creation and door guards), `reachesCollectedCopy` replays Yjs's restore walk without writing; when Yjs would throw, the step is used up unapplied, as one that can change nothing: `undo()` returns `false`, the document and the other stack are untouched, and the steps below it stay for the next undo (`undo-manager.deleted-objects.sync.test.ts`). `collected-copies.test.ts` pins the throw on a bare `Y.UndoManager` and is part of the gate for a Yjs upgrade: when it stops throwing, re-read the walk. An undo that writes only inside an object deleted since is used up the same way and leaves nothing to redo, even if the object comes back later: the copy another client's undo re-creates is linked to the old map only on that client, so the step could never apply here again (item 2's ruling).
- **Undo never deletes what someone else has touched (`creation-guard.ts`, `restore-guard.ts`, `written-by-others.ts`).** Undoing a creation deletes the object's map, and every later write inside it went with it: Ada created a shape, Bob recoloured it, Ada's undo deleted the shape and Bob's colour, silently (found on staging; the field guard protects values, not objects). The our decision is to protect: an undo or redo does not remove an object that another person has, since the step, written to (any key, its text, its label, its network), written to a direct child of (any write to an object in it: a member of a group, an object in a frame; the owner's "or to a child of it", fix round 1), or made a connector end or comment refer to. "Another person" is the field guard's notion, a Yjs client id other than the history's judged by the step's causal past, so the same person in another tab counts and a write the step had in view does not; a delete leaves no item, but every command stamps `updatedAt` on every object it writes, which is a write. **Every incarnation counts (fix round 1, C1):** after Ada deletes an object and undoes the delete, Yjs has re-created the object and every value in it, Bob's included, as Ada's own items; Bob's writes stay in the earlier incarnation, which the undo manager keeps alive, so the guard reads every entry under the id whose re-creations (`item.redone`) end in the live one (`incarnationsOf`). **The product's own writes never count (fix round 1, I1):** the reference repair runs on every client that sees a dangling reference, writes only `placement`, `z`, `from`, `to` and `anchor`, and never `updatedAt`, while every command stamps `updatedAt` (both pinned by `creation-guard.writers.test.ts`: every registered command, and every repair rule); so a peer's write of one of those keys counts only when the same peer also wrote that object's `updatedAt` since the step. No local record and no Yjs origin walk is needed, and it works whichever client's repair won and whether this client repaired at all (the first round's record of local product writes is gone). A command that writes a reference key always writes a new `updatedAt`, `max(now, stored + 1)`, so an edit in the very millisecond of the object's last stamp is a person's too (fix round 2; `creation-guard.writers.test.ts`, "reference-key edits at the same instant"). Before Yjs applies a step, `CreationGuard.begin` finds the objects it would remove (object entries among its insertions, following `item.redone` as Yjs does) and keeps those touched, with what the same step created that they lie in (the parent, up, so nothing kept dangles) and that lies inside them (a pasted group's members, a frame's content, so nothing kept is emptied), through the history's `deleteFilter`. Per object: a paste removes what nobody else touched and keeps the rest. A connector or comment kept whose target goes is detached or re-pinned where it was by the step's reference repair. When keeping an object would split the step, because the step also wrote a reference to it in an object it does not remove (`group` moves existing objects into the group it creates, and undoing that would empty the group), the step is used up whole without being applied (`SingleStep.discard`); the check reads every incarnation of those objects, since an undone delete of the members re-creates their placement as copies (fix round 2). **Values too (fix round 1, found by the property test):** Yjs restores a removed value only when every later value of its key was removed by the step, by a step on a stack, or re-created (`item.redone`); the last is a hole, since the re-creations include another person's values copied by an undo of a delete, so an undo of an older step wrote over Bob's colour after Ada's delete and its undo (the "redone-chain overwrite" `field-guard.test.ts` had pinned). `restore-guard.ts` hands Yjs a copy of the step without such restores. It also keeps a value the step set that holds a shared type another person has written inside since (Bob typed into the label Ada set), and does not restore that key. Fix round 2 makes both read every incarnation (`copiesOf`): Bob's typing into Ada's label survives only in the label an undone delete re-created from (property seed 1185, `creation-guard.recreated.sync.test.ts`); a re-created value passed on the way counts with what was written inside it, so Bob's undo of his delete of Ada's frame no longer writes her old frame over the newer one under the same id that Ada moved (seed 2088, `creation-guard.seeds.sync.test.ts`); and a restore into a map an undone delete re-created is checked against the live map's key, whose values Yjs never looks at. This fixes, the redone-chain overwrite of a label or stamp another client's write had won (`field-guard.test.ts`, "keeps a label whole when undoing an edit of it, then its set" and "keeps a label whole when undoing its removal, then its set", Bob-wins order). A step that changes nothing is used up as any other: `undo()` returns `false`, nothing goes to redo, and the app shows its notice; a later undo by the other person of their own change does not bring the step back. The redo of a delete is guarded the same way. An edit still in flight when the undo runs (not yet received by this client) cannot be seen: the undo goes ahead, and the edit, arriving later, lands in a deleted object, as with any delete that races an edit. Before the fix, a redo after such an undo brought the shape back with Bob's colour. The cost is the step's inserted and deleted structs, the items of every incarnation of each object it would remove, and the own keys of those objects' dependents (children, attached connectors, pinned comments, through the store's reverse indexes), each a pass over that key's values; never the board. Tests, in both merge orders unless noted: `creation-guard.sync.test.ts` (restyle, move, text typed, a label typed, an object put in a frame, a member added to a group made by `group`, a connector attached, the same person in another tab, the other person's later undo, a colour overwritten within the step, and an untouched object still deleted), `creation-guard.recreated.sync.test.ts` (C1: recolour and label, through delete-undo-undo, delete-undo-redo-undo-undo, and an edit racing the delete; an attached connector through the first two), `creation-guard.product.sync.test.ts` (the repair race in both orders, the review's sequences a, b and c), `creation-guard.steps.sync.test.ts` (a paste with one object touched, a pasted group moved, a write to a group member and to a pasted frame's child, and the redo of a delete), `creation-guard.writers.test.ts`, and the seeded `creation-guard.property.sync.test.ts` (below); `undo-manager.repair.test.ts` reaches the repair through a paste and through an undo restoring an object whose group another user deleted. Known limit, as for the field guard: two principals sharing one store (one Yjs client) do not protect each other's objects.
- **The property test (`creation-guard.property.sync.test.ts`, fix round 1).** Two clients, seeded: creates (ids reused after deletes), pastes, groups, restyles, moves (leaves into frames), labels, connectors, deletes (frames too), repair races (one client moves a shape into a frame while the other deletes the frame, offline), undos and redos on both, a link that drops and comes back, both client-id orders; a broad mix and a focused one (frames, moves into them, deletes). The oracle (`__fixtures__/undo-oracle.ts`) knows what the history cannot: which items the product wrote (it watches every store), who first wrote a value an undo copied (it follows `item.redone` back), and each step's causal past (its own model of the two stacks, which follows Yjs's rule that an undo writing only into a map deleted meanwhile leaves both stacks). The invariant, around every undo and redo: no value another person wrote since the step, and that was on the clicking client's board, is gone after the click; at the end both boards converge and are valid. Defaults: 60 seeds per mix and order from 20261100 (broad) and 100200 (focused), which hold the C1 (seed 20261117) and I1a (seed 100227, Ada's client id 1) sequences the first round failed; `SYNC_FUZZ_SEED` and `SYNC_FUZZ_ITERATIONS` override them. The oracle's model counts the steps on each stack (`history-depths.ts`, package-internal) and predicts on its own whether each click pushes an inverse (it does when the click's transaction changed a live type under the objects map), so a step the history drops or doubles fails the test (fix round 3). It excuses one product write, by the controller's ruling: a `z` the undo's own reference repair re-keys after the click moved the object to another parent (the key ordered it among the children of the parent it left), only when the repair's key replaced the lost one directly and the placement changed in the same click (seed 1599, `creation-guard.seeds.sync.test.ts`). A repair write over any other reference key is reported: `undo-oracle.sync.test.ts` stubs the creation guard to keep nothing and checks the oracle reports another person's shape moved out of the frame and their connector end detached, and a dropped redo step. - **Undo never writes a value the relay's door refuses (`door-guard.ts`, `door-restores.ts`).** Commands write only values the door accepts (item 1), but a step writes back what it removed, and a board can hold a value the door refuses (stored before the door existed, or arriving by a path no door sees): a peer left a width of 2^40, Ada resized it to 10 and undid, and the restore wrote 2^40 again, which the door refused with a terminal 4426 `hostile-values` close; her cache replayed it on every reconnect. Inside the undo or redo transaction, after the creation guard and before Yjs applies the step (one part of a grouped step at a time, so it is atomic per transaction), `DoorGuard.begin` reads what the step would write back (each removed item Yjs would copy, where it lands: an object's key or a network member, `restoresOf`) and judges each value under a key the door judges with the door's own table (`judgedKindOf`, `meta/field-values.ts`) and predicate (`drawableValuesReason`, `@canvas/schema`), against what the board holds there now (a field equal to it passes, as at the door, but in a size, which is judged whole as commands judge one; a re-created object has nothing stored, so its values are judged whole). What it would refuse is left out of the step it hands Yjs (`withoutRestores`): a value restored into an object on the board is left out and its key keeps its current value (through the history's delete filter, so the field is never emptied); a refused network member freezes both networks of its object for the step (no member restored or removed, so no segment ends at a vertex left out); an object the step re-creates holding a refused value is not re-created (in part it could not be read, and `restoreEmptiedFields` would refill the missing field with the value refused). Only that object is left out (fix round 1): what the step re-creates that refers to it (its children, a connector attached to it, a comment pinned on it) is re-created, and the history's reference repair in the same transaction re-roots the children where they were on the board and detaches the connector ends and pins, as for any referent that is gone (`repair/orphan-placement.ts`; its coordinates go through `finiteCoordinate` and its rotation stays within float32, so even a child of a frame whose own place is not finite re-roots to finite values the door accepts, and none has to be left out). A reference to it the step would write back into an object already on the board (a connector end, a pin, a child's parent) is left out, so the connector stays detached and the comment a point pin as the delete left them. In a grouped step the objects an earlier part left out count for the parts after it. The rest of the step applies; the step is used up, and Yjs pushes onto the other stack only what was applied, so a redo never replays what was left out. `UndoHistory.lastOmission()` says `'out-of-range'` after such an undo or redo and `lastOmittedObjects()` how many whole objects it did not bring back; the app shows "Undo could not bring back N objects because their stored values are out of range." when it left objects out, else "Part of this could not be undone: it holds a value out of range." (`runHistoryCommand`), the path the used-up notice of and takes. Cost: one pass over the step's removed structs; the predicate runs only on values under judged keys and reads the board only for a value it would refuse. Tests: `door-guard.test.ts` (a resize over 2^40, a value equal to the stored one restored, a frozen network, deletes of a poisoned shape, group and image with their children, connectors and pins), `door-guard.parts.test.ts` (a delete in parts of a frame of 1,200 shapes: a poisoned child left out; a poisoned frame left out and its 1,200 shapes back, re-rooted, in one step of parts, undo-redo-undo giving the same board), the seeded `door-guard.property.sync.test.ts` (two clients, poisons written raw and again later, single and grouped steps, undo and redo: no update refused by `judgeFieldWrites`, and the PROTECT oracle holds), `commands/invalid-untouched-field.test.ts` (the reproduction), `services/relay/src/server/undo-door-guard.test.ts` (real clients and relay: no close, the peer sees the rest, the poisoned frame's 1,200 shapes back re-rooted, and a redo) and the sync fuzz's writes around the door (`tooling/sync-fuzz/src/run/hostile-around-the-door.test.ts`). Known limit: the guard judges against this client's board; a value another client changed at the relay that has not arrived yet can still make the door refuse a restore, as it can a command.
- **Undo keeps references valid (`repair/reference-repair.ts`).** Undo reverts Yjs items, not commands, so it can remove an object something still refers to (since no longer one another client referred to since the step, which the undo keeps, but a pasted shape whose connector, also pasted, someone restyled; a pasted group whose member someone edited), or restore an object whose target someone has since deleted. Inside the same transaction, the history repairs every reference the step left dangling, with the rules a delete follows. A connector end on a removed object becomes a free point where it was, and a comment pin becomes a point pin where it was (the schema's `detachConnectorsFrom` and `detachCommentsFrom`, measured on the board before the step). An object whose parent was removed moves to the nearest surviving ancestor, or the board root, and keeps its place on the board, as `ungroup` does. Candidates are the step's touched objects and, by the reverse indexes, the dependents of what it removed, so the cost follows the step. Repaired objects appear as `updated` in the undo's change set. A redo brings the removed object back and re-attaches what was detached (tested). The rules and the geometry are the store's reference repair (below), run inside the undo's transaction so the repair is part of the step: a target someone else deleted earlier is measured where it was last seen, a connector whose two targets are both gone is deleted, and re-parented objects go on top of their new siblings. After the step, with its flags down, the history also runs the store's system repair pass over what the step touched, which finds nothing unless the step's own repair was refused. A reference that a _concurrent_ edit leaves dangling, one that arrives after the undo, is repaired by the receiving store ("Reference repair" below).
- **Reconnection.** A step is a set of Yjs item ids, not tied to a connection: an undo made offline is buffered with the other updates and converges when they are exchanged, and steps recorded before a disconnection can be undone after it (tested). The stacks live in memory with the store: a reload starts an empty history.

**1k undo steps on a 10k-object board** (`undo-manager.bench.ts`; 1k `moveObjects` commands, one per object; Node 22, Apple M1 Max, `--expose-gc`): the stacks keep about 4.8 MiB alive (about 5 KiB per step: the deleted field values Yjs must keep to restore them), beside 105 MiB for the board. Undoing or redoing one step with the stacks 1k deep, reference repair included, takes about 0.03–0.04 ms at p75 and 0.2 ms at p99 (means 0.04–0.05 ms; an earlier run with garbage-collection pauses from the two 10k boards in the process showed means of 0.25–0.33 ms and p99 up to 2 ms); `moveObjects` costs the same with or without a history recording it. Yjs checks each restored field against every step on both stacks (plus the one merged delete set of dropped redo steps), so undo cost grows with stack depth; the history has no depth limit yet (**deferred**: a cap, and releasing the oldest steps' kept content, when a product limit is set).

### Reference repair (`src/repair/`)

When undoing a component detach restores an instance while an offline collaborator adds a child
to the detached frame, the child moves to the nearest surviving container, keeping its world
placement. The changed parent's children are repair candidates even when only the parent was
listed in the update. The instance remains a valid connector target and comment anchor.
Unreadable parent entries still wait for their dependencies. The same pure plan supplies the
read-only projection; it does not require a stored layout change.

After concurrent deletes the board is repaired so that it keeps the schema's reference rules. A command validates against the board of the client that runs it, so a delete on one client merged with a reparent into, a connector to or a pin on the deleted object from another leaves every client with the same invalid board.

- **When.** `YjsDocumentStore#applyUpdate` collects the ids its change sets name (the remote one and any Yjs cleanup) and, once Yjs is done, plans a repair over them (`repair/repair-pass.ts`: the reference repair and the parent-cycle break below); only when the plan writes something does it open one transaction with `SYSTEM_ORIGIN`. It still runs when a listener threw, then rethrows. The undo history repairs inside its step and then calls the same pass (`internalsOf(store).repairReferences`). Local commands need none: they validate against the board they write.
- **What.** `planReferenceRepair(now, before, touched)` is a pure plan. Candidates are the touched objects that are present, plus, by the reverse indexes, the dependents of touched ids that are gone. An id counts as gone only when the document has no entry under it: an entry a merge left unreadable for a while is not treated as removed. The rules: a child of a missing parent moves to its nearest surviving ancestor, or the root, with the removed ancestors' placements composed into its own (`reroot`, as `ungroup` does); moved objects are re-keyed on top of their new parent's children, bottom first by `z` then id (`placeOnTop`; they keep their key when the parent's top key is not a fractional-index key); a connector end on a missing object becomes a free point where it was (the schema's `detachConnectorsFrom`); a connector whose two attached ends are both missing is deleted and a comment on it re-pinned; a comment on a missing object becomes a point pin where it was (`detachCommentsFrom`). `applyReferenceRepair` deletes, then writes with `setObject` (only changed fields); a value the store refuses, because a peer wrote an invalid field without validation, is skipped and the rest goes ahead.
- **Parent cycles (`repair/parent-cycles.ts`).** Commands refuse a parent that would close a cycle on their own board (`moveObjects` into the object itself or its descendant, `createObject` and `createObjects` whose listed parents loop: `parent-cycle`; `group` and `connect` give the parent to a new object, so they cannot close one). A merge can: Ada moves frame F1 into frame F2 while Bob moves F2 into F1, each valid where it ran, and each placement names the other; so can a plain move of a frame's descendant racing a move of the frame into it (the placement group carries the old parent), an undo, or a hostile client's placement naming its own object. Before nothing broke one: every member and everything under it had no board frame (the schema's transforms throw), every geometric command on them was refused `parent-cycle`, `validateBoard` reported the members, and `read().issues` said nothing. **The rule** (the controller's ruling): in each cycle the member with the lowest id (UTF-16 order, `compareKeys`) goes to the root, at the world placement found by walking the cycle once from it (its placement composed with each parent's up the cycle, the edge that closes it ignored, rotation brought into (−π, π]), or at its stored local placement when that is not finite; it keeps its `z` key (the cycle had no place among the root's children to keep). The other members keep their parents, so contents stay with their frames; nothing is deleted. The decision depends only on the stored values of the members, so every client that repairs writes the same values, and concurrent repairs by several editors converge: each writes one repair per cycle, the others' identical writes find nothing left to do, and a pass that finds nothing writes nothing (no repair storm). **One decision, two users.** `findParentCycleBreaks` decides for the repair, which writes the re-rooted member with `setObject` in the system transaction (only its `placement` group: no `updatedAt`, which only `runCommand` stamps, and no undo step, since histories never record a system origin), and for the reader, which applies the same break without writing (`store/parent-cycle-overlay.ts`): the snapshot, `get` and the reverse indexes show the member at the root, report it as a `parent-cycle` issue in `read().issues`, and show it where the repair then writes it, so nothing moves when the repair lands. That covers the moments before the repair runs (a change listener during `applyUpdate`), a repair the store refuses (a member with a field a peer wrote without validation), and a local raw write, which no repair follows. A command moving the re-rooted member while the store only shows the break writes the shown parent with its new position (`YjsTransaction#patchObject` starts a placement patch from the shown placement), which ends the stored cycle. A viewer's store runs the same pass on its own copy, as it does the reference repair; the relay refuses a viewer's updates, so a viewer never writes a repair to the board. **Cost:** the pass walks up from each touched object, each object at most once per pass (`findCycles`' settled set), so it reads the touched objects' chains of ancestors: O(touched + their ancestors), never the whole board; the reader does the same walk over the changed objects when it decodes them, plus the members of the cycles it already shows. When the reference repair re-parented anything, the chains of what it wrote are walked once more (a re-parent onto a surviving ancestor can close a cycle a concurrent edit opened), so a pass writes at most two transactions.
- **Vector networks: rules on read, not repairs.** A path's vertices and segments merge member by member, so two edits that were each valid can merge into a network no single edit could write: a segment ending at a vertex another client deleted (a delete racing a handle drag or a split of a segment ending there, or an undo restoring such a segment), two segments joining the same pair (two clients connecting the same vertices), or a vertex no segment touches (two clients deleting the two segments at it). The repair does not touch networks. `fromYjs` applies the rules when it decodes a path (`codec/network-visibility.ts`): it leaves out a segment with a missing end or joining a vertex to itself, all but the lowest id (UTF-16 order) of the segments joining one pair, and, once the network has a segment, every vertex no segment touches; a path with no segment keeps its vertices, so vector editing and the layers panel show what is left. **One definition, reported.** The rules are one function, `findNetworkMemberIssues` (`codec/network-well-formed.ts`): the reader hides exactly the members it names, the snapshot reports each of them in `issues` (`codec/hidden-member-issues.ts`: `hidden-segment` for a segment with a missing end, joined to itself or duplicating a pair; `stray-vertex`, the milder, for a vertex on no shown segment, since nothing drawn is wrong), naming the path (`key`), the list (`field`) and the member (`member`), and the sync fuzz fails a decoded path it names anything in, or clients whose issues differ. Reading never throws and never drops the path for a bad member; an unreadable member (not `[order, member]`) still makes the whole path unreadable (`malformed-field`). A stray vertex stays hidden from the pen tool, as before: once the network shows a segment, the read leaves it out, so vector editing cannot select it. `validateBoard` stays as it is, by our decision on: it lives in `@canvas/schema`, below this package, so it cannot see stored members, a snapshot never holds a hidden one, and the schema already refuses a malformed network in a board from elsewhere (`pathObjectSchema`). Is met by `read().issues`, where a store reports what it cannot show, and by the sync fuzz. Cost: the store compares the decoded path's member counts with the stored maps' (O(1)) and judges the stored network again only when they differ, O(n log n) in its members; a well-formed path costs what it did. The members stay in the document and `writeObject` never deletes one a read left out, so when the missing vertex comes back (an undo, a late update) the segment is whole again. Until fix round 1 the repair deleted such a segment when an update arrived, which lost edits depending on arrival order and client ids (a delete undone while another client dragged the segment's handle lost both the restore and the drag on every client when the dragging client's id was higher; an undo bringing a vertex back did not bring its segment back); the three cases are sync tests in both client-id orders. Every client decodes the same document the same way, so they converge. Cost: one pass over the segments with no sort (about 0.13 ms for a well-formed 1,000-segment path, on every decode of a path); the sort runs only when a rule hides something. The repair's check no longer reads networks: after a remote move of 100 paths of 1,000 segments it took 55 ms before and 0.016 ms after (`reference-repair.bench.ts`, "remote updates of 100 paths"; the whole update 87.6 ms before, 47.0 ms after, the rest being the decode of the 100 changed paths). `editNetwork` refuses a new vertex that joins no segment in a network that has one (a read would hide it) and deletes, with its edit, a vertex the edit leaves joined to nothing while the network keeps a segment; the transaction's per-member calls see every stored vertex, so a vertex set in one call can be joined in the next. **Collection (fix round 2, `codec/network-collection.ts`).** A write deletes, in its own transaction (one undo step restores them with the edit), the hidden members its edit makes unable to come back: the stored segments ending at a vertex id it creates (a new vertex under an old id, which agents can choose, is not the old vertex, so a segment that ended at the old one must not come back joined to the new one), the stored duplicates of a shown segment it deletes (so none shows in its place), and the stored segments ending at a vertex it deletes whose other end is stored (duplicates, in practice). So hidden members do not pile up and a later read stays on the one-pass path. A segment hidden because its other end is missing stays even when a write deletes the end it has: it waits for an undo of that missing end, and collecting it lets the writer's own undos write their older copy of it over a collaborator's edit (Ada deletes v3 while Bob drags s2's handle, then deletes v2: with s2 collected, her two undos restore her s2, without it Bob's drag; `edit-network-collection.sync.test.ts`). Known edges: a new vertex under an old id created while a collaborator's edit of a segment at the old vertex is still in flight shows that segment joined to the new vertex (the write cannot see it); after such a re-add collected a collaborator's edit of the old segment, the writer's undo of the re-add restores that edit (hidden, the new vertex gone) and her next undo, of the old vertex's delete, writes her own older copy of the segment over it (both client-id orders, on the undo guard of; reused ids are's); with the pen's fresh ids none of this arises; a segment ending at a vertex deleted for good by someone else stays stored, unseen, until the path is deleted. **Mirroring after a merge:** each member is last-writer-wins, so two clients dragging the two handles at one mirrored vertex at once can merge into a pair that no longer mirrors (each segment keeps one writer's handle); the next drag of either handle mirrors the pair again.
- **Last known state (`LastKnownObjects`, `LastKnownBoard`).** Change sets carry ids only, and Yjs keeps no readable value of a deleted object, so the store's decoded cache hands every object that leaves the document to a per-store memory, as last decoded, when it next flushes (it flushes before every transaction and at the start of every repair). The memory keeps the newest 4,096 removals, whoever made them, because a peer's reference to an object this client deleted long ago can arrive at any time; an object is forgotten when it comes back. A removed group's derived bounds count only the children removed with it (same batch), not ones removed from it earlier. `LastKnownBoard` lays that memory under the store (or, for undo, under the board before the step), and the schema's rules measure on it through `SubBoard`. An object nothing is known of has no geometry: a connector end on it goes to the connector's other end when that end's position is known (a free point, or an attached end measured on its target), else to the connector's origin; a child goes to the root keeping its coordinates. Below a parent cycle the same holds, with only a free other end known. Past the 4,096 bound, the objects a very large removal leaves in memory follow the order of that client's Yjs events, so memories can differ between clients.
- **Determinism and convergence.** The plan depends only on the board and the memory, iterates ids in sorted order and generates keys deterministically, so two clients with the same inputs write the same values (tested: both clients' repair change sets are equal). It checks references when it runs, so a child that a reparent already put in a valid parent is left alone. Placement is one group, so a repair and a concurrent user's move of the same object keep one of the two placements whole, never a mix: when the user's wins and names a removed parent, the repair runs again from the user's position (`commands/placement.sync.test.ts`). Clients whose memories of removed objects differ can repair the same object concurrently from different last-known states; one repair's placement wins whole. Either way every client holds the same valid board. A repaired board plans nothing, so the passes stop: the fuzz harness sees no repair loops.
- **Undo after a repair.** The repair's writes are later than the edit it overwrote, so undoing that edit leaves the repaired fields alone (Yjs keeps a later change by someone else) and reverts only what the repair did not touch, such as `updatedAt`; no repair follows (tested in both merge orders).
- **Errors.** When a listener throws during `applyUpdate`, the repair still runs and the listener's error is rethrown; when the repair then fails too (a listener throwing on its change set as well), `applyUpdate` throws an `AggregateError` with both, the listener's first.
- **Cost.** One remote move on a 50k-object board, applied and checked (`reference-repair.bench.ts`; Node 22, Apple M1 Max): mean 0.04–0.07 ms, p75 about 0.045 ms, against about 0.03 ms without the repair (which then leaves the decoding to the next read). Planning the repair of a remote delete that orphans a 1k-child group with 50 connectors: about 3.9 ms mean. Validation is left to the writes (checking every repaired object beforehand as well cost 13.5 ms). A load decodes every object at the end of `applyUpdate` instead of on the first read, which it would pay moments later anyway. The same bench isolates the check's share of a 50k load: load then `read()` with the check and without it (the update applied to the Yjs document directly) both measured 3.6–4.6 s in the per-field layout and 2.8–3.2 s in the grouped layout, within each other's noise; the check alone over every object takes 74–107 ms (mean 87 ms) in either layout, since it reads decoded objects.

### Assets a board uses (`src/assets/`)

The relay records which assets each board uses when it snapshots the board, so the assets service can collect the unused ones after a grace period. Decoding the board to find them costs seconds at 50k objects (the store load above), too much on every snapshot. `listAssetIds` instead walks the encoded state in update format v1 (`update-scan.ts`, the struct and delete-set encoding of Yjs's `readClientsStructRefs` and `readDeleteSet`) without building a document: it skips text, formatting and nested values in place, keeps one flat record per map entry under the two keys that hold an object's type and asset ids (the `identity` and `style` groups of the one layout since) and per shared type, then reads the values of images and videos only. The `meta` map's layout stamp is never an object's entry, so it is skipped with the rest.

- **Placement.** Yjs writes an item's parent and key only when the item was inserted with no neighbour. A map value that replaced another has the replaced value as its origin instead, so the key and parent are found by following origins to the first value of that key; an entry under any other key can neither be nor lead to a relevant one, which is why the scan drops them. An entry is live when the delete set does not cover it, and it counts only when its parent is a live `Y.Map` stored in the top-level `objects` map.
- **Trust.** Values that are not asset ids (a peer that skipped validation) are left out; an origin chain that leaves the update (a partial update) or loops (a malformed one) is skipped, not followed forever. Each item's chain end is remembered (`scanned-placements.ts`, shared with the relay's stamp check), so placing every item is linear however long the chains; an item with no left neighbour takes its key from its right one, as Yjs does. A content number update format v1 does not define throws.
- **Cost** (`list-asset-ids.bench.ts`, 50k-object board, Apple M1 Max, Node 22, measured while other work shared the machine): 0.3–0.8 s against 1.3–3.3 s for `Y.applyUpdate` alone in the same runs, 3–10× less; the scan itself is 0.17–0.4 s of it. The relay's snapshot already merges the state in a `Y.Doc`, so this is the added cost per snapshot.
- **Why not Yjs's own reader.** `Y.decodeUpdate` builds an object per item with its content (849k items at 50k objects) and took about as long as `Y.applyUpdate`. Update format v1 is the sync protocol's wire format, which Yjs keeps stable across releases; `update-scan.test.ts` checks the scan against `Y.decodeUpdate` over every content kind, so a Yjs upgrade that changed it fails there.

| Public API                                              | Purpose                                                                                       |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `highestLayoutStamp(doc, maxLayout?)`                   | Reads the highest retained supported stamp; Infinity includes future stamps for audits.       |
| `preserveHighestLayout(doc, onUnsupported?)`            | Maintains the highest observed stamp before garbage collection; returns an observer disposer. |
| `discardPendingUpdates(doc)`, `DiscardedPendingUpdates` | Removes unresolved fragments from memory and returns content-free audit counts.               |

`preserveHighestLayout(doc)` maintains a relay/persistence document's highest observed supported
layout stamp, using the existing `meta/document` representation. Install it before applying
updates; its returned function removes the observer. It observes deleted stamp values before
Yjs garbage collection, restores a concurrent lower winner, and preserves the higher schema
version when layouts tie. `readBoardLayout` reads the highest remaining chain value. Already
collected historical values cannot be reconstructed; this does not migrate document layout.

`discardPendingUpdates(doc)` clears only unresolved Yjs structs and delete sets in memory and
returns `DiscardedPendingUpdates` counts/missing clocks for logging or an offline audit. The
original complete client state must be resynced to recover removed fragments; integrated
content is untouched. `UpdateStampCheck` refuses a hub still holding pending structs rather than approving
an update that could release unchecked fragments.

`UpdateStampCheck(doc, maxSteps?, isHistoricalReplay?)` defaults to strict live admission.
Only persistence replay enables the historical flag: supported older stamps may arrive after
newer ones in the durable log, while writer proof, layout upper bounds and dependency checks
still apply. The caller must maintain the highest supported layout with `preserveHighestLayout`.

### Relay encoding and retained pending history

`DocumentStore.encodeState()` remains the full persistence/diagnostic encoding,
including unresolved structs and pending delete sets. Cache compaction must use it.
`encodeSyncState(stateVector?)` instead sends integrated history and pending deletes
without unresolved structs, which the relay cannot yet admit. `hasPendingStructs`
reports retained incomplete history; encoding never clears it. Missing dependencies
can later integrate those fragments. This is not a cache reset or a claim that all
retained fragments have reached the relay.

The Yjs 13.6.33 adapter uses an encoding-only document/store view sharing the
integrated struct map and pending deletes. Its own pending-struct field is null;
the live document is never mutated, including during nested encoding or exceptions.
The pinned-version contract test requires reviewing the encoder's store-only reads
before changing Yjs. No document writer or stored layout version changes.

### Clients per update

Yjs sets aside the structs it cannot integrate yet (`addStackToRestSS`) with one pass over
the clients left per stacked struct, so an update of one struct per client, each depending on
the client below and the lowest on a client nobody sent, costs time quadratic in its clients.
The stamp check's replay copied that filter: an editor's 1 MiB update of 95,000 clients
(`meta/__fixtures__/stacked-clients.ts`) held the relay for 31–37 s (measured on a loaded
machine; Yjs itself: 0.3 s at 10,000 clients, 5.6 s at 40,000). The replay now leaves a
set-aside client in its list and drops it when it comes up (`meta/update-integration.ts`),
which takes the same clients in the same order: `meta/update-integration.equivalence.test.ts`
holds it to the old replay (`meta/__fixtures__/eager-set-aside-replay.ts`, a test oracle) on
3,000 random updates of many clients,'s seed 2354 and stacked chains. The same update
checks in about 69 ms (`meta/update-stamp-check.stacked.test.ts` asserts under 500 ms, the
100 ms budget with a CI margin).

`MAX_UPDATE_CLIENTS` (10,000) bounds the clients one update may carry, counted in O(1) from
the update's first number (`countUpdateClients`: its client blocks, one per client in any
update Yjs writes). The largest honest update a writer sends is its sync step 2 after the
relay lost the board, carrying every client that wrote it: the sync fuzz's largest configured
run (64 clients × 40 steps, a new client per raw write) stays under 2,700, and a board gains
one client per editing session. Live admission (`UpdateStampCheck` without
`isHistoricalReplay`) refuses an update past it before scanning (`too-many-clients`); durable
history is not bounded. The bound is the relay's only: stores apply what they are given. A
long-lived board's whole state legitimately carries more clients (one per editing session),
and a cached snapshot may keep pending structs, so a store-side refusal would fail honest
cache restores while a hostile relay could still get past it (fix round 1 removed one). Tests:
`meta/update-client-bound.test.ts`.

### Plain update value nesting

`applyUpdate` scans update-v1 content before Yjs decodes it and throws `UpdateDepthError`
above 128 nested plain object/array containers. `assertUpdateDepth` is also available to
callers that merge encoded updates before applying them. The check retains no struct/delete
records; it is a depth preflight, not schema or writer-stamp validation. JSON-string content
and shared Yjs type nesting are outside this plain lib0 value bound. The layout written by
this build is unchanged.

The scan reads within the bytes it is given (`assets/update-bounds.ts`). lib0's
`readUint8` does not check the end: past it, it returns `undefined`. A scan that trusted a
declared count looped that many times over nothing, so 15 bytes declaring 2^49 plain values
froze the process (on main, any editor could reach it through the relay's stamp check). Every
byte read now refuses to pass the end, every count (clients, structs, plain values, array and
object entries, JSON strings, deleted ranges) is refused when it is larger than the bytes left,
and an unknown plain-value tag is refused as lib0's `readAny` refuses it; all three throw
`MalformedUpdateError`. Parent names and keys are range-checked before UTF-8 decoding, including the lib0 fallback used without TextDecoder. Every step of the scan consumes at least one byte or throws, so its
work is linear in the update's length, and its recursion stops at the bound.

Known limits, left for follow-ups:

- **Repeated scans (M1).** Large paths scan the same bytes two or three times: the cache
  binding scans a snapshot before the store's `applyUpdate` scans it again, and the relay's
  load scans the merged history in `mergeStoredBoardHistory` and again in the persistence
  extension. Each scan is linear; no paired benchmark measured their cost against main.
- **Other nesting (M3).** The bound covers lib0 plain values only. JSON-string content
  (`ContentJSON`, `ContentEmbed`, `ContentFormat`) and chains of nested shared types (`Y.Map`
  in `Y.Map`) are not bounded. The store's own reader is iterative; other recursive consumers
  (`JSON.stringify` in export and clipboard, Yjs `toJSON`, Yjs's recursive delete and
  collection over nested types) are not checked.

The relay rejects these updates terminally with 4426 / `update-depth-exceeded`, before
application or forwarding. A viewer's update the scan cannot read is closed with 4426 /
`update-malformed` (a writer's with the retried 4425 / `incomplete-update`). Cached snapshots and tail updates are checked before merging;
an unsupported cache stops synchronization without deleting or rewriting its bytes.
Persisted relay history fails its load before decoding rather than silently dropping content.
A reload does not repair unsupported data; no automatic conversion or recovery UI is supplied.

### Read-only repair projection

`RepairMode` is `write` or `read-only`; `YjsDocumentStoreOptions.repairMode` chooses it at
creation and `DocumentStore.setRepairMode(mode)` changes it when the collaboration role changes.
Read-only automatic repair uses the same reference plan and deterministic cycle root as a writer,
in the decoded view and reverse indexes. It emits no document update and leaves persisted bytes
unchanged. Explicit local transactions remain available. Switching to `write` materializes valid
repairs through normal validated transactions, including when view listeners throw.

Change sets retain raw entry classifications and additionally name virtual changes: creation,
update or deletion according to the visible before/after value. A role projection also notifies
view subscribers without fabricating document-update bytes. Cycle issues retain the complete
root key and total member count with a bounded member preview; issue ordering is key, then code.

Commands that change another stored cycle member's placement first validate the required root
normalization and materialize it in the same transaction. If an unrelated invalid field prevents
that repair, the whole placement command is refused before writing. Deletion remains available;
it does not require validating an unrelated cycle root. Normalized roots receive the command-time
`updatedAt` stamp like its other writes. This avoids moving the displayed root
as a side effect, bypassing validation, or making cold readers depend on a past displayed position.
Legitimate editor repair updates supersede the viewer projection when received: a viewer does not
speculate about repair bytes it has not received.

Regression coverage: `store/read-only-repairs.test.ts`, `store/parent-cycle-changes.test.ts`,
`store/parent-cycle-commands.test.ts`, `repair/parent-cycle-group.sync.test.ts`, and the opposite
client-id order, refusal, self-parent, undo and overflow cases in `repair/parent-cycle-*.test.ts`.

### Restoring a historical board

`restoreBoardCommand`, `restoreBoardInputSchema` and `RestoreBoardPlan` accept a complete
historical Yjs v1 state as `{ state: Uint8Array }`. Run the command under the restoring member's
origin through `runCommand`. The command decodes the chosen state in an isolated read-only
store, refuses unreadable layouts, incomplete dependencies and invalid projections, then
writes only object differences as new CRDT operations. It preserves original object ids and
creation metadata; the command clock timestamps actual restored writes. Untouched objects
are not rewritten, so concurrent edits to them survive. More than 1,000 differences use
referent-first replacement parts followed by referrer-first removal parts, grouped as one
undo step with the existing guards. Byte admission still belongs to chunked sync.

Restore is a deliberate board-wide command: `BoardReader` has an optional snapshot reader,
required for this command to find later objects to delete. Binary historical state is obtained
from authenticated history routes, and is not exposed through the JSON-only agent command
registry. The relational comment messages are outside the document and are never restored.

The owner approved the optional scalar `meta/lastRestore` slot on 2026-10-05. Each nonempty
restore transaction writes `{ version: 1, id: <UUID>, part, parts }` alongside its object changes;
all parts share an injected fresh operation identity. The marker grants no authority and carries
no author, operator or timestamp. Relay authentication and persisted row metadata supply those.
Undo tracks object changes and does not write another restore intent. Restoring identical content
writes neither object changes nor a marker. Timeline consumption and canonical persistence
integration remain required before the feature is complete.

`openHistoricalStore(state)` exposes the restore command's complete-state validation to the
read-only history preview, avoiding a second decoded board just for validation. Its isolated
store projects automatic repairs without writing and refuses incomplete dependencies or
unreadable entries/layouts. The caller owns destruction; the factory does not create a cache,
relay writer or portable stamp evidence. Shell policy disables explicit commands in a preview.

Component storage: layout 5 adds component and instance objects, an optional own-key constraints record, a retirement flag, and a Y.Map of plain override records by child path. Default start/start constraints remain absent. Schema version 4 and layout 5 accept older content without rewriting it. Deleting a main retains its definition and detaches known surviving instances in one undo step; concurrently placed instances keep resolving the retained definition. Collection is deferred. Agent repair mode keeps ordinary repairs outside component content writable, but projects repairs within definitions (including orphan, cycle and depth repairs) without writing foreign mains. Detach materializes nested mains as plain frames. Detach gives its copies stacking keys of their own, in the main's order, never the main children's keys, so two people detaching one instance at once merge into a total order. A frame restored to an instance by undo is protected if another person edited its content; split-paste undo retains the whole definition across every transaction part.

Main-creation undo also retains and retires the definition. Wrapped existing members return
to their former parents; late offline instances retain overrides and can resolve an empty
retired main until redo. A pasted definition keeps descendants created in that same step.
Restoring an older board likewise retains removed definitions and their absent descendants,
while objects present in the historical snapshot are restored normally. No snapshot storage
or retained-definition collection is added.
